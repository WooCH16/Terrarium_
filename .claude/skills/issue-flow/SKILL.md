# issue-flow: 이슈 하나를 8단계로 처리한다

이슈 번호 하나를 받아 **분석 → ADR 점검 → 스펙 → 스펙 리뷰 → 계획 → 계획 리뷰 → 구현 → 구현 리뷰** 순서로 처리한다. 단계를 건너뛰지 않는다. 리뷰 세 번은 모두 **리뷰어 서브에이전트**가 한다. 구현은 **시험 먼저**다.

이 스킬은 **PR을 만들지 않고, 머지·push도 하지 않는다.** 그 일은 `docs/adr/workflow.md`의 GitHub Actions 흐름이 맡는다.

## 시작

1. 이슈 번호 `N`을 정한다. 말에 번호가 없으면 묻는다(이것만 묻는다).
2. 저장소: `git remote get-url origin`의 `소유자/이름`. 이슈는 읽기만 한다: `gh issue view N --repo <소유자/이름> --json number,title,body,state,labels,comments`. 이슈에 댓글·라벨을 쓰지 않는다.
3. 진행 폴더 `docs/issues/N/`를 만들고 `progress.md`를 아래 모양으로 시작한다. 이미 있으면 읽고 `상태`가 멈춘 단계부터 이어 한다.
4. 예산을 정한다. 사용자가 말하지 않았으면 **리뷰 단계마다 3바퀴**다. 사용자가 "예산 N바퀴"라고 하면 그 값이다.

## progress.md 모양

```markdown
# 이슈 #N 진행: <이슈 제목>

- 상태: <단계 이름> | 완료 | 중단(예산 소진)
- 예산: 리뷰 단계마다 <k>바퀴
- 마지막 갱신: <YYYY-MM-DD HH:MM>

| # | 단계 | 결과 | 리뷰 바퀴 | 남은 블로커 |
|---|---|---|---|---|
| 1 | 분석 | | - | |
| 2 | ADR 점검 | | - | |
| 3 | 스펙 | spec.md | - | |
| 4 | 스펙 리뷰 | | 0/<k> | |
| 5 | 계획 | plan.md | - | |
| 6 | 계획 리뷰 | | 0/<k> | |
| 7 | 구현 | 시험·커밋 | - | |
| 8 | 구현 리뷰 | | 0/<k> | |

## 기록
(단계마다 몇 줄: 무엇을 읽고 무엇을 정했는지, 리뷰어 판정 요지)
```

단계가 끝날 때마다 표의 그 줄과 `상태`, `마지막 갱신`을 고친다.

## 단계

| # | 단계 | 하는 일 | 끝나는 조건 |
|---|---|---|---|
| 1 | 분석 | 이슈 본문·댓글과 관련 코드·시험·문서를 읽는다. 무엇이 문제이고 어디를 바꾸는지 `기록`에 적는다 | 바꿀 파일 후보와 모르는 점이 적혀 있다 |
| 2 | ADR 점검 | `docs/adr/*.md`, `docs/checks/owner-decisions.md`, `docs/known-limitations.md`에서 관련 결정을 찾는다. 이슈가 결정과 부딪히면 그 결정 번호를 적는다 | 관련 결정 목록이 있다. 부딪힘은 블로커로 적는다(스스로 결정을 바꾸지 않는다) |
| 3 | 스펙 | `docs/issues/N/spec.md`: 목표, 범위 밖, 완료 기준(기준마다 확인 방법), 관련 결정 | 모든 완료 기준에 확인 방법이 있다 |
| 4 | 스펙 리뷰 | 리뷰어 서브에이전트(아래) | 판정 `통과` |
| 5 | 계획 | `docs/issues/N/plan.md`: 작은 단계 목록. 단계마다 **먼저 쓸 실패하는 시험**, 바꿀 파일, 돌릴 명령 | 단계마다 시험이 정해져 있다 |
| 6 | 계획 리뷰 | 리뷰어 서브에이전트 | 판정 `통과` |
| 7 | 구현 | 계획 단계마다: 시험을 쓴다 → 돌려서 **실패를 본다**(출력 요지를 `기록`에) → 고친다 → 돌려서 통과를 본다. 관련 시험 파일만 돌린다. 끝나면 로컬 커밋 | 모든 단계의 시험이 실패 → 통과를 거쳤다 |
| 8 | 구현 리뷰 | 리뷰어 서브에이전트(스펙·계획·`git diff`를 준다) | 판정 `통과` → `상태: 완료` |

시험을 먼저 쓸 수 없는 단계(문서만 바꾸는 단계 등)는 계획에 "시험 없음: <이유>"와 대신 확인할 방법을 적고, 계획 리뷰에서 리뷰어가 받아들여야 한다.

## 리뷰어 서브에이전트

- 리뷰는 **새 서브에이전트**가 한다(Agent 도구, 새 맥락). 이 세션이 스스로 통과를 주지 않는다.
- 리뷰어에게는 읽기만 맡긴다. 파일을 고치게 하지 않는다.
- 브리프는 [reviewer.md](reviewer.md)를 채워 보낸다. 리뷰어는 `판정: 통과` 또는 `판정: 블로커 있음`과 블로커 목록(파일·줄·이유)을 돌려준다.
- 블로커가 있으면 고치고 다시 리뷰한다. 한 번 보낼 때마다 그 단계의 리뷰 바퀴가 1 는다.
- 블로커가 아닌 의견(작은 제안)은 고쳐도 되고 `기록`에 남기고 넘어가도 된다.

## 예산이 떨어지면

리뷰 바퀴가 예산에 닿았는데 블로커가 남았으면:

1. **통과시키지 않는다.** 다음 단계로 가지 않는다.
2. `progress.md`의 `상태`를 `중단(예산 소진)`으로, 그 단계 줄의 `남은 블로커`에 블로커를 그대로 적는다. `기록`에 마지막 리뷰어 판정 원문 요지와 "다시 시작하려면 무엇이 필요한지"를 적는다.
3. 멈추고 사용자에게 그 내용을 보고한다.

ADR 점검의 부딪힘(2단계)도 같은 방식으로 멈춘다. 결정은 사용자가 바꾼다.

| 이런 생각이 들면 | 실제 |
|---|---|
| "블로커가 사소해 보이니 통과로 하자" | 블로커인지는 리뷰어가 정했다. 예산이 끝났으면 중단이다 |
| "한 바퀴만 더 돌리면 될 것 같다" | 예산을 넘기지 않는다. 사용자가 예산을 늘리면 이어 한다 |
| "리뷰어 대신 내가 다시 보면 된다" | 리뷰는 서브에이전트만 한다 |
| "시험은 구현 뒤에 쓰자" | 7단계는 실패를 먼저 본다. 본 실패를 `기록`에 적는다 |

## 끝

- `상태: 완료`면 바뀐 파일, 커밋, 시험 결과, 리뷰 바퀴를 보고한다.
- PR·머지·push는 하지 않는다. 다음은 사용자 또는 `docs/adr/workflow.md`의 흐름이 한다.

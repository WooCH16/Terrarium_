# CI 묶음 처리 (ci-batch-flow)

관련 이슈를 묶음으로 처리해 **묶음 하나 = PR 하나**로 만들고, [중간 브랜치]에 모았다가 [메인 브랜치]로 **한 번만** 병합한다. 목적은 메인이 바뀔 때마다 CI·시험이 반복해 도는 시간을 줄이는 것이다. 시험을 건너뛰거나 끄는 것으로 줄이지 않는다.

## 단계

### 1. 현황 확인 (읽기만, 고치지 않음)

아래를 모두 보고 **한 표**로 보고한다: 위치 | 언제(이벤트·브랜치) | 무엇을 | 의도한 설정인가.

- **실행 위치:** 로컬 명령(`package.json` scripts, `scripts/` 실행 파일), CI(`.github/workflows/*.yml`만 실제로 돈다. 다른 폴더의 yml은 틀일 뿐이라 따로 적는다), git 훅(`.husky`, `core.hooksPath`, `.git/hooks`의 sample 아닌 것), 에이전트 훅(`.claude/settings*.json`의 hooks).
- **실행 시점:** `on:`의 이벤트(push, pull_request, merge_group, schedule/cron, workflow_dispatch)와 브랜치 필터, `concurrency`.
- **의도하지 않은 설정:** 기준 브랜치와 비교한다. `git diff --stat origin/<main>...HEAD -- .github`, `git log origin/<main>..HEAD -- .github`(작성자·날짜), `schedule:`·`cron:` 검색.
- **실제 횟수:** `gh run list --limit 50 --json event,headBranch`로 어떤 이벤트·브랜치에서 몇 번 돌았는지 센다.
- **자주 놓치는 원인:** 중간 브랜치 → 메인 PR이 열려 있으면 `pull_request` 때문에 중간 브랜치에 push할 때마다 CI가 돈다.

의도하지 않은 것으로 보이는 설정이 있으면 **지우지 말고 멈춰서 묻는다.**

### 2. 이슈 묶기 → 계획 보이고 승인받기

- 열린 이슈 본문(끝나는 조건, 먼저 끝나야 할 것, 건드리는 파일)을 읽는다.
- **묶는 기준:** 같은 파일이나 같은 기능을 건드리는 것, 의존 관계(A가 끝나야 B)인 것. 관련 없는 것은 억지로 묶지 않는다.
- **PR을 만들지 않는 묶음:** 코드가 있고 소유자의 직접 확인(실제 로그인, 깨끗한 계정 설치, 서명 결정)만 남은 이슈. 확인 목록만 정리해 보고한다.
- **이번에 빼는 것:** 실제 모델 호출·비용이 드는 실행처럼 소유자가 횟수·비용을 먼저 정해야 하는 이슈. 이유를 적는다.
- 보고: 묶음 | 이슈 번호 | 묶은 이유 | 할 일. [중간 브랜치]와 [메인 브랜치] 이름을 제안한다(이미 메인으로 가는 PR이 열린 작업 브랜치가 있으면 그것이 자연스러운 중간 브랜치다).
- CI 횟수 예상을 함께 보인다(아래 "CI 횟수 세기").
- **승인 전에는 구현하지 않는다.** 계획을 보였으면 한 번 묻고 멈춘다. 같은 질문을 되풀이하지 않는다. 계획을 본 뒤 "진행해" 같은 분명한 말이 오면 승인으로 본다.

### 3. 묶음마다 작업 (승인 뒤)

1. [중간 브랜치]에서 `bundle/<묶음 이름>` 브랜치를 딴다.
2. 끝나는 조건의 명령을 먼저 돌려 지금 상태를 본다. 이미 충족된 조건은 고치지 말고 기록만 한다.
3. 고칠 것은 **시험 먼저**(실패 확인 → 고침 → 통과). 작업 중에는 **바꾼 것과 관련된 시험 파일만** 돌린다.
4. **커밋은 이슈 단위로** 나누고 메시지를 `#<번호> …`로 시작한다. 코드 변경이 없는 확인형 이슈는 끝나는 조건별 결과를 적은 확인 기록 문서가 그 이슈의 커밋이 된다.
5. PR을 올리기 직전에 **전체 단위 시험을 한 번** 돌린다(무거우면 백그라운드로, 메모리가 부족하면 다른 무거운 작업을 멈춘다). 앱 스모크처럼 무거운 시험은 아래 "통과한 시험은 다시 돌리지 않는다"를 따른다.
6. 묶음 브랜치를 push하고 PR 하나를 연다. 대상은 [중간 브랜치]. 본문에는 바꾼 것, `Closes #N`(이슈마다 한 줄), 실행한 시험과 결과 표, 반복 횟수를 넣는다.
   - **주의:** 닫기 키워드는 기본 브랜치로 병합할 때만 작동한다. 중간 브랜치 대상 PR이면 본문에 "메인 병합 뒤 닫는다"고 적고, 메인 병합 뒤 이슈를 닫는다.
7. PR의 CI가 통과하면 **병합 커밋 방식**(`gh pr merge <N> --merge`)으로 중간 브랜치에 넣는다. 스쿼시하면 이슈별 커밋 구분이 사라진다. 그 뒤 묶음 브랜치(로컬·원격)를 지운다.
8. 다음 묶음으로 간다.

### 4. 메인 병합 (승인 뒤에만)

모든 묶음이 중간 브랜치에 들어가고 중간 브랜치 CI가 통과하면 **멈추고 최종 보고와 함께 메인 병합 승인을 묻는다.** 승인 뒤 한 번만 병합하고, 그때 메인 CI가 한 번 도는 것을 확인한 뒤 남은 이슈를 닫는다.

## 머지 큐 (메인 세션이 병합한다)

여러 PR이 [중간 브랜치]를 향해 열려 있으면 메인 세션이 줄을 세워 한 번에 하나씩 병합한다. GitHub의 머지 큐 기능은 쓰지 않는다. 이 저장소의 [중간 브랜치]는 `WooCH16/beta`다(docs/plan-ci-merge-queue.md).

1. 의존 순서, 올린 순서로 줄 세운다.
2. 맨 앞 PR을 [중간 브랜치] 최신에 맞추고 CI를 기다린다. [중간 브랜치]로 가는 PR의 CI는 바뀐 부분에 닿는 시험만 돈다(`node scripts/test.mjs --changed`).
3. 통과하면 병합한다. 실패하면 큐에서 빼고 원인을 고친 뒤 다시 넣는다. 다음 PR은 새 최신에 다시 맞춘다.
4. 큐가 비면 [중간 브랜치] → [메인 브랜치] PR로 전체 CI를 돌린다. [메인 브랜치] 병합은 사용자가 시킬 때만 한다.

로컬에서도 같은 규칙을 쓴다: `node scripts/test.mjs --changed <기준 브랜치>`. 고른 목록과 건너뛴 이유가 출력된다.

## 통과한 시험은 다시 돌리지 않는다

이 세션과 이 세션이 시킨 에이전트 모두에 적용한다.

1. 시험이 통과하면 그때의 커밋을 기록에 적는다. 아직 커밋 전이면 `git diff --stat` 요지를 함께 적는다. 예: `스모크 40개 통과 @ 3d3ba93`.
2. 다시 돌릴지는 `git diff --name-only <통과 때 커밋>`으로 그 뒤에 바뀐 파일을 보고 정한다. **바뀐 파일에 닿는 시험만** 돌린다.
3. 앱 스모크(`npm run smoke`, `app/test/smoke.mjs`)는 `app/main.js`, `app/preload.cjs`, `app/tower/`, `app/lib/`, `app/test/smoke.mjs`, `app/package.json` 중 하나가 바뀌었을 때만 다시 돌린다. 문서·하네스·다른 시험 파일만 바뀌었으면 돌리지 않는다.
4. 하네스 시험은 바뀐 모듈의 시험 파일과 그 모듈을 불러 쓰는 시험 파일만 돌린다(`harness/test/` 안에서 모듈 이름으로 찾는다).
5. 돌리지 않은 시험은 보고에 한 줄로 남긴다: `다시 돌리지 않음: <시험> — <통과 때 커밋> 뒤 관련 파일 변경 없음`.
6. 관련 파일이 바뀌었는지 가릴 수 없으면(설정·공용 도우미 변경 등) 돌린다.

## 반복 세기

반복 1회 = "구현 → 시험 → 수정" 한 바퀴. 묶음별 횟수와 전체 횟수를 기록해 PR 본문과 최종 보고에 적는다.

## CI 횟수 세기

- 묶었을 때: 묶음 PR마다 1 + (중간→메인 PR이 열려 있으면) 묶음 병합마다 1 + 메인 병합 1.
- 이슈마다 PR을 만들고 매번 메인에 병합했을 때: 이슈마다 (PR 1 + 메인 병합 1). 수정 push마다 더 늘어난다.
- 실제 횟수는 `gh run list --json headSha,event`로 세어 예상과 비교한다.
- **CI를 기다릴 때:** `gh run list --commit <sha>`는 `pull_request` 실행을 찾지 못해 빈 목록을 돌려준다(그걸 조건으로 기다리면 끝나지 않는다). `gh run list --limit 10 --json headSha,status,conclusion`을 받아 `headSha`로 거르거나 `gh pr checks <N>`을 쓴다. 대기 명령에는 반드시 최대 시간을 둔다.

## 하지 말 것

- 승인 없이 CI 설정 파일(워크플로)을 추가·수정하지 않는다.
- [메인 브랜치]에 직접 push하거나 병합하지 않는다. 병합은 승인 뒤.
- 시험을 건너뛰거나 끄거나 느린 시험을 빼는 방식으로 CI 시간을 줄이지 않는다.
- 이 흐름을 `/goal`로 걸지 않는다. 중간에 승인 대기 멈춤이 있어 goal 종료 훅과 서로 막는다(같은 질문이 반복된다). 승인 뒤 단계만 맡길 때 끝 조건에 "승인 대기 중단 조건에서 보고하고 멈추면 끝으로 본다"를 넣는다.

## 중단 조건 (하나라도 해당하면 멈추고 보고)

- 의도하지 않은 것으로 보이는 CI 설정을 발견함(지우기 전에 확인).
- 이슈 묶음 계획을 만듦(승인 전에는 구현하지 않음).
- 전체 시험이 실패했는데 이번 변경 탓인지 기존 문제인지 가릴 수 없음.
- 같은 시험 실패를 두 번 고쳤는데도 통과하지 않음.
- 묶음 안의 이슈끼리 요구사항이 충돌함.
- 한 묶음에서 5회 반복해도 시험이 통과하지 않음(다음 묶음으로 넘어가지 않음).
- 전체 반복 20회, 또는 시작한 지 2시간.
- 중간 브랜치를 메인으로 병합할 준비가 끝남(병합은 승인 뒤).

## 최종 보고 모양

1. CI 현황표(1단계).
2. 묶음 목록: 묶음 | 이슈 | 묶은 이유 | 결과(PR 번호 또는 "확인 목록만").
3. 숫자: 처리한 이슈 수, 만든 PR 수, 묶음별 반복 횟수와 전체 횟수, CI 실행 횟수(실제 대 이슈마다 PR이었을 때의 예상).
4. 처리하지 못한 이슈와 이유, 소유자가 확인할 목록.
5. 결정할 것: 메인 병합 승인.

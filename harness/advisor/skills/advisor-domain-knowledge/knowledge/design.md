# 디자인 어드바이저 지식

## 사용 원칙
- 수치·예시는 참고다. 대상 프로젝트의 디자인 시스템과 지시의 범위가 우선이다. 지시 밖의 일(감사, 대안 비교 등)은 새 작업으로 만들지 말고 전제·위험에 적는다.
- 지시가 담고 있는 해결책보다 그 밑의 결정을 먼저 찾는다. "버튼 색 바꿔줘"의 실제 결정은 "이 행동을 얼마나 눈에 띄게 할 것인가"다.
- 지시에 숨은 전제를 찾는다. 사용자가 누구인지, 무엇이 문제인지, 무엇을 성공으로 볼지 셋 중 비어 있는 것을 먼저 짚는다.
- 근거 수준을 구분해 말한다. 관찰된 사실, 해석, 추정을 섞지 않는다. 확실하지 않으면 확인 방법을 함께 제안한다.
- 아래 실패 패턴은 영역을 넘나든다. 예를 들어 시각 위계 문제로 보이는 것이 정보 구조 문제일 때가 많다. 증상이 나타난 영역보다 원인이 있는 영역을 다룬다.

## 사용자 조사와 문제 정의

**자주 보는 실패와 근본 원인**
- 해결책 검증형 조사: 이미 정한 기능에 대한 동의를 모으려고 조사를 설계한다. 질문은 유도형이 되고 결과는 확증 편향으로 읽힌다. 원인은 조사 목적을 "결정을 바꿀 수 있는 정보"로 정의하지 않은 데 있다.
- 방법과 질문의 불일치: "왜"를 알고 싶은데 설문을 돌리거나, "얼마나 많이"를 알고 싶은데 인터뷰 5건으로 일반화한다. 정성 조사는 이유와 맥락을 찾는 데, 정량 조사는 규모와 분포를 재는 데 쓴다.
- 말과 행동의 혼동: 사용자의 미래 의향("쓸 것 같다")이나 선호 진술을 행동 증거처럼 다룬다. 사람은 자기 행동을 정확히 예측하지 못한다. 실제로 한 행동, 최근의 구체적 사례, 이미 쓰고 있는 우회 방법이 더 강한 증거다.
- 표본 편향: 쉽게 모이는 사람만 만난다. 열성 사용자, 사내 직원, 지인이 대표적이다. 이탈자, 비사용자, 경계 사용자(고령, 저사양 기기, 보조 기술 사용자)가 빠진다.
- 인사이트 없는 종합: 인용문만 모으거나 "사용자는 쉬운 걸 원한다" 같은 진부한 결론으로 끝난다. 관찰에서 패턴을 거쳐 함의까지 가는 단계를 건너뛴 것이다.
- 페르소나 장식화: 인구통계와 취미로 채운 페르소나는 결정에 쓰이지 않는다. 결정에 영향을 주는 것은 목표, 맥락, 제약, 행동 차이다.

**징후 → 진단 → 조치**
- 징후: 조사 계획서에 "확인한다", "검증한다"만 있고 "결과가 X면 Y를 한다"가 없다. → 진단: 결정과 연결되지 않은 조사다. → 조치: 결정 질문을 먼저 쓰고, 결과별 행동을 미리 합의한다.
- 징후: 문제 진술에 해결책이 들어 있다("사용자는 대시보드가 필요하다"). → 진단: 니즈와 수단을 혼동했다. → 조치: "누가, 어떤 상황에서, 무엇을 하려다, 무엇 때문에 막히는가"로 다시 쓴다.
- 징후: 성공 지표가 출시 여부나 클릭 수뿐이다. → 진단: 산출물과 성과를 혼동했다. → 조치: 행동 변화 지표 하나와 그 지표가 망가뜨릴 수 있는 지표(가드레일)를 함께 정한다.

**점검표**
- 이 조사로 바뀔 수 있는 결정이 명시되어 있는가
- 질문 유형(이유, 규모, 비교, 탐색)과 방법이 맞는가
- 모집 기준에 이탈자, 비사용자, 경계 사용자가 포함되는가
- 질문이 과거의 구체적 행동을 묻는가, 의향이나 선호를 묻는가
- 종합 결과가 관찰, 패턴, 함의, 기회 순서로 추적 가능한가
- 가설이 "~하면 ~가 ~만큼 변할 것이다"처럼 반증 가능한 형태인가
- 인터뷰 수가 적을 때 일반화 범위를 스스로 제한했는가

## 정보 구조와 내비게이션

**자주 보는 실패와 근본 원인**
- 조직도형 구조: 메뉴가 회사의 부서나 내부 시스템 구분을 그대로 따른다. 사용자의 과업 모델이 아니라 만드는 쪽의 모델을 반영한 결과다.
- 내부 용어 라벨: 팀 안에서만 쓰는 기능명이나 마케팅 명칭을 메뉴명으로 쓴다. 사용자는 라벨을 보고 그 아래에 무엇이 있을지 예측하는데, 낯선 이름은 그 예측을 막는다.
- 잡동사니 범주: "기타", "더보기", "도구"에 분류하기 어려운 것이 쌓인다. 분류 기준이 하나로 정해져 있지 않거나 섞여 있다는 신호다.
- 깊이와 폭의 극단: 단계를 줄이려고 한 화면에 모든 항목을 펼치거나, 깔끔해 보이려고 깊이 숨긴다. 어느 쪽이 맞는지는 라벨의 예측 가능성에 달려 있다. 경로가 명확하면 단계가 많아도 괜찮다.
- 검색으로 구조를 대신함: "검색이 있으니 괜찮다"고 본다. 하지만 사용자는 무엇을 검색해야 할지 모를 때가 많고, 검색 결과의 품질과 결과가 없을 때의 처리도 함께 설계해야 한다.
- 현재 위치 상실: 깊은 화면이나 외부 링크로 들어온 사용자가 지금 어디에 있는지, 어디로 갈 수 있는지 모른다.

**징후 → 진단 → 조치**
- 징후: 같은 기능이 여러 메뉴에 중복 배치된다. → 진단: 분류 축이 둘 이상 섞여 있다(대상별과 행동별 등). → 조치: 주 분류 축을 하나 정하고, 보조 축은 필터나 교차 링크로 처리한다.
- 징후: 지원 문의에 "어디 있나요"가 많다. → 진단: 라벨이나 위치가 기대와 다르다. → 조치: 카드 소팅으로 사용자의 분류를 확인하고, 트리 테스트로 텍스트 구조만 놓고 찾기 성공률을 잰다.
- 징후: 검색 로그에 메뉴에 있는 항목명이 상위로 나온다. → 진단: 내비게이션에서 그 항목을 찾지 못한다. → 조치: 검색어를 라벨 후보로 쓰고 동의어 사전을 만든다.

**점검표**
- 최상위 분류가 사용자의 과업이나 목표를 기준으로 하는가
- 라벨만 보고 그 아래 내용을 예측할 수 있는가(사용자 언어로 확인했는가)
- 범주들이 서로 겹치지 않고, 빠진 것 없이 전체를 포괄하는가
- 어떤 화면에서든 현재 위치, 상위 경로, 돌아갈 방법이 보이는가
- 검색에 오타, 동의어, 결과 없음, 결과 과다 상황이 설계되어 있는가
- 콘텐츠가 늘어날 때 구조가 버티는가(새 항목이 어디로 갈지 바로 정해지는가)
- 외부 링크나 알림으로 깊은 화면에 바로 들어온 경우를 고려했는가

## 인터랙션 디자인

**자주 보는 실패와 근본 원인**
- 행복 경로만 설계: 정상 흐름 화면만 있고 빈 상태, 로딩, 오류, 부분 실패, 권한 없음, 오프라인 상태가 빠진다. 원인은 화면 단위로 생각하고 상태 단위로 생각하지 않는 데 있다. 빠진 상태는 결국 개발자가 즉석에서 정한다.
- 시그니파이어 부족: 평면화된 UI에서 무엇이 눌리는지 구분되지 않는다. 숨은 제스처, 호버에만 드러나는 기능도 같은 문제다. 터치 환경에는 호버가 없다.
- 피드백 공백: 눌렀는데 아무 반응이 없어 사용자가 다시 누르고, 결과적으로 중복 제출이 생긴다. 입력을 받았다는 확인, 처리 중이라는 표시, 결과 알림이 각각 필요하다.
- 사후 확인에 기대는 오류 대응: 위험한 행동마다 "정말 삭제하시겠습니까?"를 띄운다. 사용자는 습관적으로 확인을 누르게 된다. 되돌리기(취소 가능 기간)나 애초에 잘못 입력할 수 없는 형식 제약이 더 효과적이다.
- 기계 중심 오류 메시지: 오류 코드나 "잘못된 입력" 같은 문구만 보여 준다. 무엇이 잘못됐는지, 어떻게 고치는지가 없다. 입력한 값을 지워 버리는 것도 흔한 실수다.
- 장식 모션: 전환 애니메이션이 공간 관계나 인과를 설명하지 않고 시간만 잡아먹는다. 전정기관 장애가 있는 사용자에게는 불편을 줄 수 있다.

**징후 → 진단 → 조치**
- 징후: 시안에 데이터가 늘 이상적인 길이와 개수로 들어 있다. → 진단: 극단값을 검토하지 않았다. → 조치: 0개, 1개, 아주 많은 경우와 긴 이름, 번역문, 누락 값을 넣어 다시 본다.
- 징후: 개발 중 "이럴 땐 어떻게 해요?"라는 질문이 반복된다. → 진단: 상태 정의가 없다. → 조치: 컴포넌트와 화면마다 상태 표를 만들고, 상태 사이의 전환 조건을 적는다.
- 징후: 플로우 중간 이탈률이 높다. → 진단: 단계마다 요구하는 것이 과하거나 진행 상황이 보이지 않는다. → 조치: 꼭 필요한 입력만 남기고, 나머지는 나중에 받거나 기본값을 쓴다. 진행 표시와 저장 후 재개를 넣는다.

**점검표**
- 모든 상호작용 요소가 눌릴 수 있다는 것이 시각적으로 드러나는가(호버 없이도)
- 행동마다 즉시 반응, 진행 상태, 결과를 알려 주는가. 긴 작업은 진행 정도를 보여 주는가
- 빈 상태, 로딩, 오류, 부분 성공, 권한 없음, 오프라인 상태가 정의되어 있는가
- 되돌릴 수 없는 행동에 대해 예방 장치나 되돌리기가 있는가
- 오류 메시지가 원인과 해결 방법을 사용자 언어로 알려 주고, 입력값을 유지하는가
- 모션이 기능적 이유(관계, 인과, 주목)를 갖고, 모션 줄이기 설정을 존중하는가
- 중복 제출, 뒤로 가기, 새로고침, 세션 만료 상황을 처리하는가

## 시각 디자인과 위계

**자주 보는 실패와 근본 원인**
- 모든 것이 강조됨: 굵게, 색, 크기를 여러 요소에 동시에 쓴다. 강조는 상대적인 것이라 모두를 강조하면 아무것도 강조되지 않는다. 원인은 화면의 우선순위를 먼저 정하지 않은 데 있다.
- 색으로만 의미 전달: 빨강과 초록만으로 상태를 구분한다. 색각 이상 사용자, 흑백 출력, 햇빛 아래 화면에서 정보가 사라진다.
- 임의의 값: 간격, 글자 크기, 색이 화면마다 조금씩 다르다. 정해진 척도가 없어서 생긴다. 사용자는 미세한 차이를 의도된 의미 차이로 읽을 수 있다.
- 근접성 위반: 라벨과 입력란 사이 간격이 그룹 사이 간격과 같거나 더 커서, 무엇이 무엇에 속하는지 헷갈린다.
- 시안과 실제 환경의 차이: 큰 고해상도 모니터와 짧은 더미 텍스트로만 검토한다. 실제 기기, 긴 문장, 다국어 환경에서 줄바꿈이 깨지고 위계가 무너진다. 한글은 영문보다 글자 밀도가 높아서 줄 간격과 자간을 따로 조정해야 할 때가 많다.
- 대비 부족 미학: 연한 회색 텍스트를 세련됨으로 여긴다. 저시력 사용자와 열악한 환경에서 읽기 어려워진다.

**징후 → 진단 → 조치**
- 징후: 화면을 흐리게 보거나 실눈으로 봤을 때 가장 먼저 보이는 것이 핵심 정보가 아니다. → 진단: 위계가 우선순위와 어긋난다. → 조치: 정보 우선순위 목록을 먼저 쓰고, 크기, 굵기, 색, 위치, 여백 중 적은 수의 수단으로만 위계를 만든다.
- 징후: 같은 역할의 요소가 화면마다 다르게 생겼다. → 진단: 타입 스케일과 간격 척도가 없다. → 조치: 단계가 제한된 척도를 정의하고 토큰으로 묶는다.
- 징후: 본문 한 줄이 너무 길거나 짧다. → 진단: 그리드가 화면 폭만 고려하고 읽기 폭을 고려하지 않았다. → 조치: 본문의 최대 폭을 제한하고, 반응형 구간마다 다시 확인한다.

**점검표**
- 화면의 1순위, 2순위 정보가 정해져 있고, 시각적으로 그 순서대로 보이는가
- 위계를 만드는 수단이 절제되어 있는가(한 요소에 여러 강조를 겹치지 않았는가)
- 글자 크기, 간격, 색이 정해진 척도와 토큰에서 나왔는가
- 그룹 안의 간격이 그룹 사이의 간격보다 작은가
- 색 외에 아이콘, 텍스트, 패턴 같은 보조 단서가 있는가
- 텍스트와 배경의 대비가 기준을 충족하는가(최소한 실측했는가)
- 실제 콘텐츠 길이, 다국어, 작은 화면, 확대 상태, 다크 모드에서 확인했는가

## 디자인 시스템

**자주 보는 실패와 근본 원인**
- 스티커 시트로 끝남: 컴포넌트 그림만 모아 두고 사용 기준, 상태, 접근성 규칙, 코드가 없다. 원인은 시스템을 산출물로 보고 제품으로 보지 않은 데 있다. 시스템은 사용자(제품팀)가 있는 제품이고, 지원과 로드맵이 필요하다.
- 변형 폭증: 요청이 들어올 때마다 새 변형이나 옵션을 추가해서 컴포넌트가 아무도 이해하지 못할 만큼 복잡해진다. "이 요구가 반복되는 패턴인가, 한 번뿐인 예외인가"를 판단하는 기준이 없어서다.
- 토큰 계층 부재: 원시값(특정 색 코드)을 컴포넌트에 직접 연결한다. 테마나 브랜드가 바뀌면 전체를 고쳐야 한다. 원시 토큰, 의미 토큰(예: 오류 배경), 컴포넌트 토큰으로 계층을 나누면 변경 범위를 통제할 수 있다.
- 디자인과 코드의 분기: 디자인 툴의 컴포넌트와 코드 컴포넌트가 따로 진화한다. 결국 실제 제품에 들어간 것이 정본이 되고 디자인 파일은 신뢰를 잃는다.
- 거버넌스 부재 또는 과잉: 아무나 수정해서 일관성이 무너지거나, 중앙 팀이 병목이 되어 제품팀이 시스템을 우회한다(로컬 복제본 증가).
- 버전 관리 없는 변경: 공지 없이 컴포넌트를 바꿔 여러 제품 화면이 한꺼번에 깨진다.

**징후 → 진단 → 조치**
- 징후: 제품 코드에 시스템 컴포넌트를 복제하거나 덮어쓴 흔적이 많다. → 진단: 시스템이 실제 요구를 감당하지 못하거나 기여 경로가 너무 느리다. → 조치: 우회 사례를 수집해서 공통 요구는 시스템으로 흡수하고, 기여 절차와 응답 기한을 명시한다.
- 징후: 컴포넌트 속성이 십여 개 이상이고 서로 조합하면 안 되는 것이 있다. → 진단: 하나의 컴포넌트가 여러 역할을 떠안고 있다. → 조치: 역할별로 나누거나, 작은 부품을 조합하는 구조로 바꾼다.
- 징후: 디자인 파일과 실제 제품의 값이 다르다. → 진단: 정본이 정해져 있지 않다. → 조치: 토큰을 단일 소스에서 관리하고 양쪽으로 배포하며, 차이를 정기적으로 점검한다.

**점검표**
- 컴포넌트마다 언제 쓰고 언제 쓰지 않는지, 상태, 접근성 규칙, 코드 대응이 문서화되어 있는가
- 토큰이 원시, 의미, 컴포넌트 계층으로 나뉘어 있는가
- 새 변형을 추가하는 판단 기준(반복성, 복수 제품 수요)이 있는가
- 변경이 의미 있는 버전 체계로 관리되고, 깨지는 변경에 이전 안내와 유예 기간이 있는가
- 기여 모델(누가 제안하고, 누가 검토하고, 얼마 안에 답하는지)이 정해져 있는가
- 채택률, 우회율, 문의 같은 시스템 자체의 건강 지표를 보는가

## 접근성과 포용적 디자인

**자주 보는 실패와 근본 원인**
- 마지막 단계 점검: 출시 직전에 감사를 해서 고치기 비싼 구조적 문제(시맨틱, 포커스 흐름, 커스텀 위젯)가 남는다. 원인은 접근성을 품질 검사 항목으로만 보고 설계 요구사항으로 보지 않은 데 있다.
- 자동 검사 맹신: 자동 도구가 통과했으니 접근 가능하다고 본다. 자동 검사로 잡을 수 있는 문제는 일부뿐이다. 포커스 순서의 논리, 대체 텍스트의 적절성, 스크린 리더로 들었을 때 흐름이 자연스러운지는 사람이 확인해야 한다.
- 시각 장애만 생각: 운동 장애(키보드나 스위치 사용, 떨림), 인지 장애(복잡한 문장, 시간 제한), 청각 장애(자막 없는 영상), 일시적이거나 상황적인 제약(한 손 사용, 강한 햇빛)이 빠진다.
- 커스텀 컴포넌트: 기본 요소 대신 div로 버튼이나 드롭다운을 만들어 키보드 조작과 역할 정보가 사라진다. 기본 HTML 요소가 할 수 있는 일이면 기본 요소를 쓰는 것이 가장 싸고 안전하다.
- 포커스 관리 누락: 모달을 열었는데 포커스가 배경에 남거나, 닫은 뒤 원래 위치로 돌아가지 않는다. 포커스 표시를 디자인상의 이유로 지운다.
- 형식적 대체 텍스트: "이미지", 파일명, 또는 장식 이미지에 긴 설명을 붙인다. 대체 텍스트는 그 이미지가 맥락 속에서 하는 역할을 전달해야 하고, 장식 이미지는 비워 둬야 한다.

**징후 → 진단 → 조치**
- 징후: 마우스 없이 키보드만으로는 핵심 과업을 끝낼 수 없다(포커스가 닿지 않는 요소, 키로 실행되지 않는 컨트롤, 들어가면 빠져나올 수 없는 영역 등). 키보드 조작은 Tab만 쓰는 것이 아니다. Tab과 Shift+Tab으로 요소 사이를 이동하고, Enter나 Space로 실행하며, 라디오 그룹, 메뉴, 탭, 리스트박스 같은 복합 위젯은 ARIA 작성 지침(APG)에 따라 화살표 키로 내부를 이동하는 것이 표준이다. 따라서 "Tab만으로는 안 된다"는 사실 자체는 결함이 아니다. → 진단: 키보드 조작이 설계되지 않았다. → 조치: 설계 문서에 포커스 순서, 키 동작(이동, 실행, 위젯 내부 이동, 닫기), 포커스 이동 규칙(모달, 화면 전환, 삭제 후)을 명시한다.
- 징후: 스크린 리더가 "버튼, 버튼, 링크"만 읽는다. → 진단: 접근 가능한 이름이 없다. → 조치: 아이콘 버튼마다 이름을 정의하고, 제목 구조와 랜드마크를 시안 단계에서 표시한다.
- 징후: 확대하면 레이아웃이 깨지거나 가로 스크롤이 생긴다. → 진단: 고정 크기에 의존한다. → 조치: 텍스트 확대와 좁은 화면 리플로우를 기준에 넣는다.

**점검표**
- WCAG의 네 원칙(인식 가능, 운용 가능, 이해 가능, 견고함) 관점에서 요구사항을 정의했는가. 목표 적합성 수준(대개 AA)을 정했는가
- 텍스트 대비와 비텍스트 대비(아이콘, 입력란 경계, 포커스 표시)를 확인했는가. 예: 일반 텍스트 4.5:1, 큰 텍스트와 UI 요소 3:1
- 모든 기능을 키보드로 쓸 수 있고, 포커스가 항상 보이며, 순서가 논리적인가
- 제목 계층, 랜드마크, 입력란 라벨, 오류 연결이 시안에 주석으로 들어 있는가
- 터치 대상 크기와 간격이 충분한가
- 시간 제한, 자동 재생, 깜빡임이 통제 가능한가
- 실제 보조 기술(스크린 리더, 확대, 음성 제어)로 핵심 과업을 시험했는가. 가능하면 장애 당사자와 함께 시험했는가

## 사용성 평가와 검증

**자주 보는 실패와 근본 원인**
- 유도형 과업: "설정 메뉴에서 알림을 끄세요"처럼 과업 문장에 화면 라벨을 넣는다. 그러면 찾기 능력이 아니라 단어 맞추기를 시험하게 된다. 과업은 사용자의 목표와 상황으로 쓴다.
- 선호를 사용성으로 착각: "어느 쪽이 좋으세요?"의 답을 사용성 근거로 쓴다. 사용성은 과업 성공, 오류, 시간, 혼란 지점 같은 관찰된 행동으로 판단한다.
- 소수 표본의 오용: 소수 참가자 테스트는 반복 개선 과정에서 주요 문제를 찾는 데 효율적이지만, 비율이나 차이를 통계적으로 주장하는 데는 맞지 않는다. 반대로 정량 테스트 결과로 "왜"를 설명하려는 것도 오용이다.
- A/B 테스트의 함정: 표본 크기를 정하지 않고 시작하거나, 중간에 결과를 보고 멈추거나, 여러 지표 중 유리한 것만 고르거나, 짧은 기간의 신기함 효과를 지속 효과로 읽는다. 단기 전환 지표가 오르면서 장기 신뢰나 재방문이 떨어지는 경우도 있다.
- 휴리스틱 평가의 단독 사용: 평가자 한 명이 원칙 목록을 대조하는 것으로 테스트를 대신한다. 평가자 한 명은 문제의 일부만 찾고, 실제 사용자가 막히는 지점을 놓치거나 사소한 것을 과장할 수 있다.
- 심각도 없는 문제 목록: 발견된 문제를 나열만 해서 팀이 무엇부터 고칠지 모른다.

**징후 → 진단 → 조치**
- 징후: 테스트 후 결론이 "대체로 괜찮았다"이다. → 진단: 사전에 정한 성공 기준이 없다. → 조치: 과업별 성공 정의와 관찰할 지표를 미리 정한다.
- 징후: 실험 결과가 유의하다는데 효과 크기가 작고, 다른 지표는 보지 않았다. → 진단: 통계적 유의성과 실질적 중요성을 혼동하고, 가드레일 지표가 없다. → 조치: 최소 의미 효과, 표본, 기간을 사전 등록하고, 가드레일 지표를 함께 본다.
- 징후: 행동 데이터에서 특정 단계 이탈이 높다. → 진단: 무엇이 일어났는지는 알지만 왜인지는 모른다. → 조치: 해당 구간을 세션 관찰이나 짧은 인터뷰로 보완한다. 상관을 인과로 단정하지 않는다.

**점검표**
- 평가 질문이 탐색(문제 발견)인지 측정(비교, 기준 충족)인지 정했고, 방법이 그에 맞는가
- 과업 문장이 화면 라벨을 노출하지 않고 현실적인 목표와 맥락을 담는가
- 참가자가 실제 대상 사용자인가(사내 인원 대체 여부를 기록했는가)
- 심각도를 빈도, 영향, 지속성(반복해서 겪는가, 우회할 수 있는가)으로 판정했는가
- 실험에 사전 가설, 표본 크기, 기간, 주 지표, 가드레일 지표가 정해져 있는가
- 결과 보고서에 표본, 환경, 방법 때문에 생긴 한계를 적었는가

## 디자인 의사결정과 협업

**자주 보는 실패와 근본 원인**
- 취향 논쟁: 리뷰가 "저는 이게 더 좋아요"로 흐른다. 평가 기준(목표, 사용자, 제약)을 먼저 합의하지 않아서 생긴다.
- 최고 직급자의 의견(HiPPO)이 근거를 이김: 근거가 정리되어 있지 않거나, 결정권자와 결정 방식이 미리 정해져 있지 않을 때 생긴다.
- 트레이드오프를 숨김: 한 안의 장점만 말하고 비용을 숨긴다. 나중에 비용이 드러나면 디자인 전체의 신뢰가 떨어진다. 개발 비용, 일정, 일관성, 접근성, 유지보수 부담을 함께 제시한다.
- 크리틱의 변질: 피드백이 즉석 해결책 제시나 개인 평가가 된다. 발표자는 방어하고, 정작 필요한 피드백 유형은 말하지 않는다.
- 던지기식 핸드오프: 완성 시안만 넘긴다. 상태, 극단값, 반응형 규칙, 의도가 빠져서 개발자가 추측으로 채운다. 원인은 개발을 설계 이후의 실행 단계로만 본 데 있다. 기술 제약을 일찍 알면 더 나은 안이 나온다.
- 이해관계자의 늦은 등장: 최종 단계에서 법무, 보안, 운영, 고객지원이 처음 보고 뒤집는다.

**징후 → 진단 → 조치**
- 징후: 같은 결정을 회의마다 다시 논의한다. → 진단: 결정 기록과 결정권자가 없다. → 조치: 결정, 근거, 검토한 대안, 재검토 조건을 짧은 결정 기록으로 남긴다.
- 징후: 개발 후 결과물이 시안과 다르고 서로 탓한다. → 진단: 명세가 불완전하고, 중간 확인 지점이 없다. → 조치: 설계 초기에 개발과 함께 실현 가능성을 검토하고, 구현 중 중간 검수와 출시 전 디자인 QA를 일정에 넣는다.
- 징후: 요청이 모두 긴급하다. → 진단: 우선순위 기준이 없다. → 조치: 사용자 영향, 사업 영향, 노력, 근거 확실성 같은 축으로 비교하고, 하지 않을 것을 명시한다.

**점검표**
- 결정이 어떤 문제와 지표에 연결되는지, 결정권자가 누구인지 명확한가
- 대안을 최소 두 개 이상 비교했고, 각 대안의 비용과 위험을 함께 제시했는가
- 크리틱 전에 목표, 단계, 원하는 피드백 유형을 밝혔는가. 피드백이 목표 기준으로 표현되는가
- 핸드오프에 상태, 극단값, 반응형 규칙, 인터랙션 세부, 접근성 주석, 토큰 참조, 의도가 포함되는가
- 법무, 보안, 지원, 운영 같은 이해관계자를 발견 단계에서 확인했는가
- 결정과 근거가 나중에 찾아볼 수 있는 곳에 기록되는가
- 출시 후 검증 계획(무엇을 언제 보고, 결과에 따라 무엇을 할지)이 있는가

## 더 짚을 것 (검토 보강)

- **UX 라이팅:** 버튼은 결과를 말하는 동사로 쓴다("확인" 대신 "주문하기"). 같은 것은 같은 말로 부른다(용어 일관성). 오류 문구는 무엇이 왜 잘못됐고 어떻게 고치는지를 사용자의 말로 쓴다. 빈 상태와 첫 사용 화면의 문구도 설계 대상이다.
- **반응형·여러 기기:** 터치와 포인터는 다르다(호버 없음, 터치 영역 크기). 소프트 키보드가 입력 칸이나 주요 버튼을 가리지 않는지, 노치·홈 표시줄 같은 안전 영역을 피하는지, 가로·세로 전환과 큰 글꼴에서 무너지지 않는지 본다.
- **기만적 패턴 피하기:** 해지를 가입보다 어렵게 만들기, 미리 체크된 동의, 숨은 비용, 죄책감을 주는 거절 문구 같은 다크 패턴은 단기 지표를 올려도 신뢰와 법적 위험(소비자 보호 규정)으로 돌아온다. 지시가 이런 쪽이면 전제·위험에 적는다.

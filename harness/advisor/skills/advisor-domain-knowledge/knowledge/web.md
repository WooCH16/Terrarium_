# 웹 사이트 어드바이저 지식

이 파일은 요청을 쪼개고 위험을 짚을 때 기준으로 삼는 원리 모음이다. 각 영역은 원리, 판단 규칙, 트레이드오프, 흔한 오해 순서로 정리했다. 제품명과 수치는 예시일 뿐이므로, 최신 사양과 기본값은 작업 시점의 공식 문서로 확인한다.

## 브라우저 렌더링 파이프라인과 런타임 성능

**원리**
- 브라우저는 다음 순서로 화면을 만든다.
  1. HTML을 파싱한다.
  2. 리소스를 발견하고 요청한다.
  3. DOM과 CSSOM을 만든다.
  4. 스타일을 계산한다.
  5. 레이아웃, 페인트, 합성을 거친다.
- 각 단계는 앞 단계의 산출물을 기다린다. 그래서 병목은 대개 "늦게 발견된 리소스"나 "메인 스레드를 오래 점유한 작업" 둘 중 하나다.
- CSS는 렌더를 막는다. 스타일 없이 그리면 다시 그려야 하기 때문이다.
- `defer`나 `async`가 없는 동기 스크립트는 파서를 막는다. 스크립트가 DOM을 바꾸거나 `document.write`를 쓸 수 있기 때문이다.
- 프리로드 스캐너는 HTML 문자열에 보이는 리소스만 미리 찾는다. 다음 리소스는 발견이 늦다.
  - JS가 주입한 이미지
  - CSS `background-image`
  - `@import` 체인
- 로딩 지표(예: LCP)는 세 구간의 합이다. 개선하려면 어느 구간이 긴지부터 분해해야 한다.
  - 서버 응답
  - 리소스 발견과 다운로드 지연
  - 렌더 지연
- 반응성 지표(예: INP)는 세 구간의 합이다.
  - 입력 지연: 메인 스레드가 바빠서 이벤트를 늦게 받는 시간
  - 핸들러 실행 시간
  - 다음 프레임 표시까지의 시간
- 레이아웃 이동(CLS)은 크기를 예약하지 않은 콘텐츠나 늦게 끼어드는 콘텐츠 때문에 생긴다.

**판단 규칙**
- 측정을 먼저 하고 최적화는 그다음이다. 실사용자 데이터(필드)로 문제를 확인하고, 랩 도구로 원인을 재현한다. 랩 점수만으로 우선순위를 정하지 않는다.
- LCP 요소가 이미지라면 다음을 확인한다.
  - HTML에서 바로 발견되는가
  - 지연 로딩이 잘못 걸려 있지 않은가
  - 우선순위 힌트가 있는가
  - 크기에 맞는 포맷으로 제공되는가
- 50ms를 넘는 긴 작업은 쪼개거나 다른 곳으로 옮긴다.
  - 쪼개는 방법: 작업 사이에 메인 스레드를 양보한다. 무거운 계산은 Worker로 보낸다.
  - 시각적 피드백을 먼저 그리고, 무거운 일은 그 뒤로 미룬다.
- 레이아웃 스래싱을 피한다. 스래싱은 읽기와 쓰기를 번갈아 하면서 강제 동기 레이아웃이 반복되는 현상이다. 읽기를 모은 뒤 쓰기를 모은다.
- 애니메이션은 합성 단계에서 처리되는 속성(transform, opacity)으로 만든다.
- 서드파티 스크립트는 성능 예산 항목으로 관리한다. 지연 로드, 대체 수단, 제거 중 하나를 결정한다.

**트레이드오프**
- 프리로드를 남발하면 정말 중요한 리소스와 대역폭을 다툰다. 우선순위는 상대적이다.
- 인라인 크리티컬 CSS는 첫 렌더를 앞당긴다. 대신 캐시 재사용을 잃고 HTML이 커진다.
- 번들을 잘게 나누면 초기 비용이 준다. 대신 요청 수와 워터폴 위험이 늘어난다.

**흔한 오해**
- "파일 크기만 줄이면 빨라진다"는 틀렸다. 발견 시점과 실행 시간이 더 자주 지배한다.
- "`will-change`를 많이 걸면 부드러워진다"는 틀렸다. 레이어가 늘면 메모리와 합성 비용이 커진다.
- "랩 점수 100점이면 사용자도 빠르다"는 틀렸다. 실제 기기, 네트워크, 상호작용 분포가 다르다.

## 프런트엔드 렌더링 전략과 상태 관리

**원리**
- 렌더링 방식별 특성은 다음과 같다.

| 방식 | 장점 | 비용 |
|---|---|---|
| SSR | 첫 HTML에 콘텐츠가 있다 | 상호작용하려면 JS로 하이드레이션해야 한다 |
| CSR | 서버가 단순하다 | 빈 셸 → JS 다운로드·실행 → 데이터 요청의 직렬 지연이 생긴다 |
| SSG/ISR | 결과를 빌드 시점이나 주기적으로 미리 만들어 캐시처럼 쓴다 | 데이터 신선도를 갱신 정책에 맡겨야 한다 |

- 하이드레이션은 "서버가 만든 DOM과 클라이언트의 첫 렌더 결과가 같다"는 가정에 의존한다. 다음 값이 첫 렌더에 섞이면 이 가정이 깨진다.
  - 현재 시각, 난수, 로케일, 타임존
  - `window` 크기, 로그인 여부, 로컬스토리지
- 가정이 깨지면 경고가 나거나, 서브트리를 다시 렌더하거나, 미묘하게 잘못된 UI가 나온다.
- 상태는 성격이 다른 두 종류다. 둘을 같은 저장소에 섞으면 동기화 버그가 난다.
  - 서버 상태: 원격 데이터의 사본이다. 소유자가 서버이고 언제든 낡을 수 있으며, 캐시·무효화·재요청·중복 제거·낙관적 갱신이 필요하다.
  - 클라이언트 상태: 모달 열림, 입력 중 값, 선택 항목처럼 브라우저가 소유한다.

**판단 규칙**
- 페이지 유형에 따라 전략을 고른다.
  - 색인되어야 하고 첫 화면이 중요한 콘텐츠 페이지: SSR이나 SSG가 우선이다.
  - 로그인 후 대시보드처럼 상호작용이 많고 색인이 필요 없는 화면: CSR도 타당하다.
- 비결정적 값은 서버와 클라이언트가 같은 입력을 받게 한다. 예: 서버 시각을 직렬화해 넘긴다. 그럴 수 없으면 마운트 뒤에 렌더한다.
- 서버 상태는 전용 캐시 계층에 둔다. 키 설계, stale 기준, 변경 후 무효화를 명시한다. 원격 데이터를 전역 클라이언트 스토어에 복사하는 습관은 피한다.
- URL에 담을 수 있는 상태(필터, 페이지, 탭)는 URL에 둔다. 공유, 뒤로 가기, SEO가 함께 해결된다.
- 파생 값은 저장하지 않고 계산한다. 원본이 둘이면 언젠가 어긋난다.

**트레이드오프**
- 하이드레이션 비용을 줄이는 방법이 있다. 부분·지연 하이드레이션, 아일랜드, 서버 컴포넌트 같은 방식이다. 대신 경계 설계와 직렬화 제약이 생긴다.
- 낙관적 갱신은 체감 속도를 올린다. 대신 실패 시 롤백과 충돌 표현을 설계해야 한다.

**흔한 오해**
- "SSR이면 빠르다"는 틀렸다. 화면은 일찍 보이지만 상호작용은 늦을 수 있다(보이는데 안 눌리는 구간).
- "전역 상태 라이브러리가 데이터 캐시를 대신한다"는 틀렸다. 신선도와 무효화 의미론이 빠져 있다.

## HTTP 캐시와 CDN

**원리**
- 캐시의 동작은 두 가지 질문으로 정해진다. 언제까지 묻지 않고 재사용하는가(신선도), 그리고 낡은 뒤 어떻게 확인하는가(검증)이다.
- 주요 Cache-Control 지시어는 다음과 같다.

| 지시어 | 의미 |
|---|---|
| `max-age` | 신선한 기간 |
| `s-maxage` | 공유 캐시 전용 신선 기간 |
| `no-cache` | 저장은 하되 매번 검증한다 ("캐시 금지"가 아니다) |
| `no-store` | 저장 자체를 금지한다 |
| `private` | 브라우저 캐시에만 저장한다 |
| `public` | 공유 캐시에 저장해도 된다 |
| `must-revalidate` | 낡으면 반드시 검증한다 |
| `stale-while-revalidate` | 낡은 응답을 주면서 뒤에서 갱신한다 |
| `stale-if-error` | 오류 시 낡은 응답을 허용한다 |
| `immutable` | 신선 기간 중 재검증하지 않는다 |

- 검증은 두 방식이 있다. 둘 다 성공하면 본문 없이 304를 받는다.
  - `ETag`와 `If-None-Match`
  - `Last-Modified`와 `If-Modified-Since`
- 캐시 키는 기본적으로 메서드와 URL이다. `Vary`에 적힌 요청 헤더가 키에 더해진다.
- 공유 캐시(CDN, 프록시)는 여러 사용자가 같은 사본을 받는다. 그래서 개인화 응답이 공유 캐시에 들어가는 것이 가장 위험한 사고다.

**판단 규칙**
- 정적 자산은 파일명에 콘텐츠 해시를 넣고 길게 캐시하며 `immutable`을 쓴다.
- HTML은 짧게 캐시하거나 `no-cache`로 둔다. HTML이 새 자산 URL을 가리키게 하는 것이 무효화 전략이다.
- 인증이 필요하거나 사용자별인 응답은 `private`이나 `no-store`로 둔다. CDN 설정과 오리진 헤더가 어떻게 상호작용하는지(어느 쪽이 우선인지) 반드시 확인한다.
- `Vary`는 최소한으로 둔다.
  - `Vary: Cookie`나 User-Agent 전체를 넣으면 적중률이 무너진다.
  - 디바이스 분기는 정규화한 헤더나 별도 URL로 한다.
- 압축을 쓰면 `Vary: Accept-Encoding`이 필요하다.
- CORS 응답이 Origin별로 다르면 `Vary: Origin`이 필요하다.
- 배포 순서는 새 자산을 먼저 올리고 HTML은 그 뒤에 바꾼다. 구 자산은 한동안 남긴다. 캐시된 구 HTML이 구 자산을 요청하기 때문이다.
- 퍼지는 비상 수단이다. 정상 경로는 URL 버전 관리다. 태그나 서로게이트 키 기반 퍼지는 키 설계를 미리 해야 쓸 수 있다.

**트레이드오프**
- TTL이 길면 적중률과 비용 면에서 유리하지만 신선도가 떨어진다.
- `stale-while-revalidate`는 지연을 숨긴다. 대신 한 번은 낡은 값을 보여준다.

**흔한 오해**
- "`no-cache`는 캐시 안 함"이라는 이해는 틀렸다. 저장한 뒤 매번 검증하는 것이다.
- "CDN 퍼지면 즉시 전 세계 반영"이라는 기대는 틀렸다. 반영에는 전파 지연이 있다. 브라우저 캐시와 중간 캐시는 퍼지가 닿지 않는다.
- "쿼리스트링 버전이면 충분"하다는 생각은 틀렸다. 일부 캐시는 쿼리를 무시하거나 정규화한다.

## 백엔드 API 설계와 데이터 일관성

**원리**
- 네트워크에서는 "실패"와 "응답 유실"을 구분할 수 없다. 그래서 재시도는 필연이고, 재시도는 중복 실행을 낳는다.
- 멱등성이란 같은 요청을 여러 번 보내도 결과가 같다는 뜻이다.
  - GET, PUT, DELETE는 의미상 멱등이다.
  - POST는 멱등 키가 있어야 멱등해진다.
  - 멱등 키 방식: 클라이언트가 키를 생성하고, 서버는 키와 첫 결과를 함께 저장해 재생한다.
- 경쟁 조건의 전형은 다음 셋이다.
  - 읽고-수정하고-쓰기 사이의 갱신 유실
  - 중복 생성
  - 재고·잔액 초과 차감
- 트랜잭션 경계 바깥에서 외부 호출(결제, 메일, 큐)을 하면 원자성이 깨진다. 일반적인 구성에서는 DB 커밋과 메시지 발행의 원자성을 보장할 수 없다(이중 쓰기 문제). XA·2PC 같은 분산 트랜잭션으로 DB와 일부 메시지 브로커를 한 트랜잭션에 묶을 수는 있지만, 지원 범위가 제한적이고 비용과 가용성 부담이 크다.

**판단 규칙**
- 돈, 재고, 생성 요청에는 멱등 키를 둔다. 키의 저장 범위, 만료, 같은 키에 다른 본문이 오면 거부하는 규칙을 정한다.
- 동시성 제어는 조건별로 고른다.
  - 충돌이 드물면 낙관적 잠금: 버전 컬럼이나 `If-Match`/ETag를 쓰고 412를 반환한다.
  - 충돌이 잦고 구간이 짧으면 비관적 잠금이나 조건부 원자 갱신. 예: `UPDATE … WHERE stock >= n`
  - 존재하면 안 되는 중복은 애플리케이션 검사가 아니라 유니크 제약으로 막는다.
- DB 변경과 이벤트 발행이 함께 맞아야 하는 곳이라면 아웃박스 패턴을 쓴다. 같은 트랜잭션에서 이벤트를 테이블에 기록하고 별도 프로세스가 발행한다. 소비자는 중복 수신을 전제로 멱등하게 처리한다.
- 페이지네이션은 데이터 성격에 따라 고른다.
  - 변하는 큰 목록은 커서(키셋) 방식이다. 정렬 키에 유일한 타이브레이커를 붙인다.
  - 오프셋 방식은 깊은 페이지에서 느리고, 삽입·삭제가 있으면 항목이 누락되거나 중복된다.
- 재시도는 지수 백오프와 지터를 쓰고 상한을 둔다. 타임아웃은 호출 체인 전체 예산 안에서 정한다. 400, 401, 403, 404, 422 같은 비일시 오류는 재시도하지 않는다. 4xx라도 429 Too Many Requests는 `Retry-After`에 맞춰 재시도하고, 408 Request Timeout도 재시도 대상이다.
- N+1 쿼리, 무제한 결과, 인덱스 없는 정렬은 설계 리뷰 단계에서 잡는다.

**트레이드오프**
- 강한 일관성을 얻으면 지연과 가용성을 잃는다. 결과적 일관성을 쓰면 UI와 사용자에게 지연을 설명해야 한다.
- 분산 트랜잭션은 회피하고 사가 패턴(보상 작업)으로 대체하는 경우가 많다. 대신 보상 로직이 복잡해진다.

**흔한 오해**
- "트랜잭션이면 동시성 안전"하다는 생각은 틀렸다. 격리 수준에 따라 갱신 유실이나 쓰기 왜곡이 남는다.
- "정확히 한 번 전달"을 인프라가 보장해 준다는 기대는 틀렸다. 실무에서는 최소 한 번 전달과 멱등 처리를 조합한다.

## 브라우저 보안 모델과 인증

**원리**
- 출처(origin)는 스킴, 호스트, 포트의 조합이다. SOP는 다른 출처의 응답을 읽는 것을 막지만, 요청 보내기 자체는 대부분 허용한다.
  - CSRF는 "요청은 보내진다"는 사실을 악용한다.
  - CORS는 서버가 읽기를 선택적으로 허용하는 장치이지, 보호 장치가 아니다.
- 단순하지 않은 요청은 프리플라이트(OPTIONS)를 거친다. 자격 증명을 포함하면 와일드카드 Origin을 쓸 수 없다.
- 사이트(site)는 등록 가능 도메인 단위다. SameSite 쿠키는 출처가 아니라 사이트 기준으로 동작한다. 서브도메인 하나가 탈취되면 같은 사이트 전체가 위험해진다.
- 쿠키 속성의 의미는 다음과 같다.

| 속성 | 의미 |
|---|---|
| `HttpOnly` | JS가 읽지 못하게 한다. XSS로 인한 탈취를 줄인다 |
| `Secure` | HTTPS에서만 전송한다 |
| `SameSite=Lax` | 교차 사이트 하위 요청에는 보내지 않는다. 최상위 GET 이동에는 보낸다 |
| `SameSite=Strict` | 교차 사이트 요청 전반에서 보내지 않는다 |
| `SameSite=None` | 교차 사이트 전송을 허용한다. `Secure`가 필요하다 |
| `__Host-` 접두사 | `Secure` 필수, `Path=/` 필수, `Domain` 속성 금지를 브라우저가 강제한다. 셋 중 하나라도 어기면 쿠키를 버린다(하위 경로 전용 쿠키에는 못 쓴다) |

- XSS는 출처 안에서 코드를 실행한다. 그래서 그 출처의 모든 방어를 무력화한다. HttpOnly 쿠키를 써도 공격자는 피해자 브라우저로 요청을 대신 보낼 수 있다.

**판단 규칙**
- 토큰 저장 위치에 따라 주된 위협이 달라진다.
  - 브라우저 앱의 세션: HttpOnly·Secure·SameSite 쿠키가 기본이다. 상태 변경 요청에는 CSRF 토큰이나 Origin 검증을 추가한다.
  - localStorage의 토큰: CSRF에는 강하지만 XSS로 즉시 유출된다.
- XSS 방어는 여러 층으로 쌓는다.
  1. 출력 컨텍스트별로 인코딩한다(HTML, 속성, URL, JS).
  2. 프레임워크의 자동 이스케이프를 우회하지 않는다.
  3. CSP는 nonce나 hash 기반으로 적용한다.
  4. 서드파티 스크립트를 최소화한다.
- 상태 변경은 GET으로 하지 않는다. Lax 쿠키는 최상위 GET 이동에 실려 가기 때문이다.
- CORS 허용 목록은 정확한 Origin 비교로 만든다. 요청 Origin을 그대로 반사하거나 접미사로 매칭하는 것은 금지한다.
- 세션은 로그인 시 재발급하고(세션 고정 방지), 서버 측에서 폐기할 수 있게 한다. 수명이 짧은 액세스 토큰과 회전하는 리프레시 토큰을 조합할 때는 탈취 감지 규칙을 둔다.

**트레이드오프**
- 상태 없는 JWT는 확장이 쉽다. 대신 즉시 폐기가 어렵다.
- Strict 쿠키는 안전하다. 대신 외부 링크로 들어온 사용자가 로그아웃된 것처럼 보인다.

**흔한 오해**
- "CORS를 열면 보안 문제, 막으면 안전"이라는 이해는 틀렸다. CORS는 서버 간 요청이나 CSRF를 막지 않는다.
- "HTTPS면 XSS 무관"하다는 생각은 틀렸다. HTTPS는 전송 구간만 보호한다.

## 웹 접근성

**원리**
- 보조기기는 접근성 트리를 읽는다. 접근성 트리는 DOM의 역할(role), 이름, 상태, 값에서 만들어진다.
- 네이티브 요소(`button`, `a[href]`, `input`, `label`, `select`, `dialog`)는 다음을 공짜로 준다.
  - 역할
  - 키보드 동작
  - 포커스 가능성
  - 상태 전달
- ARIA는 의미만 바꾸고 동작은 바꾸지 않는다. `role="button"`을 붙여도 Enter·Space 처리와 포커스는 직접 구현해야 한다.
- ARIA를 틀리게 쓰면 없을 때보다 나쁘다. 거짓 정보를 전달하기 때문이다.
- 동적 변화(토스트, 오류, 검색 결과 수)는 포커스 밖에서 일어난다. 라이브 영역이나 포커스 이동이 없으면 보조기기 사용자는 변화를 모른다.

**판단 규칙**
- 우선순위는 네이티브 요소 → 네이티브 요소 조합 → 마지막에 ARIA 패턴이다. 커스텀 위젯은 확립된 패턴의 키보드 모델을 따른다(탭 목록, 콤보박스, 메뉴 등).
- 모든 상호작용은 키보드로 할 수 있어야 한다.
  - 포커스 표시를 지우지 않는다.
  - DOM 순서가 시각 순서와 맞아야 한다.
  - 양수 `tabindex`는 쓰지 않는다.
- 모달과 SPA 라우팅의 포커스는 다음처럼 관리한다.
  - 모달은 열 때 안으로 포커스를 옮기고, 열려 있는 동안 배경을 비활성화하며, 닫을 때 트리거로 포커스를 돌려준다.
  - SPA 라우팅 후에는 새 페이지 제목이나 주 영역으로 포커스를 옮기거나 변화를 알린다.
- 폼 접근성의 기본은 다음과 같다.
  - 모든 입력에 프로그램적으로 연결된 레이블을 둔다.
  - 오류는 텍스트로 알리고 필드에 연결한다.
  - 색만으로 의미를 전달하지 않는다.
- 라이브 영역 사용 규칙은 다음과 같다.
  - 영역은 미리 DOM에 두고 내용만 바꾼다.
  - 기본은 polite로 둔다. assertive는 긴급한 경우에만 쓴다.
- 검증은 자동 도구와 수동 키보드·스크린리더 점검을 함께 한다. 자동 도구는 일부 문제만 잡는다.

**트레이드오프**
- 완전 커스텀 디자인은 네이티브 요소의 이점을 포기한다. 스타일링 한계와 구현 부담을 비교해서 정한다.

**흔한 오해**
- "`aria-label`을 붙이면 해결"된다는 생각은 틀렸다. 보이는 텍스트와 이름이 다르면 음성 조작 사용자가 혼란을 겪는다.
- "`div`에 `onClick`이면 버튼"이라는 생각은 틀렸다. 그 요소는 키보드로 포커스할 수도, 실행할 수도 없다.
- 접근성은 마무리 단계의 점검 항목이 아니다. 컴포넌트를 설계할 때 정하는 사항이다.

## 검색 엔진 최적화(기술 SEO)

**원리**
- 검색 노출은 세 단계를 거치며, 각 단계에서 따로 실패할 수 있다.
  - 크롤링: URL을 발견하고 가져온다.
  - 렌더링: JS를 실행해 최종 DOM을 얻는다.
  - 색인: 내용을 평가하고 대표 URL을 골라 저장한다.
- 단계별 신호는 다음과 같이 작동한다.
  - robots.txt는 크롤링을 막는 장치다. 색인을 막지는 못한다. 외부 링크만으로 URL이 색인될 수 있다. 차단된 페이지의 `noindex`는 아예 읽히지 않는다.
  - `noindex`는 색인 단계의 지시다. 페이지를 가져올 수 있어야 효과가 있다.
  - canonical은 중복 URL 중 대표를 고르는 힌트다. 검색엔진이 다른 신호와 함께 판단해서 무시할 수 있다.
- JS 렌더링은 지연되거나 실패할 수 있다. 다음 경우 발견이 늦거나 누락된다.
  - 초기 HTML에 없는 콘텐츠와 링크
  - 클릭이나 스크롤 후에야 나오는 콘텐츠
  - `<a href>`가 아닌 이벤트 기반 네비게이션
- 상태 코드는 의미 그대로 해석된다.

| 상태 코드 | 해석 |
|---|---|
| 301, 308 | 영구 이동. 신호가 이전된다 |
| 302, 307 | 일시 이동 |
| 404, 410 | 없음 |
| 5xx | 일시 장애. 지속되면 크롤링 감속과 제외로 이어진다 |

- 200 상태로 "없음" 화면을 보여주면 소프트 404가 된다.

**판단 규칙**
- 검색 유입이 중요한 공개 페이지라면 색인 대상 콘텐츠와 내부 링크를 서버 응답 HTML에 둔다(SSR·SSG). 로그인 뒤 화면처럼 색인이 필요 없는 곳에는 해당하지 않는다. 다음 메타 요소도 서버에서 렌더한다.
  - title
  - meta description
  - canonical
  - hreflang
  - 구조화 데이터
- 색인에서 빼려면 `noindex`를 쓰고 크롤링은 허용한다. robots.txt는 크롤링 예산과 서버 부하를 관리하는 용도다.
- URL은 하나의 콘텐츠에 하나의 대표 URL이 있어야 한다. 다음 변형은 리다이렉트나 canonical로 하나로 모은다.
  - 정렬·추적 파라미터
  - 대소문자
  - 끝 슬래시
  - 프로토콜·호스트 변형
- 사이트를 이전할 때는 URL을 일대일로 매핑해 301로 보낸다. 다음은 피한다.
  - 리다이렉트 체인
  - 모든 URL을 홈으로 보내는 일괄 리다이렉트
- 클라이언트 라우팅 SPA는 다음을 지켜야 한다.
  - 실제 URL을 쓴다(History API).
  - 링크는 `<a href>`로 만든다.
  - 존재하지 않는 경로에는 서버가 진짜 404를 반환한다.
- 렌더링 결과는 검색엔진 도구의 URL 검사나 렌더된 HTML 확인으로 검증한다.

**트레이드오프**
- 무한 스크롤이나 패싯 필터는 사용성은 좋지만 크롤링 공간을 폭발시킨다. 페이지 URL을 제공하고 색인 대상 조합을 제한한다.

**흔한 오해**
- "canonical이면 중복 해결 보장"된다는 생각은 틀렸다. canonical은 힌트일 뿐이고, 내부 링크와 사이트맵이 서로 일관되어야 한다.
- "robots.txt 차단 = 검색 결과에서 사라짐"이라는 생각은 틀렸다. 차단은 크롤링만 막는다.
- "크롤러가 JS를 실행하니 CSR도 동일"하다는 생각은 틀렸다. 렌더링 지연, 리소스 차단, 실패 위험이 남는다.

## 배포·운영과 관측성

**원리**
- 배포 중에는 항상 신·구 버전이 공존한다. 공존하는 쌍은 다음과 같다.
  - 롤링 배포의 서버 인스턴스들
  - 캐시된 구 프런트엔드와 새 API
  - 큐에 남은 구 메시지
  - 구 스키마를 기대하는 코드
- 그래서 모든 변경은 한 단계 앞뒤 버전과 호환되어야 한다.
- 스키마 변경은 확장-이전-수축(expand-migrate-contract) 순서로 쪼갠다.
  1. 새 컬럼을 nullable로 추가한다.
  2. 이중 쓰기를 시작한다.
  3. 백필한다.
  4. 읽기를 전환한다.
  5. 구 경로를 제거한다.
- 컬럼 이름 변경이나 삭제를 한 번에 하면 공존 구간에서 장애가 난다.
- 평균은 꼬리를 숨긴다. 사용자 경험은 백분위(p75, p95, p99)와 분포로 봐야 한다.
- 집계 계층이 다르면 백분위를 평균할 수 없다. 원시 분포나 히스토그램을 보존해야 한다.

**판단 규칙**
- 배포 전략은 다음 원칙으로 정한다.
  - 카나리, 블루그린, 기능 플래그로 배포와 출시를 분리한다.
  - 롤백할 수 있는지 확인한다. 데이터 마이그레이션은 되돌릴 수 없는 경우가 많다.
  - 헬스체크는 준비 상태(readiness)와 생존(liveness)을 구분한다.
  - 종료 시에는 진행 중 요청을 마저 처리한다(graceful drain).
- 프런트엔드는 청크 로드 실패에 대비한다. 대비 방법은 다음과 같다.
  - 구 자산을 보존한다.
  - 실패를 감지해 재로드한다.
  - API를 버전 관리하거나 하위 호환으로 바꾼다.
- 관측 데이터는 역할별로 쓴다.
  - 지표: 무슨 일이 얼마나 일어났나
  - 로그: 개별 사건의 맥락. 구조화하고 상관 ID를 단다.
  - 트레이스: 요청이 어디서 시간을 썼나. 컨텍스트를 서비스 경계 너머로 전파한다.
  - RUM: 실제 브라우저에서의 지표와 오류
- 서비스 지표는 RED(요청률, 오류율, 지연)로, 자원은 USE(사용률, 포화도, 오류)로 본다.
- 높은 카디널리티(사용자 ID 등)는 지표 라벨이 아니라 트레이스나 로그에 둔다.
- 알림은 증상 기반으로 건다. SLO 위반과 오류 예산 소진 속도를 기준으로 하고, 원인 지표는 대시보드에서 진단용으로 쓴다.
  - 사람이 행동할 수 없는 알림은 없앤다.
  - 다중 윈도 소진율 알림으로 오탐과 늦은 탐지를 함께 줄인다.

**트레이드오프**
- 트레이스는 전부 수집하면 비용이 크고, 샘플링하면 드문 오류를 놓친다. 오류·지연 기준의 테일 샘플링을 검토한다.
- 기능 플래그는 위험을 줄인다. 대신 조합 폭발과 기술 부채를 낳는다. 플래그마다 제거 일정을 둔다.

**흔한 오해**
- "롤백하면 원상복구"된다는 생각은 틀렸다. 롤백해도 데이터, 캐시, 발행된 이벤트는 남는다.
- "서버 지연이 정상이면 사용자도 정상"이라는 생각은 틀렸다. 다음은 RUM에서만 보인다.
  - CDN 구간과 클라이언트 렌더링
  - 서드파티 지연
  - 특정 지역·기기의 문제

## 요청을 쪼갤 때의 공통 점검

- **사용자 결정 확인**: 요청에서 사용자가 실제로 결정하려는 것이 무엇인지 먼저 이름 붙인다. 성능, 정확성, 노출, 보안 중 무엇이 목표인지 정하면, 필요한 측정과 성공 기준이 정해진다.
- **경계 지점 위험**: 변경이 다음 경계를 건드리는지 확인한다. 위험의 대부분이 경계에 있다.
  - 캐시(누가 낡은 사본을 들고 있나)
  - 공존 버전(구 클라이언트와 데이터는 어떻게 되나)
  - 재시도(두 번 실행되면 어떻게 되나)
  - 신뢰 경계(입력이 어디서 오나)
- **함께 확인할 항목**: 되돌릴 수 없는 작업이 있는지, 그리고 실사용자 데이터로 효과를 확인할 수단이 있는지 함께 점검한다. 대상 작업은 다음과 같다.
  - 데이터 마이그레이션
  - 퍼지
  - 리다이렉트
  - 공개 API 변경

## 더 짚을 것 (검토 보강)

- **기본 보안 헤더:** 클릭재킹은 CSP `frame-ancestors`(옛 브라우저까지는 `X-Frame-Options`)로 막는다. `X-Content-Type-Options: nosniff`로 형식 추측을 끈다. HTTPS 강제는 HSTS로 하되 처음에는 짧은 `max-age`로 시작하고, `includeSubDomains`와 preload는 모든 하위 도메인이 HTTPS일 때만 켠다(되돌리기 어렵다).
- **파일 업로드:** 크기 제한을 두고, 형식은 확장자나 `Content-Type`이 아니라 내용으로 확인한다. 저장 이름은 서버가 정한다. 사용자 파일은 별도 도메인이나 `Content-Disposition: attachment`로 내보내 SVG·HTML이 내 출처에서 실행되지 않게 한다. 큰 파일은 사전 서명 URL로 저장소에 직접 올리고, 서버는 완료 뒤 검증한다.
- **실시간 통신:** 서버에서 클라이언트로만 흐르면 SSE(HTTP 위, 자동 재연결)로 충분하고, 양방향이 필요할 때 WebSocket을 쓴다. 재연결 때 놓친 이벤트를 마지막 ID부터 다시 보내는 방법, 느린 소비자에 대한 백프레셔, 연결 수만큼 드는 서버 자원, 프록시·로드밸런서의 유휴 타임아웃을 함께 정한다.
- 위 원칙은 대상 프로젝트의 규모와 기존 스택에 맞을 때 쓴다. 지시에 없는 구조 변경을 새로 만들지 말고, 필요하면 전제·위험으로 적는다.

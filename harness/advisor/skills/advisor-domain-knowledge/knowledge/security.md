# 보안 어드바이저 지식

이 파일은 사용자의 지시를 읽고 숨은 전제, 빠진 고려, 위험한 순서를 짚을 때 판단 근거로 쓴다. 영역마다 시니어가 자주 보는 실패와 근본 원인, 징후→진단→조치, 점검표를 담았다. 제품명과 수치는 예시일 뿐이므로, 현행 권고는 매번 1차 출처로 확인하라고 안내한다.

## 공통 판단 원칙

- **지시는 "무엇을 만들까"로 오지만, 실제 결정은 "무엇을 누구로부터 지킬까"다.** 기능 요청에 위협 가정이 없으면 합리적인 가정을 제안문의 전제·위험에 명시하고 진행한다. 가정에 따라 설계가 크게 갈려 정할 수 없으면 자료 요청으로 돌린다.
- **"내부망이라 괜찮다", "우리 사용자는 신뢰할 수 있다", "나중에 보안을 붙이자"는 대표적인 잘못된 전제다.** 나중에 붙이는 보안은 대개 구조 변경 비용으로 돌아온다.
- **도구를 도입했다고 통제가 생기지는 않는다.** "스캐너를 붙였다"와 "결과를 누가 언제까지 처리한다"는 다른 문제다.
- **우선순위는 영향도×악용 가능성×노출도로 정한다.** CVSS 점수만으로 정하지 않는다.
- **확실하지 않으면 단정하지 않는다.** 가정, 확인 방법, 확인 전까지의 안전한 기본값을 함께 제시한다.

## 위협 모델링과 보안 아키텍처 원칙

**자주 보는 실패**
- 위협 모델링을 문서 작성 행사로 끝낸다. 설계가 바뀌어도 모델은 갱신되지 않는다.
  - 근본 원인: 모델이 개발 산출물(티켓, 테스트)과 연결되어 있지 않다.
- 신뢰 경계를 네트워크 경계로만 본다. 실제 경계는 프로세스, 테넌트, 권한 수준, 데이터 분류가 바뀌는 지점이다. 서드파티 웹훅, 관리자 콘솔, 배치 작업, 메시지 큐 소비자가 흔히 누락된다.
- 자산을 "데이터베이스"처럼 뭉뚱그린다. 실제로는 서명 키, 세션 토큰, 감사 로그, 결제 권한처럼 기밀성·무결성·가용성 요구가 제각각이다.
- STRIDE를 체크박스로 쓴다. 요소(프로세스·데이터 저장소·흐름·외부 개체)별로 적용하지 않아 "부인(Repudiation)", "권한 상승"이 비어 있다.
- 심층 방어를 "같은 통제를 두 번"으로 오해한다. WAF와 입력 검증은 서로 다른 실패 모드를 막아야 의미가 있다.

**징후→진단→조치**
- 징후: 데이터 흐름도가 없다. "누가 이 API를 호출할 수 있나"에 즉답이 안 나온다. 관리 기능이 일반 API와 같은 경로에 있다.
- 진단:
  1. 자산 목록을 만든다.
  2. 공격자 프로파일을 정한다. 외부 익명, 인증된 악성 사용자, 악성 테넌트, 내부자, 탈취된 의존성, 탈취된 CI.
  3. 경계를 넘는 흐름마다 STRIDE를 적용한다.
  4. 고가치 목표("타 테넌트 데이터 읽기")는 공격 트리로 분해해 가장 싼 경로를 찾는다.
- 조치: 위협마다 완화책, 담당자, 검증 방법(테스트 또는 리뷰 항목)을 붙인다. 수용한 위험은 수용자와 재검토 시점을 기록한다.

**설계 점검표**
- [ ] 각 구성요소가 필요한 최소 권한만 가졌는가? 사람이 아니라 워크로드 단위로 확인한다.
- [ ] 실패 시 닫히는가(fail-closed)? 인가 서비스 장애 시 허용으로 떨어지지 않는가?
- [ ] 기본값이 안전한가? 디버그 엔드포인트, 기본 자격 증명, 공개 버킷, 넓은 CORS가 없어야 한다.
- [ ] 쓰지 않는 기능·포트·엔드포인트를 제거했는가?
- [ ] 단일 통제가 무너질 때 피해 범위(blast radius)가 한정되는가?
- [ ] 보안 결정이 클라이언트가 아니라 서버에 있는가?

## 인증·인가와 세션 관리

**자주 보는 실패**
- **비밀번호를 범용 해시로 저장한다.** SHA-256에 솔트를 쳐도 빠른 해시는 GPU 대입에 약하다. 메모리 하드 KDF(예: Argon2id, scrypt)나 bcrypt를 쓰고, 파라미터를 주기적으로 상향한다. 길이 제한(bcrypt의 입력 길이 한계 등)과 페퍼 운용 방식은 직접 확인한다.
- **JWT를 "서명되어 있으니 안전하다"고 믿는다.**
  - 실제 사고: `alg` 헤더 신뢰(none, RS→HS 혼동), `aud`/`iss`/`exp` 미검증, 키 ID(`kid`)로 임의 경로 로드.
  - 근본 원인: 검증 라이브러리에 알고리즘을 고정하지 않았다.
- **JWT를 세션처럼 쓰고 폐기를 못 한다.** 수명이 긴 무상태 토큰은 로그아웃, 권한 회수, 탈취 대응이 불가능하다. 짧은 액세스 토큰 + 회전하는 리프레시 토큰 + 재사용 탐지가 대안이다.
- **OAuth를 인증으로 오용한다.** 액세스 토큰을 받았다고 사용자 신원이 증명되지는 않는다. 신원은 OIDC ID 토큰을 검증해 확인한다(서명, `aud`, `nonce`).
  - 공개 클라이언트(SPA, 모바일)는 PKCE가 사실상 필수다.
  - 암시적 흐름과 비밀번호 그랜트는 현행 권고에서 배제되는 추세다.
  - `redirect_uri`는 정확 일치로 비교한다.
- **MFA를 붙였지만 우회 경로가 남는다.** 비밀번호 재설정, 레거시 API, 지원팀 수동 처리가 흔한 구멍이다. SMS·TOTP는 피싱 중계에 약하다. 패스키(WebAuthn)는 출처(origin)에 바인딩되어 피싱 저항성이 높지만, 계정 복구 경로가 약하면 효과가 상쇄된다.
- **인가를 컨트롤러마다 흩어 놓는다.** 엔드포인트 하나만 빠져도 IDOR이 된다. RBAC는 역할이 폭증하면 관리가 무너진다. 소유권·테넌트·속성 조건이 필요하면 ABAC나 관계 기반 모델로 중앙화한다.
- **세션 고정.** 로그인이나 권한 상승 시 세션 ID를 재발급하지 않는다.

**징후→진단→조치**
- 징후: 로그아웃 후에도 API가 동작한다. 역할 이름이 수십 개다. 토큰 검증 코드가 서비스마다 복붙되어 있다.
- 진단:
  - 토큰 검증 경로를 하나 골라 알고리즘 고정, 클레임 검증, 키 회전 대응을 확인한다.
  - 객체 접근 엔드포인트마다 "타인 ID로 바꾸면?"을 테스트한다.
- 조치:
  - 검증은 공용 미들웨어로, 인가는 정책 엔진 또는 단일 계층으로 모은다.
  - 쿠키는 `HttpOnly`, `Secure`, 적절한 `SameSite`로 설정한다.
  - 유휴·절대 만료를 함께 둔다.
  - 고위험 작업에는 재인증(step-up)을 요구한다.

**점검표**
- [ ] 비밀번호 저장에 느린 KDF를 쓰고, 유출 비밀번호 대조와 레이트 리밋을 적용했는가?
- [ ] 계정 열거(로그인·재설정 응답 차이, 타이밍)를 막았는가?
- [ ] 토큰 검증에서 알고리즘, 발급자, 대상, 만료, 키 회전(JWKS 캐시 갱신)을 모두 처리하는가?
- [ ] 세션과 토큰을 서버 측에서 폐기할 수 있는가? 비밀번호 변경 시 기존 세션을 끊는가?
- [ ] 인가 거부가 기본이고, 테넌트 격리 조건이 모든 쿼리에 강제되는가?
- [ ] 계정 복구 경로가 주 인증 수단만큼 강한가?

## 웹·API 애플리케이션 취약점

근본 원리는 하나다. **데이터가 다른 해석기(SQL, 셸, HTML, URL 파서, 역직렬화기)에서 코드나 제어 정보로 해석된다.** 방어는 "입력을 깨끗이"가 아니라 그 해석기의 문맥에 맞게 데이터와 코드를 분리하는 것이다.

**자주 보는 실패**
- **인젝션:** 문자열 연결로 만든 쿼리, ORM의 raw 쿼리, 동적 정렬 컬럼명, 셸 호출.
  - 매개변수화 쿼리를 쓴다.
  - 식별자는 허용 목록으로 받는다.
  - 셸을 거치지 않는 인자 배열 실행으로 막는다.
  - 블랙리스트 필터는 거의 항상 우회된다.
- **XSS:** 출력 인코딩을 문맥(HTML 본문, 속성, JS, URL)별로 하지 않는다. 프레임워크의 "raw HTML" 탈출구를 쓴다. 사용자 입력이 `href`의 `javascript:`로 들어간다.
  - CSP는 보조 방어다. `unsafe-inline`이 있으면 효과가 크게 떨어진다. nonce·해시 기반 정책을 쓴다.
- **CSRF:** 쿠키 인증을 쓰면서 상태 변경을 GET으로 처리하거나 토큰이 없다. `SameSite`는 도움이 되지만 하위 도메인, 브라우저 차이, `Lax`의 예외 때문에 유일한 방어로 두지 않는다.
- **CORS 오해:** CORS는 서버를 보호하는 장치가 아니다. 브라우저의 읽기 제한을 푸는 장치다.
  - Origin을 그대로 반사하면서 `credentials`를 허용하는 설정이 흔한 사고다.
  - `null` origin 허용, 접미사 매칭(`evil-example.com`)도 마찬가지다.
- **SSRF:** URL 미리보기, 웹훅, 이미지 가져오기, PDF 렌더러가 내부 메타데이터 엔드포인트나 내부 서비스에 접근한다.
  - 호스트명 검사 후 DNS 재바인딩, 리다이렉트, IPv6·10진 표기 우회가 일어난다.
  - 조치: 송신 전용 프록시를 두고, 해석된 IP 기준으로 차단하며, 리다이렉트를 재검증한다. 클라우드 메타데이터는 토큰 필수 모드를 쓴다.
- **안전하지 않은 역직렬화:** 언어 고유 객체 직렬화(예: Java 직렬화, pickle, 일부 YAML 로더)로 신뢰할 수 없는 입력을 받는다. 서명 검증만으로는 키 유출 시 무너진다. 데이터 전용 형식과 스키마 검증으로 바꾼다.
- **IDOR·BOLA:** 인증은 했지만 객체 소유권을 확인하지 않는다. 추측 불가능한 ID(UUID)는 완화책일 뿐 인가가 아니다. 대량 할당(mass assignment)으로 `role`, `tenant_id`가 덮어써지는 것도 같은 계열이다.
- **API 특유의 실패:**
  - 응답에 내부 필드를 과다 노출한다.
  - 페이지 크기와 GraphQL 쿼리 깊이·비용에 제한이 없다.
  - 레이트 리밋을 IP 기준으로만 걸어 인증 계정·토큰 단위 남용을 놓친다.

**징후→진단→조치**
- 징후: "프론트에서 검증한다", 검증 로직이 엔드포인트마다 다르다, 내부 URL을 받는 기능이 있다.
- 진단: 신뢰 불가 입력이 들어가는 모든 해석기(sink)를 추적한다. 객체 접근 API는 두 계정으로 교차 테스트한다.
- 조치:
  - 서버 측 스키마 검증(형식·길이·열거형, 알 수 없는 필드 거부)을 적용한다.
  - 문맥별 출력 인코딩을 기본으로 둔다.
  - 인가 검사를 데이터 접근 계층에 강제한다.

**점검표**
- [ ] 모든 쿼리가 매개변수화되었는가? 동적 식별자는 허용 목록으로 받는가?
- [ ] 템플릿 자동 이스케이프를 켰는가? raw 출력 사용처를 목록화했는가?
- [ ] 상태 변경 요청에 CSRF 방어가 있는가? CORS가 명시적 허용 목록인가?
- [ ] 서버 측 URL 가져오기에 송신 통제가 있는가?
- [ ] 역직렬화 입력이 신뢰 가능한가? 아니라면 형식을 바꿨는가?
- [ ] 레이트 리밋과 리소스 상한(크기, 깊이, 시간)이 있는가?
- [ ] 오류 응답에 스택 트레이스나 내부 정보가 없는가?

## 응용 암호학의 올바른 사용

**자주 보는 실패**
- **직접 조합하는 암호.** 기밀성만 있는 모드(CBC, CTR)에 무결성을 빠뜨리거나, MAC을 잘못된 순서로 결합한다. 기본은 AEAD(예: AES-GCM, ChaCha20-Poly1305)이고, 가능하면 고수준 라이브러리(예: libsodium 계열, Tink 계열)를 쓴다.
- **논스 재사용.** GCM에서 같은 키·논스를 재사용하면 기밀성과 인증이 함께 붕괴한다. 무작위 논스는 키당 암호화 횟수 한도를 고려한다. 대량 암호화에는 키 회전이나 논스 오용 내성 구성을 검토한다.
- **용도 혼동.**
  - 해시는 무결성 지문일 뿐이고 키가 없다.
  - 메시지 인증에는 MAC(HMAC)을 쓴다. 단순 `hash(key||msg)`는 길이 확장 공격에 취약할 수 있다.
  - 부인 방지와 공개 검증에는 전자서명을 쓴다.
  - 비밀번호에서 키를 만들 때는 느린 KDF를, 이미 고엔트로피인 비밀에서 키를 파생할 때는 HKDF류를 쓴다.
  - 비대칭 암호로 대용량 데이터를 직접 암호화하지 않는다. 하이브리드 구성을 쓴다.
- **약한 난수.** 토큰·키·논스를 일반 PRNG(예: 언어 기본 `random`)로 만든다. 운영체제 CSPRNG를 쓴다.
- **비교 타이밍.** MAC과 토큰을 일반 문자열 비교로 검사한다. 상수 시간 비교를 쓴다.
- **TLS 검증 끄기.** "개발 중에만" 끈 인증서 검증이 운영에 남는다. 호스트명 검증 누락, 사설 CA를 전역 신뢰 저장소에 추가하는 경우도 흔하다. 상호 TLS는 클라이언트 인증서 폐기와 회전 계획이 있어야 한다.
- **인코딩을 암호로 착각한다.** Base64, 난독화, "자체 알고리즘"이 그렇다.

**알고리즘 수명 주기와 암호 민첩성**
- 알고리즘·키 길이·파라미터는 언젠가 바뀐다고 전제한다.
  - 암호문과 서명에 버전·알고리즘 식별자를 넣는다.
  - 재암호화 경로를 설계에 포함한다.
  - 알고리즘을 코드 곳곳에 하드코딩하지 않는다.
- 양자내성 전환:
  - 장기 기밀 데이터는 "지금 수집하고 나중에 해독" 위협을 고려한다.
  - 키 교환부터 하이브리드(고전+PQC) 구성을 검토한다.
  - 표준화된 알고리즘(예: ML-KEM, ML-DSA 계열)의 라이브러리 지원 상태는 시점마다 달라지므로 확인한다.
  - 첫 단계는 암호 사용처 목록(인벤토리) 작성이다.

**징후→진단→조치**
- 징후: 코드에 `AES/ECB`, `MD5`, `verify=False`, 고정 IV, `Math.random` 토큰이 보인다.
- 진단: 암호 호출 지점을 검색해 용도·키 출처·논스 생성·검증 여부를 표로 만든다.
- 조치: 고수준 API로 교체한다. 버전 필드를 추가하고 점진적으로 재암호화한다.

**점검표**
- [ ] 직접 설계한 프로토콜이나 구성이 없는가?
- [ ] AEAD를 쓰고, 논스 고유성이 보장되는가?
- [ ] 키·토큰을 CSPRNG로 생성하는가?
- [ ] 인증서 검증과 호스트명 검증을 모든 클라이언트에서 켰는가?
- [ ] 알고리즘 교체 경로와 암호 인벤토리가 있는가?

## 비밀값과 키 관리

**자주 보는 실패**
- **비밀값이 저장소, 이미지 레이어, CI 로그, 환경 변수 덤프, 크래시 리포트에 남는다.** 커밋을 지워도 히스토리, 포크, 캐시에 남는다. 유출된 비밀값은 삭제가 아니라 **폐기·교체**가 우선이다.
- **장기 정적 자격 증명.** 클라우드 액세스 키, 서비스 계정 키 파일, 개인 토큰을 CI와 워크로드에 박아 둔다. 단기 자격 증명(OIDC 페더레이션, 워크로드 아이덴티티, 인스턴스 역할)으로 대체할 수 있는지부터 묻는다.
- **"볼트에 넣었으니 끝".** 볼트 접근 토큰 자체가 정적이다. 모든 워크로드가 모든 경로를 읽을 수 있다. 감사 로그를 보지 않는다.
- **KMS로 데이터를 직접 대량 암호화한다.** 크기 제한과 지연 때문에 비효율적이다. 봉투 암호화로 처리한다.
  - 데이터 키(DEK)로 데이터를 암호화한다.
  - 마스터 키(KEK)가 있는 KMS·HSM으로 DEK를 감싼다.
  - 회전은 KEK 기준으로 하고, 재암호화 범위를 설계해 둔다.
- **교체 불가능한 설계.** 키가 하나뿐이고 교체하면 서비스가 중단된다. 다중 키 동시 유효(구키 검증, 신키 서명) 기간을 설계해야 무중단 회전이 가능하다.
- HSM도 키 추출을 무조건 막아 주지는 않는다. 키 속성(extractable 등)과 내보내기 정책에 따라 키 래핑을 통한 반출이 허용될 수 있고, 제품에 따라 기본값이 추출 가능인 경우도 있다. 추출 방지는 키를 추출 불가 속성으로 생성하고 래핑·내보내기 정책을 막았을 때에만 성립하므로, 실제 설정을 확인한다. 그렇게 설정해도 호출 권한이 탈취되면 오용은 막지 못한다. 사용 정책과 호출 모니터링이 함께 필요하다.

**징후→진단→조치**
- 징후: `.env`가 커밋되었다. 키 생성일이 수년 전이다. 담당자가 퇴사했는데 키는 그대로다.
- 진단: 비밀 스캐너로 히스토리 전체와 아티팩트를 스캔한다. 비밀값마다 소유자·용도·범위·만료·마지막 사용 시점을 목록화한다.
- 유출 대응 순서:
  1. 폐기·교체한다.
  2. 해당 자격 증명의 사용 로그로 악용 여부를 조사한다.
  3. 유출 경로를 차단한다.
  4. 히스토리를 정리한다. 이는 보조 수단이다.
- 예방: pre-commit 훅과 저장소 측 푸시 차단 스캐닝을 함께 쓴다. 클라이언트 훅만으로는 우회된다.

**점검표**
- [ ] 코드·이미지·로그에 비밀값이 없는가? 로그 마스킹이 있는가?
- [ ] 정적 키 대신 단기·페더레이션 자격 증명을 쓰는가?
- [ ] 비밀값마다 최소 범위, 소유자, 회전 주기, 폐기 절차가 있는가?
- [ ] 무중단 회전을 실제로 연습해 봤는가?
- [ ] 볼트·KMS 접근이 워크로드별로 분리되고 감사되는가?

## 소프트웨어 공급망 보안

**자주 보는 실패**
- **범위 버전과 잠금 파일 미사용.** 빌드마다 다른 의존성이 들어온다.
- **이름 혼동 공격.** 의존성 혼동(내부 패키지명을 공개 레지스트리에 선점), 타이포스쿼팅, 유지관리자 계정 탈취가 있다. 설치 스크립트(postinstall 등)가 개발자 PC와 CI에서 임의 코드를 실행한다.
- **스캐너 경보 피로.** 수백 건의 CVE를 일괄 무시한다.
  - 근본 원인: 도달 가능성, 실제 노출, 악용 여부(KEV류 목록, EPSS류 지표)로 분류하지 않는다.
  - 반대로 "CVE가 없으니 안전"하다는 판단도 틀렸다. 악성 패키지는 대개 CVE가 없다.
- **CI/CD가 최고 권한 시스템인데 가장 덜 보호된다.**
  - 신뢰할 수 없는 PR이 비밀값에 접근한다(예: 포크 PR에 비밀을 노출하는 트리거 설정).
  - 서드파티 액션·플러그인을 변경 가능한 태그로 참조한다.
  - 러너를 작업 간에 재사용해 오염이 지속된다.
- **SBOM을 만들고 아무도 쓰지 않는다.** SBOM의 가치는 새 취약점 공개 시 "우리 어디에 있나"를 몇 분 안에 답하는 데 있다.
- 서명을 해 놓고 배포 측에서 검증하지 않는다. 검증하지 않는 서명은 통제가 아니다.

**징후→진단→조치**
- 징후: 잠금 파일이 없다. 액션을 `@main`으로 참조한다. 빌드 서버에 사람이 SSH로 들어간다. 배포 아티팩트의 출처를 증명할 수 없다.
- 진단: 소스→빌드→아티팩트→배포 각 단계에서 "누가 무엇을 바꿀 수 있나"를 그린다. SLSA 단계 요구사항을 기준표로 쓴다.
- 조치:
  - 의존성을 잠그고 해시를 검증한다. 내부 레지스트리를 프록시하고 네임스페이스를 예약한다.
  - 서드파티 액션은 커밋 해시로 고정한다.
  - CI 토큰은 최소 권한으로 두고 작업 단위로 발급한다.
  - 격리된 일회용 러너를 쓴다.
  - 아티팩트에 서명하고 출처 증명을 붙인다(예: Sigstore 계열의 키리스 서명). 배포 시 admission 단계에서 검증한다.
  - 보호 브랜치와 필수 리뷰를 적용하고, 리뷰어가 자기 변경을 승인하지 못하게 한다.

**점검표**
- [ ] 잠금 파일과 무결성 해시가 있고, 업데이트는 리뷰를 거치는가?
- [ ] 신규 의존성 도입 기준(유지관리 상태, 권한, 설치 스크립트)이 있는가?
- [ ] 취약점 분류가 도달 가능성과 악용 여부 기반인가?
- [ ] CI가 신뢰 불가 코드와 비밀값을 분리하는가?
- [ ] 아티팩트 서명을 배포 단계에서 강제 검증하는가?
- [ ] SBOM이 자산 목록과 연결되어 조회 가능한가?

## 클라우드·인프라 보안

**자주 보는 실패**
- **공동 책임 모델 오해.** "관리형 서비스니까 보안은 클라우드 사업자 몫"이라고 여긴다. 사업자는 인프라를 책임지고, 구성·IAM·데이터·패치 범위의 상당 부분은 고객 몫이다. 경계는 서비스 유형(IaaS/PaaS/SaaS)에 따라 다르다.
- **IAM 와일드카드.** `*` 액션과 리소스를 쓰고, 신뢰 정책이 넓다(외부 계정·임의 주체가 역할을 맡을 수 있다).
  - 권한 상승 경로가 숨어 있다. 역할 전달 권한, 정책 수정 권한, 함수 코드 교체 권한이 대표적이다.
  - 사람 계정의 영구 관리자 권한도 같은 문제다.
- **데이터 저장소 노출.** 공개 버킷, 인터넷에 열린 DB·검색 엔진·캐시, 공유된 스냅샷이 반복되는 대형 유출 원인이다.
- **평면 네트워크.** VPC 안이면 서로 다 통신한다. 제로 트러스트의 핵심은 "망 위치로 신뢰를 주지 않는다"이다. 요청마다 신원·기기·맥락을 인증·인가하는 것이다. VPN을 없애는 것이 핵심이 아니다.
- **컨테이너를 격리 경계로 과신한다.**
  - 위험 구성: 특권 컨테이너, 호스트 경로 마운트, 런타임 소켓 마운트, root 실행, 자동 마운트된 서비스 계정 토큰.
  - 쿠버네티스 위험: 넓은 RBAC, 기본 허용 네트워크 정책, 노드에서 클라우드 메타데이터 접근.
  - 멀티테넌트라면 커널 공유의 한계를 인정하고 샌드박스 런타임이나 노드 분리를 검토한다.
- **IaC 드리프트.** 콘솔 수동 변경이 코드와 어긋난다. 상태 파일에 비밀값이 평문으로 남는다.

**징후→진단→조치**
- 징후: 루트 계정을 일상적으로 사용한다. 정책 문서에 `*`가 있다. 보안 그룹에 `0.0.0.0/0`이 있다. 파드가 `privileged: true`다.
- 진단:
  - 클라우드 설정 진단(CSPM류) 결과를 실제 노출 경로와 결합해 본다. 인터넷 노출 + 민감 데이터 + 과도 권한이 겹치는 지점이 1순위다.
  - IAM 접근 분석으로 미사용 권한을 찾는다.
- 조치:
  - 조직 수준 가드레일(서비스 제어 정책류, 공개 접근 차단 기본값)을 둔다.
  - 계정·프로젝트를 분리한다.
  - IaC에 정책 검사(policy-as-code)를 PR 단계에서 적용한다.
  - admission 정책으로 위험 파드 사양을 거부한다.
  - 기본 거부 네트워크 정책을 적용한다.
  - 사람 접근은 SSO, 단기 권한 승격(JIT), 세션 기록으로 관리한다.

**점검표**
- [ ] 루트·브레이크글래스 계정이 봉인되고 사용 시 경보가 울리는가?
- [ ] IAM이 최소 권한이고, 권한 상승 경로를 검토했는가?
- [ ] 데이터 저장소가 기본 비공개, 저장 시 암호화, 접근 로깅 상태인가?
- [ ] 네트워크가 분할되고 송신(egress)도 통제되는가?
- [ ] 컨테이너가 비root, 읽기 전용 루트 파일시스템, 최소 capability로 실행되는가?
- [ ] 이미지가 최소 베이스이고 정기적으로 재빌드되는가?
- [ ] IaC가 단일 진실 원천이고, 드리프트를 탐지하는가?

## 탐지·사고 대응과 보안 개발 수명 주기 운영

**탐지 쪽 실패**
- **"다 수집했는데 아무것도 모른다."** 로그는 많지만 질문이 정의되지 않았다. 탐지는 "어떤 공격 행위를 어떤 신호로 잡을지"(예: ATT&CK류 기법 매핑)에서 출발해 역산한다.
- **반드시 남겨야 하는 이벤트가 빠진다.**
  - 인증 성공·실패
  - 권한 변경
  - 비밀값 접근
  - 관리 작업
  - 클라우드 제어면(control plane) 로그
  - 대량 데이터 접근
  - 인가 거부
- **로그 자체가 위험하다.** 비밀번호, 토큰, 개인정보가 들어간다. 로그 인젝션이 일어난다. 공격자가 로그를 지울 수 있다. 로그는 별도 계정의 변경 불가 저장소로 보내고, 시간 동기화를 맞춘다.
- **탐지 규칙을 테스트하지 않는다.** 규칙이 조용히 깨진다. 공격 시뮬레이션으로 정기 검증하고, 경보마다 대응 런북을 붙인다. 오탐률이 높은 규칙은 조정하거나 폐기한다.

**사고 대응 실패와 순서**
- 흔한 실패:
  - 증거를 먼저 파괴한다. 인스턴스를 즉시 종료하거나, 재부팅해 메모리를 잃는다.
  - 공격자에게 대응 사실을 알린다. 탐지 직후 유출 계정만 먼저 바꾸면 공격자가 다른 지속성 수단으로 옮겨 간다.
  - 대응 채널이 탈취된 시스템 위에 있다.
- 순서:
  1. **준비:** 역할, 연락망, 권한, 별도 통신 채널, 런북.
  2. **식별·범위 산정:** 타임라인, 영향 자산.
  3. **격리:** 네트워크 격리, 자격 증명 일시 정지. 증거 보존과 균형을 맞춘다.
  4. **근절:** 지속성 수단, 백도어, 탈취된 키를 전면 교체한다.
  5. **복구:** 신뢰 가능한 이미지로 재구축하고, 강화 모니터링하에 복귀한다.
  6. **사후 분석:** 비난 없는 회고, 근본 원인, 통제 개선, 탐지 공백 보완.
- 포렌식 보존:
  - 휘발성 순서대로 수집한다. 메모리 → 프로세스·네트워크 → 디스크 → 로그.
  - 디스크 스냅샷과 해시를 확보하고, 증거 관리 기록(누가·언제·무엇을)을 남긴다.
  - 법적·규제 통지 기한이 있을 수 있으므로 법무와 조기에 연계한다. 기한은 관할마다 다르니 단정하지 않는다.

**SDLC 운영 실패**
- **보안 요구사항이 없다.** 기능 명세에 인증·인가·데이터 분류·로깅 요구가 없어서 리뷰 기준도 없다. 요구 기준 틀(예: ASVS류)을 재단해 쓴다.
- **SAST·DAST를 붙이기만 한다.** 결과가 개발자 흐름(PR 코멘트) 밖에 있다. 차단 기준이 없거나 모든 것을 차단해 결국 꺼진다.
  - 새로 들어온 고신뢰 결과만 차단한다.
  - 기존 부채는 별도 백로그로 관리한다.
  - SAST는 비즈니스 로직 결함(IDOR 등)을 거의 못 잡는다. 위협 모델 기반 리뷰와 테스트로 보완한다.
- **코드 리뷰가 보안을 보지 않는다.** 인증·인가·암호·역직렬화·파일·URL 처리 변경은 보안 리뷰 트리거로 지정한다.
- **패치 SLA가 이름뿐이다.**
  - 심각도별 기한(예: 악용 중인 치명 취약점은 수일 이내)을 정한다. 숫자는 조직 위험 성향에 따라 정한다.
  - 예외는 보완 통제와 만료일을 붙여 승인한다.
  - 자산 목록이 없으면 SLA를 측정할 수 없다.

**징후→진단→조치**
- 징후: 마지막 사고 훈련 기록이 없다. 경보의 대부분이 무시된다. 취약점 백로그가 늘기만 한다.
- 진단: 최근 사고나 모의 시나리오로 "탐지까지 걸린 시간, 범위 산정 가능 여부, 필요한 로그 존재 여부"를 측정한다.
- 조치:
  - 고가치 시나리오 몇 개부터 탐지와 런북을 완성한다.
  - 정기 테이블탑 훈련을 한다.
  - 취약점 지표(기한 준수율, 평균 수정 시간)를 경영 보고에 올린다.

**점검표**
- [ ] 핵심 보안 이벤트가 중앙에 변경 불가로 저장되고, 보존 기간이 정의되었는가?
- [ ] 탐지 규칙마다 담당자, 런북, 정기 검증이 있는가?
- [ ] 사고 대응 역할, 대체 통신 채널, 증거 보존 절차가 문서화·훈련되었는가?
- [ ] 보안 요구사항과 위협 모델이 설계 단계 산출물인가?
- [ ] 스캐너 결과가 PR 흐름에 들어가고, 차단 기준이 합리적인가?
- [ ] 패치 SLA, 예외 승인, 자산 목록이 연결되어 측정되는가?

## 더 짚을 것 (검토 보강)

- **경로 순회:** 사용자 입력으로 파일 경로를 만들지 않는 것이 먼저다. 어쩔 수 없으면 정규화하고 심볼릭 링크를 풀어 낸 실제 경로가 기준 폴더 안인지 확인한다. 압축 파일을 풀 때는 항목마다 경로를 같은 방식으로 검사한다(Zip Slip).
- **업로드 파일:** 실행될 수 있는 위치(웹 루트, 스크립트 폴더)에 두지 않는다. SVG·HTML 업로드는 XSS 통로이므로 별도 출처에서 내보내거나 다운로드로만 준다. 이미지 처리 라이브러리도 공격면이다.
- **경쟁 조건:** "확인한 뒤 사용"(TOCTOU) 사이에 상태가 바뀌면 쿠폰·잔액·재고·초대 코드가 두 번 쓰인다. 원자적 조건부 갱신(`UPDATE … WHERE 잔액 >= 금액`), 유니크 제약, 멱등 키, 필요한 곳의 잠금으로 막는다. 정적 분석은 이것을 거의 찾지 못하므로 동시 요청 시험을 둔다.
- **LLM·에이전트 기능:** 외부 글(웹 페이지, 문서, 이메일, 이슈)은 지시가 아니라 데이터로 다룬다(프롬프트 인젝션). 도구 권한은 최소로 주고, 돈·삭제·외부 전송 같은 민감한 동작은 사람 확인을 거친다. 모델 출력은 신뢰하지 않는 입력처럼 이스케이프하고, 비밀값을 컨텍스트에 넣지 않는다.

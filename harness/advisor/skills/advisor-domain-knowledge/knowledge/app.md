# 앱 어드바이저 지식

이 파일은 앱 관련 지시를 받았을 때 숨은 전제를 찾아내고 빠진 고려를 짚기 위한 개념 지도다. 각 영역은 핵심 개념과 원리, 판단 규칙, 트레이드오프, 흔한 오해 순서로 정리한다. 버전, 수치, 정책은 자주 바뀐다. 아래에 나오는 구체적인 숫자와 제품명은 예시일 뿐이며, 실제 판단은 해당 시점의 공식 문서로 확인해야 한다.

**공통 원칙**
- 모바일 앱은 OS가 자원을 통제하는 손님 프로세스다. 데스크톱 앱은 그보다 자유롭지만 배포 신뢰 체계(서명·공증·백신)에 묶여 있다.
- "되게 만들기"보다 "OS가 언제 나를 죽이고, 막고, 거절하는가"를 먼저 묻는다.

## 앱 수명 주기와 백그라운드 실행

**핵심 개념과 원리**
- 앱 상태는 대략 다섯 가지다. 실행 중(포그라운드·활성), 비활성(전화 수신·제어센터 등), 백그라운드, 일시정지(메모리에 있으나 CPU 할당 없음), 종료.
- 핵심 사실은 하나다. 일시정지 상태의 앱은 메모리 압박이 오면 **아무 콜백 없이** 종료될 수 있다. 사용자에게는 "앱이 계속 떠 있던 것"처럼 보이지만 실제로는 콜드 스타트가 일어난다.
- 그래서 상태 복원이 필요하다. 지원 수단은 Android의 SavedState·프로세스 재생성, iOS의 장면(Scene) 상태 복원 등이다. 화면 위치, 입력 중인 폼, 내비게이션 스택처럼 사용자가 기대하는 상태는 백그라운드로 갈 때 저장해야 한다. 종료 콜백에 의존하면 안 된다.
- Android는 설정 변경(회전·다크모드·언어)이 일어나면 기본적으로 Activity를 재생성한다. 매니페스트의 android:configChanges로 해당 변경을 직접 처리하겠다고 선언하면 재생성되지 않고 onConfigurationChanged가 호출되며, 이때 리소스 재적용은 앱이 책임진다. 생명주기를 고려하지 않은 코드에서는 상태 유실과 메모리 누수가 함께 나타난다.

**백그라운드 실행 수단**
- 모바일 OS는 배터리를 이유로 백그라운드 실행을 점점 더 제한하는 방향으로 움직여 왔다. 데스크톱 OS는 상대적으로 자유롭다(아래 데스크톱 항목 참조).
- Android
  - 지연 가능하고 보장이 필요한 작업에는 WorkManager를 쓴다. 제약조건(네트워크·충전 중), 재시도, 백오프, 체이닝을 지원한다.
  - 사용자가 인지해야 하는 즉시·지속 작업(재생·내비게이션·운동 기록)에는 포그라운드 서비스를 쓴다. 최근 버전은 서비스 유형 선언과 사용 목적 심사를 요구한다.
  - 정확한 시각에 실행해야 하면 정확 알람을 쓰지만, 이 권한 자체가 제한될 수 있다.
  - Doze·앱 대기 버킷·제조사별 배터리 최적화 때문에 실행 시점은 보장되지 않는다.
- iOS
  - BGTaskScheduler(앱 새로고침·처리 작업)는 OS가 사용 패턴과 배터리를 보고 **실행 여부와 시점을 결정**한다. 요청은 힌트일 뿐이다.
  - 그 외 수단: 백그라운드 URLSession(시스템이 앱을 종료해도 OS가 전송을 이어 간다. 단, 사용자가 앱 전환기에서 강제 종료하면 진행 중인 백그라운드 전송은 취소된다), 무음 푸시(빈도 제한·전달 비보장), 특정 백그라운드 모드(오디오·위치·VoIP 등, 심사 대상).
  - 백그라운드 진입 직후 연장 시간은 짧다(수십 초 수준, 버전별 상이).
- 데스크톱: 시스템 트레이·로그인 항목·서비스(데몬)로 상주할 수 있다. 다만 macOS는 로그인 항목을 사용자에게 고지하고, 절전과 App Nap이 타이머를 늦춘다.

**판단 규칙**
- "주기적으로 N분마다 동기화" 같은 요구를 보면 먼저 정확성 요구가 진짜인지 묻는다.
- 서버 주도 갱신이 가능하면 푸시를 기반으로 하고 앱 진입 시 증분 동기화를 하는 조합이 대체로 낫다.
- 대용량 업로드·다운로드는 OS 위임 전송(백그라운드 URLSession, WorkManager의 장기 작업 등)을 쓴다.
- 작업은 중간에 끊겨도 재실행 가능하도록 멱등하게 쪼갠다.

**흔한 오해**
- "onDestroy나 applicationWillTerminate에서 저장하면 된다": 호출이 보장되지 않는다.
- "iOS에서 15분마다 백그라운드 작업이 돈다": 보장되지 않는다. 사용자가 앱을 강제 종료하면 많은 백그라운드 경로가 막힌다.
- "에뮬레이터에서 됐으니 된다": 실제 기기의 제조사 배터리 정책과 저전력 모드에서 따로 검증해야 한다.

## 오프라인 우선 데이터와 동기화

**핵심 개념과 원리**
- 오프라인 우선은 로컬 DB를 진실의 원천으로 두고 UI가 로컬만 관찰하는 구조다. 네트워크는 로컬을 갱신하는 백그라운드 과정이 된다.
- 이 구조에서는 지연·단절·불안정 네트워크가 예외가 아니라 기본 상태로 취급된다. 모바일 네트워크는 "연결됨" 표시와 실제 도달 가능성이 자주 어긋난다. 따라서 연결 상태 API보다 **요청 실패 처리**가 본질이다.
- 구성 요소
  - 로컬 저장소: SQLite 계열, Room, Core Data/SwiftData, Realm 등.
  - 변경 큐(아웃박스): 로컬 변경을 작업 단위로 기록한다. 클라이언트가 만든 ID와 멱등 키를 포함한다.
  - 동기화 커서: 서버의 변경 시퀀스, 타임스탬프, 버전 벡터 등.
  - 충돌 해결 정책.
- 증분 동기화는 "마지막 커서 이후 변경분"만 받는다. 삭제 전파에는 툼스톤이 필요하다. 툼스톤 보존 기간보다 오래 오프라인이었던 클라이언트는 전체 재동기화로 보내는 경로가 있어야 한다.

**충돌 해결 선택**
- LWW(마지막 쓰기 승리)
  - 장점: 단순하다.
  - 한계: 클라이언트 시계를 믿으면 시계 오차로 엉뚱한 쪽이 이긴다. 서버 수신 순서나 하이브리드 논리 시계를 쓴다.
  - 한계: 레코드 단위 LWW는 서로 다른 필드 편집을 덮어쓴다. 필드 단위로 낮추면 많이 완화된다.
- 서버 권위 + 재조정: 서버가 거절하면 클라이언트가 롤백하거나 재적용한다. 재고·결제·예약처럼 불변식이 있는 데이터에 필수다. 이런 데이터는 오프라인 "확정"을 허용하면 안 되고 "보류" 상태로 보여야 한다.
- CRDT: 공동 편집 텍스트, 리스트, 카운터처럼 병합이 의미 있는 데이터에 적합하다. 대가는 메타데이터 증가, 구현 복잡도, 권한·검증 로직을 붙이기 어렵다는 점이다. 모든 데이터에 쓸 이유는 없다.
- 사용자에게 묻기: 문서형 데이터에서 자동 병합이 불가능할 때만 쓴다.

**판단 규칙**
- 데이터 종류별로 정책을 나눈다.
  - 참조 데이터: 캐시 + 만료.
  - 사용자 소유 데이터: 필드 LWW.
  - 공유·불변식 데이터: 서버 권위.
  - 협업 데이터: CRDT/OT.
- 스키마 마이그레이션은 로컬 DB에도 있다. 구버전 앱이 보낸 큐 항목을 서버가 받아들여야 하므로, 동기화 프로토콜에도 버전이 필요하다.
- 캐시에는 무효화 기준을 정한다(TTL, ETag/조건부 요청, 서버 푸시 무효화).
- 민감 데이터의 로컬 저장은 암호화 여부와 로그아웃 시 삭제를 함께 설계한다.

**흔한 오해**
- "오프라인 지원 = 응답 캐싱": 쓰기 큐와 충돌 처리가 없으면 읽기 전용 오프라인일 뿐이다.
- "재시도하면 된다": 멱등 키가 없으면 중복 결제와 중복 생성이 생긴다.
- "CRDT면 일관성 문제 끝": 수렴은 보장하지만 비즈니스 규칙의 정합성은 보장하지 않는다.

## 네이티브·크로스플랫폼 아키텍처 선택

**핵심 개념과 원리**
- 선택의 본질은 세 가지다. 어느 층을 공유하는가(UI까지, 로직만), 플랫폼 API와의 거리, 조직의 기술 역량. 성능 차이는 대부분의 앱에서 결정 요인이 아니다. 결정 요인은 **플랫폼 기능 접근 비용**과 **장기 유지보수**다.

**스택별 특징**
- 네이티브(Swift/Kotlin): 신규 OS 기능을 즉시 쓸 수 있고 플랫폼 관례에 맞추기 쉽다. 대신 두 팀(또는 두 코드베이스)을 유지해야 한다.
- Flutter: 자체 렌더링이라 UI 일관성이 높다. 플랫폼 기본 컴포넌트와는 체감이 다를 수 있고, 네이티브 기능은 플랫폼 채널과 플러그인에 의존한다.
- React Native: JS/TS 생태계와 웹 인력을 활용한다. 신 아키텍처로 브리지 비용이 줄었지만 네이티브 모듈 품질과 업그레이드 부담이 있다. Expo 같은 도구가 빌드와 OTA를 단순화한다.
- Kotlin Multiplatform: 도메인·데이터 로직을 공유하고 UI는 네이티브로 두는 선택이 가능하다. Compose Multiplatform으로 UI 공유도 넓어지는 추세다. iOS 팀의 Kotlin 수용도가 관건이다.
- Electron: 크로미움과 Node를 번들한다. 개발 속도가 빠르고 웹 자산을 재사용할 수 있지만, 크기와 메모리가 크고 보안 설정(컨텍스트 격리, 노드 통합 비활성)을 직접 책임져야 한다.
- Tauri: OS 웹뷰 + Rust 백엔드다. 가볍지만 OS별 웹뷰 엔진 차이로 렌더링·API 호환을 테스트해야 한다.

**판단 규칙**
- 위젯, 워치, 확장, 백그라운드 위치, 카메라 고급 처리, AR, 결제 등 플랫폼 깊숙한 기능 비중이 크면 네이티브나 KMP 쪽으로 기운다.
- 콘텐츠·폼 위주이고 빠른 동시 출시가 중요하면 크로스플랫폼 UI가 유리하다.
- 기존 앱이 있으면 전면 재작성보다 점진 도입(모듈 단위 임베드)을 먼저 검토한다.
- 비용 추정에 넣을 항목:
  - 프레임워크 메이저 업그레이드 주기와 서드파티 플러그인 방치 위험.
  - 크래시 스택이 여러 언어에 걸칠 때의 디버깅 비용.
  - 채용 시장.

**흔한 오해**
- "코드 공유 90%면 비용 절반": 플랫폼별 엣지 케이스, 스토어, 권한, 테스트는 여전히 두 배다.
- "크로스플랫폼은 느리다": 대부분은 프레임워크가 아니라 앱 코드(과도한 리빌드, 큰 이미지, 메인 스레드 작업)가 원인이다.

## 성능·메모리·전력 최적화

**핵심 개념과 원리**
- 측정 없이 최적화하지 않는다. 지표는 사용자 체감 기준으로 정의한다.
  - 시작 시간(콜드·웜·핫 구분, 첫 프레임과 첫 의미 있는 콘텐츠까지).
  - 프레임 드랍·지연(주사율에 따라 프레임 예산이 달라지므로 고정 수치를 가정하지 않는다).
  - 메모리 피크와 누수, OOM 및 백그라운드 강제 종료율.
  - 배터리·발열·네트워크 바이트.
- 개발 기기 측정과 현장 측정은 다르다. 저사양 기기, 발열 스로틀링, 저전력 모드, 느린 네트워크에서 차이가 크므로 **현장 텔레메트리**가 필수다.

**도구 예시**
- Android: Android Studio Profiler, Perfetto 트레이스, Macrobenchmark, Baseline Profile, StrictMode, LeakCanary, Play Console의 Android vitals.
- iOS: Instruments(Time Profiler, Allocations, Leaks, Energy), MetricKit, Xcode Organizer.
- 데스크톱/웹뷰: 플랫폼 프로파일러와 크로미움 DevTools.

**최적화 과정**
- 재현 가능한 시나리오를 정한다.
- 기준선을 측정하고 트레이스로 병목을 찾는다.
- 하나만 바꾼 뒤 재측정한다.
- CI 벤치마크로 회귀를 막는다.

**대표 처방**
- 시작 시간: 시작 경로의 동기 초기화(SDK, DI 그래프, 디스크 I/O)를 지연시키거나 병렬화한다. 사전 컴파일 프로파일을 적용한다.
- 렌더링: 메인 스레드의 I/O와 파싱을 제거하고, 리스트 재활용, 오버드로우·레이아웃 패스·불필요한 재구성을 줄인다.
- 메모리
  - 이미지를 표시 크기로 디코딩한다.
  - 생명주기를 넘는 참조(리스너, 클로저 순환, 정적 컨텍스트)를 끊는다.
  - 캐시에 상한을 둔다.
  - 메모리 경고에 응답한다.
- 전력
  - 웨이크업 횟수를 줄이고 네트워크를 배치 처리한다.
  - 위치 정확도와 빈도를 낮춘다.
  - 폴링 대신 푸시를 쓴다. 라디오를 한 번 깨우는 비용이 크다.

**흔한 오해**
- "메모리가 넉넉한 기기니 괜찮다": OS별 앱당 한도와 백그라운드 축출 기준은 기기 RAM과 정비례하지 않는다.
- "평균이 좋으면 된다": p90·p99와 저사양 군을 봐야 한다.
- "Debug 빌드로 측정": 최적화가 꺼져 있어 결론이 틀린다. 릴리스 구성으로 측정한다.

## 권한 모델과 개인정보 보호

**핵심 개념과 원리**
- 권한은 기술 장치이자 신뢰 장치다. 거절당한 권한은 다시 묻기 어렵다(시스템 대화상자 재노출 제한).
- 그래서 권한은 **필요한 순간, 맥락과 함께** 요청한다. 사전 설명 화면을 두되 그것이 시스템 요청을 강요하는 패턴이 되면 안 된다.
- 최소화 원칙
  - 기능에 필요한 가장 좁은 범위를 고른다(대략적 위치, 사용 중에만 허용, 선택한 사진만 접근).
  - 시스템 피커(사진·파일·연락처 피커)로 권한 자체를 피할 수 있으면 피한다.
  - 거절 시에도 기능이 축소된 채 동작해야 한다.
- 추적
  - iOS의 ATT는 다른 회사 앱·웹과 데이터를 연결하는 "추적"에 동의를 요구한다. 거절 시 광고 식별자는 무의미해진다.
  - 핑거프린팅 같은 우회는 정책 위반이다.
  - SDK가 수집하는 데이터도 앱 책임이다.
- 보안 저장소
  - 토큰·키는 Keychain이나 Android Keystore 기반 암호화로 보관한다. 일반 설정 저장소(UserDefaults, SharedPreferences)에 두지 않는다.
  - 하드웨어 기반 키, 생체 인증 바인딩, 백업·기기 이전 시 동작(접근성 클래스, 백업 제외)을 결정한다.
  - 클라이언트에 넣은 비밀은 결국 추출 가능하다고 가정한다. 진짜 비밀은 서버에 둔다.
- 개인정보 선언
  - 스토어의 개인정보 라벨, 데이터 안전 섹션, 개인정보 매니페스트, 필수 사유 API 선언 같은 요구가 계속 늘고 있다. 실제 수집과 불일치하면 거절이나 제재 사유가 된다.
  - 규제(GDPR, 각국 개인정보법, 아동 보호법 등)는 동의의 적법 근거, 목적 제한, 삭제권, 국외 이전을 요구한다. 계정 생성이 있는 앱은 앱 내 계정 삭제 경로를 요구받는 추세다.

**판단 규칙**
- 새 SDK를 넣을 때는 먼저 데이터 흐름(무엇을, 어디로, 동의 전에 전송하는지)을 감사한다.
- 동의 전 초기화를 막는다.
- 법적 판단은 단정하지 말고 법무 확인 항목으로 분리한다.

**흔한 오해**
- "권한 거절은 드문 경우": 거절 경로는 주 경로로 설계해야 한다.
- "HTTPS면 안전": 로컬 저장, 로그, 크래시 리포트, 클립보드, 스크린샷을 통한 유출을 따로 점검해야 한다.

## 빌드·서명·배포 파이프라인

**핵심 개념과 원리**
- 서명은 "누가 만들었고 변조되지 않았는가"의 증명이다. 키를 잃거나 유출하면 업데이트 연속성과 신뢰가 무너진다.
- Android
  - 업로드 키와 앱 서명 키가 분리된다(Play 앱 서명).
  - 앱 서명 키를 분실하면 같은 패키지로 업데이트할 수 없는 상황이 생길 수 있으므로 보관·백업 체계를 문서화한다.
- iOS
  - 인증서 + 앱 ID + 엔타이틀먼트 + 프로비저닝 프로파일의 조합이다. 만료와 기기 등록이 잦은 장애 원인이다.
  - 팀 단위로 서명 자산을 중앙 관리한다(예: fastlane match, 클라우드 서명).
- 데스크톱
  - macOS는 개발자 ID 서명, 하드닝된 런타임, 공증(notarization)이 없으면 Gatekeeper가 경고하거나 차단한다. 스테이플링은 필수가 아니다. 공증만 되어 있으면 Gatekeeper가 온라인으로 공증 티켓을 확인하므로, 스테이플링이 없을 때 문제가 되는 것은 오프라인 상황뿐이다.
  - Windows는 코드 서명 인증서와 SmartScreen 평판이 설치 경험을 좌우한다. 인증서 발급 요건(하드웨어 보관 등)은 변동이 잦으니 확인한다.
  - 패키징 형식 예: DMG/PKG, MSI/MSIX, AppImage/Flatpak/Snap.

**빌드 변형과 재현성**
- 빌드 타입(debug·release)과 플레이버·스킴(dev·staging·prod)을 나눠 엔드포인트, 앱 ID, 아이콘을 분리한다. 그래야 테스트 빌드와 운영 빌드가 같은 기기에 공존한다.
- 재현 가능한 산출물을 위해 할 일:
  - 도구체인 버전(SDK, Xcode, JDK, Node)을 고정하고 의존성 잠금 파일을 쓴다.
  - 빌드 번호를 자동 증가시킨다.
  - 비밀은 CI 비밀 저장소에서 주입하고 저장소에는 두지 않는다.
  - 심볼 파일(dSYM, 매핑 파일)을 산출물과 함께 보관한다.
- CI/CD 흐름: PR 검증(린트·테스트), 메인 브랜치 내부 배포, 태그 기반 스토어 업로드. iOS는 macOS 러너가 필요해 비용과 대기열이 병목이 된다.

**흔한 오해**
- "로컬에서 서명해 올리면 충분": 담당자 퇴사, 기기 교체, 인증서 만료 때 출시가 멈춘다.
- "난독화가 보안": 분석을 늦출 뿐이다. 그리고 매핑 파일을 보관하지 않으면 크래시를 읽을 수 없게 된다.

## 스토어 심사와 업데이트 전략

**핵심 개념과 원리**
- 심사는 기술 검증이 아니라 정책 준수 검증이다. 자주 걸리는 영역은 다음과 같다.
  - 디지털 재화의 인앱 결제 의무와 외부 결제 안내 규정(지역별로 변동).
  - 로그인 요구, 계정 삭제, 리뷰용 데모 계정 제공.
  - 메타데이터와 실제 기능의 불일치, 미완성·크래시.
  - 권한 사용 사유 부족, 사용자 생성 콘텐츠의 신고·차단 기능.
  - 원격으로 앱의 성격을 바꾸는 행위.
- 거절 대응
  - 지적 조항을 정확히 인용해 수정하고, 해명이 필요하면 근거와 함께 회신한다.
  - 반복 거절이 예상되는 기능은 출시 일정과 분리한다(피처 플래그로 끈 채 제출하되, 심사 회피 목적의 숨김은 위반이 될 수 있다).
  - 심사 소요 시간은 변동하므로 일정에 여유를 둔다.
- Google Play의 대상 API 레벨 요구는 해마다 올라가는 경향이 있다. 정책 미준수 앱은 노출이 제한될 수 있다.

**업데이트 전략**
- 단계적 출시: 비율을 점진적으로 올리며 지표를 본다. 중단은 가능하지만 이미 설치된 사용자에게서 바이너리를 회수할 수는 없다.
- 강제 업데이트: 서버가 최소 지원 버전을 내려주고 앱이 시작 시 확인한다. Android에는 인앱 업데이트 API가 있다. 이 장치는 **1.0부터** 넣어야 한다. 나중에 넣으면 이미 깔린 구버전에는 그 장치가 없다.
- 선택 업데이트: 권유만 하고 차단하지 않는다.
- OTA
  - JS 번들(React Native 계열)이나 웹 콘텐츠 교체는 정책상 "앱의 주 목적을 바꾸지 않는 수정"에 한정된다.
  - 네이티브 코드는 OTA로 바꿀 수 없다. 번들과 네이티브 버전의 호환성을 관리해야 한다.
- 데스크톱 자동 업데이트: 서명된 업데이트 피드, 서명 검증, 델타 업데이트, 업데이트 실패 시 복구 경로가 필요하다.
- 구버전 호환
  - 모바일은 사용자가 업데이트하지 않는다는 전제로 간다. 다수 버전이 동시에 서버를 호출한다.
  - API는 버전을 붙이고 하위 호환을 유지한다(필드 추가는 허용, 의미 변경과 삭제는 금지).
  - 지원 종료 정책을 정하고 버전별 트래픽을 모니터링한다.

**흔한 오해**
- "버그는 서버나 OTA로 바로 고친다": 네이티브 버그는 심사와 업데이트 보급 속도에 묶인다.
- "심사 통과 = 정책 준수 확정": 출시 후 재검토로 제재될 수 있다.

## 크래시 분석과 출시 품질 관리

**핵심 개념과 원리**
- 수집
  - 크래시 SDK(예: Firebase Crashlytics, Sentry)와 스토어 콘솔을 병행한다.
  - ANR(Android 메인 스레드 장시간 차단)과 iOS 행·워치독 종료는 일반 크래시와 별개 지표다.
  - OOM과 백그라운드 강제 종료는 SDK가 잘 잡지 못하므로 OS 리포트(MetricKit, 종료 사유 API)를 활용한다.
- 심볼리케이션: iOS와 네이티브(C/C++) 코드의 릴리스 빌드는 주소만 남긴다. Android Java/Kotlin 릴리스 빌드는 R8/ProGuard로 축소하면 난독화된 클래스·메서드 이름이 남고, 축소를 끄면 원래 이름이 그대로 남는다. 빌드마다 dSYM, R8/ProGuard 매핑, 네이티브 심볼, JS 소스맵을 업로드해 자동화해야 스택을 읽을 수 있다. 누락은 사후에 복구하기 어렵다.
- 지표
  - 크래시 프리 사용자 비율과 세션 비율을 구분한다. 버전·기기·OS별로 쪼갠다.
  - 신규 크래시와 회귀를 분리한다. 비치명 오류와 브레드크럼으로 맥락을 남긴다.
  - 목표치는 앱 성격과 업계 관행에 따라 정한다. 스토어의 "불량 행동" 임계치는 노출에 영향을 줄 수 있다.

**출시 게이트와 피처 플래그**
- 게이트: 내부·베타 트랙 → 단계적 출시 각 단계에서 크래시율, ANR, 핵심 퍼널, 성능 지표가 기준선 이내인지 확인한다. 자동 정지 조건을 둔다.
- 피처 플래그
  - 배포와 출시를 분리하고, 바이너리를 다시 내지 않고 기능을 끄는 킬 스위치를 제공한다.
  - 플래그 서버가 불통일 때의 기본값과 로컬 캐시를 정한다.
  - 수명을 관리해 오래된 플래그를 제거한다. 남겨 두면 조합 폭발로 테스트가 불가능해진다.

**롤백·핫픽스 판단**
- 이미 설치된 기기의 네이티브 바이너리는 원격으로 되돌릴 수 없다. "롤백"은 이전 코드로 새 버전을 다시 내거나, 원격 플래그로 기능을 끄는 것이다.
- 대응 순서:
  1. 단계적 출시를 중단한다.
  2. 플래그로 원인 기능을 끈다.
  3. 서버 측에서 완화한다.
  4. 핫픽스 빌드를 만들고(필요하면 신속 심사를 요청) 직전 안정 코드를 더 높은 버전 번호로 재제출한다.
- 영향 범위(사용자 비율 × 심각도: 데이터 손실·결제·보안은 최우선)로 결정한다.

**사후 분석**
- 비난 없는 회고로 다음을 기록한다: 타임라인, 탐지 경로와 소요 시간, 근본 원인, 왜 게이트가 못 잡았는지.
- 재발 방지 조치(테스트, 모니터, 게이트 기준)를 담당자와 기한과 함께 남긴다.

**흔한 오해**
- "크래시 0이면 안정": 행, ANR, OOM, 조용한 데이터 손상은 크래시 리포트에 안 잡힌다.
- "베타에서 문제없었다": 베타 표본은 기기·지역·사용 패턴이 편향되어 있다.

## 지시 검토 시 교차 점검 질문

- 먼저 대상이 모바일·스토어 배포 앱인지, 데스크톱이나 사내 배포 앱인지 가른다. 아래 질문은 해당하는 것만 쓴다.

- 이 기능은 앱이 죽었다 살아나도, 오프라인이어도, 권한이 거절되어도 성립하는가?
- 구버전 앱이 계속 존재할 때 서버 변경은 안전한가? 강제 업데이트 장치는 이미 배포돼 있는가?
- 플랫폼 정책(백그라운드, 결제, 추적, 개인정보 선언)에 걸리는 지점이 있는가? 최신 가이드라인을 확인했는가?
- 측정 지표, 출시 게이트, 끄는 수단(플래그), 심볼 업로드가 설계에 포함됐는가?
- 서명 키, 인증서, 비밀의 보관 주체와 만료 일정이 사람이 아니라 체계에 묶여 있는가?

## 더 짚을 것 (검토 보강)

- **딥링크:** Universal Links·App Links는 도메인 쪽 검증 파일이 있어야 동작한다. 앱이 꺼진 상태(콜드 스타트)와 백그라운드(웜 스타트) 모두에서 같은 화면으로 가는지, 로그인이 필요한 화면이면 로그인 뒤 원래 목적지로 돌아가는지 확인한다. OAuth 로그인은 인앱 웹뷰가 아니라 시스템 브라우저 세션(ASWebAuthenticationSession, Custom Tabs)과 PKCE로 한다. 웹뷰 로그인을 막는 제공자가 있다.
- **푸시 알림:** 토큰은 바뀔 수 있으므로 갱신될 때마다 서버에 다시 등록한다. 사용자와 기기는 다대다이고, 로그아웃하면 그 기기의 토큰을 해제한다. 전달은 보장되지 않으므로 중요한 상태는 앱이 열릴 때 서버에서 다시 읽는다. Android의 알림 채널과 Android 13 이상의 알림 권한, 알림 피로도 설계에 넣는다.
- **모바일 접근성:** VoiceOver·TalkBack용 레이블, 글꼴 크기 확대(Dynamic Type, sp 단위)에서 레이아웃이 깨지지 않는지, 터치 영역 최소 크기(대략 iOS 44pt, Android 48dp), 색만으로 정보를 전하지 않는지 본다.

# 게임 개발 어드바이저 지식

이 문서는 사용자의 지시에서 잘못된 전제와 빠진 고려를 찾아내는 데 쓴다. 각 영역은 세 부분으로 되어 있다. 자주 보는 실패와 그 근본 원인, 징후에서 진단을 거쳐 조치로 가는 순서, 그리고 리뷰·설계 점검표다. 수치는 감을 잡기 위한 예시다. 플랫폼, 엔진, 장르에 따라 달라지므로 실제 측정값으로 대체해야 한다.

## 게임 루프와 프레임 시간 관리

**핵심 원리.** 시뮬레이션은 고정 간격(예: 1/60초)으로 진행하고, 렌더는 가능한 빈도로 그린다. 남은 누적 시간의 비율(alpha)로 이전 상태와 현재 상태를 보간한다. 결정성은 같은 입력과 같은 dt, 같은 연산 순서에서 나온다. 가변 dt를 물리나 게임 규칙에 직접 넣으면 프레임레이트가 결과를 바꾼다.

**자주 보는 실패**
- **가변 dt를 그대로 적분.** 점프 높이, 마찰, 쿨다운이 FPS에 따라 달라진다. `velocity *= 0.9`처럼 dt 없이 쓴 감쇠도 같은 문제를 일으킨다. 지수 감쇠는 `pow(k, dt)` 형태로 써야 한다.
- **죽음의 나선.** 한 프레임이 느려지면 다음 프레임에서 고정 스텝을 여러 번 돌리고, 그만큼 또 느려진다. 누적 시간 상한이나 최대 스텝 수가 없어서 생긴다.
- **보간 없는 고정 스텝.** 144Hz 모니터에서 60Hz 시뮬레이션이 떨린다. 렌더가 최신 상태만 보기 때문이다.
- **외삽 남용.** 충돌 직전에 물체가 벽을 넘어 보였다가 돌아온다. 외삽은 예측일 뿐이다.
- **프레임 페이싱 불균일.** 평균 FPS는 60인데 끊겨 보인다. 프레임 간격이 16/33ms로 번갈아 나오기 때문이다. 더블 버퍼링 vsync에서는 예산을 살짝 넘기면 반토막 프레임레이트로 떨어진다. 트리플 버퍼링, 가변 주사율(VRR), 적응형 vsync에서는 이렇게 고정되지 않으므로 어떤 표시 방식인지 먼저 확인한다.
- **시간 소스 혼용.** 벽시계, 게임 시간, 일시정지 시간, 슬로모션 배율이 섞여 있다. 그 결과 타이머가 일시정지 중에도 흐르거나 히트스톱 중에도 흐른다.

**징후→진단→조치**
- "고FPS에서 캐릭터가 더 높이 뛴다" → 적분에 쓰인 dt의 출처를 추적한다 → 고정 스텝으로 옮기거나 dt를 일관되게 적용한다.
- "가끔 멈칫한다" → 평균이 아니라 프레임 시간 그래프의 분포를 본다(백분위, 최악값) → GC, 셰이더 컴파일, 동기 로딩, 에셋 스트리밍 스파이크를 찾는다.
- "느린 기기에서 게임이 슬로모션이 된다" → 스텝 상한이 시뮬레이션 시간을 버리고 있는지 확인한다 → 기획이 허용하는 손실 방식인지 결정하고, 아니면 부하 자체를 줄인다.

- [ ] 렌더 보간에 쓰는 이전 상태를 보관하는가? 순간이동 시 보간을 끊는가?
- [ ] 시간 종류(실시간, 게임 시간, UI 시간)를 구분하는가?
- [ ] 프레임 예산이 목표 FPS별로 CPU·GPU 각각 할당되어 있는가?

## 렌더링 파이프라인

**핵심 원리.** 처리 순서는 CPU의 씬 준비(컬링, 정렬, 커맨드 생성)에서 시작해 GPU의 정점 처리, 래스터화, 픽셀 셰이딩, 출력 병합으로 이어진다. 비용은 대략 세 축으로 나뉜다. 첫째는 드로우콜과 상태 변경, 즉 CPU와 드라이버 비용이다. 둘째는 정점 수, 셋째는 픽셀 수×셰이더 복잡도×오버드로우, 그리고 대역폭이다. 포워드는 광원 수에 비례해 픽셀 비용이 늘고, MSAA와 투명 처리가 쉽다. 디퍼드는 다수 광원에 강하지만, G-버퍼 대역폭이 크고 투명·MSAA·재질 다양성에서 불리하다. 타일·클러스터 방식은 그 중간을 노린다.

**자주 보는 실패**
- **병목을 확인하지 않고 폴리곤부터 줄인다.** 실제 병목은 픽셀 필레이트나 드로우콜인 경우가 많다.
- **재질 변종 폭증으로 배칭이 깨진다.** 인스턴싱, 아틀라스, 재질 공유를 고려하지 않고 아트를 제작했기 때문이다.
- **셰이더 변종 폭발.** 키워드 조합이 늘어나 빌드 시간과 메모리가 불어나고, 런타임 첫 사용 시 컴파일 끊김이 생긴다.
- **투명 오버드로우.** 파티클, UI, 풀(foliage)이 화면을 여러 겹 덮는다. 모바일에서 특히 치명적이다.
- **그림자 비용 과소평가.** 광원마다 씬을 다시 그린다. 캐스케이드 수, 해상도, 그림자를 드리우는 오브젝트 범위가 제한되어 있지 않다.
- **LOD 부재 또는 팝핑.** 원거리 오브젝트가 풀 디테일로 그려지거나, 전환 거리가 눈에 띈다.
- **후처리 누적.** 블룸, DOF, SSAO, 모션블러가 각각 전체 해상도 패스로 돈다. 해상도 스케일링을 고려하지 않았다.

**징후→진단→조치**
- 해상도를 낮췄을 때 빨라진다 → 픽셀 측 병목이다 → 오버드로우, 셰이더 비용, 후처리 해상도를 줄인다.
- 해상도와 무관하고 오브젝트 수에 비례한다 → CPU 렌더 스레드, 게임 스레드(로직), GPU 정점 처리 중 어디인지 스레드별 시간과 GPU 캡처로 가른다 → 렌더 스레드면 컬링, 배칭, 인스턴싱, 정적 병합, 정점 처리면 LOD와 정점 셰이더 단순화, 로직이면 업데이트 비용과 빈도를 줄인다.
- 특정 시점에만 스파이크가 생긴다 → 해당 프레임을 캡처해 원인을 확인한다(셰이더·파이프라인 상태 생성, 텍스처 업로드, GC, 동기 로딩, 에셋 스트리밍 등) → 셰이더·업로드면 프리워밍과 캐시, GC면 할당 감소, 로딩이면 비동기화와 사전 로드로 대응한다.
- GPU 캡처 도구로 패스별 시간을 확인하기 전에는 결론 내리지 않는다.

**점검표**

- [ ] 프러스텀 컬링과 오클루전 컬링, LOD와 임포스터 전략이 있는가?
- [ ] 투명 레이어 수와 파티클 화면 점유 상한이 있는가?
- [ ] 셰이더 변종 수를 측정하고 있는가? 프리워밍 계획이 있는가?

## 물리 시뮬레이션과 충돌 처리

**핵심 원리.** 게임 물리는 보통 반암시적(심플렉틱) 오일러로 적분한다. 속도를 먼저 갱신하고 그 속도로 위치를 갱신하는 방식으로, 명시적 오일러보다 에너지가 덜 폭주한다. 충돌 검출은 두 단계로 나뉜다. 브로드페이즈(AABB와 공간 분할, 정렬·스윕, BVH)로 후보 쌍을 줄이고, 내로우페이즈(GJK/EPA, SAT 등)로 접촉점을 구한다. 응답은 제약 해결기가 반복적으로 맞춘다. 반복 횟수, 스텝 크기, 질량비가 안정성을 결정한다.

**자주 보는 실패**
- **터널링.** 빠른 총알이 얇은 벽을 통과한다. 한 스텝의 이동량이 물체 두께보다 크기 때문이다. 이때는 CCD, 레이·셰이프 캐스트, 서브스텝을 쓴다. 총알은 강체 대신 히트스캔이나 레이캐스트로 처리하는 것이 보통 맞다.
- **떨림과 폭발.** 쌓인 상자가 진동한다. 원인은 질량비 극단(예: 1:1000), 스텝이 너무 큼, 반복 수 부족, 겹친 상태로 스폰, 큰 페널티 보정이다.
- **트랜스폼 직접 조작.** 물리 바디의 위치를 코드로 매 프레임 덮어써서 속도 정보가 사라지고 충돌 응답이 깨진다. 키네매틱 바디로 지정하거나 힘·속도로 제어해야 한다.
- **스케일 단위 불일치.** 1유닛=1cm로 만들고 기본 중력과 허용오차는 미터 기준으로 둔다. 슬립(sleep) 임계값과 접촉 오프셋이 맞지 않게 된다.
- **캐릭터 컨트롤러를 강체로 만든다.** 경사, 계단, 모서리에 끼이는 문제가 생긴다. 조작감이 중요한 캐릭터는 보통 커스텀 키네매틱 컨트롤러가 낫다.
- **물리 결정성 가정.** 같은 엔진이라도 플랫폼, 컴파일러, 스레드 수에 따라 결과가 달라질 수 있다. 엔진 문서가 결정성을 명시하지 않으면 보장되지 않는다고 본다.

**징후→진단→조치**
- 가끔 벽을 뚫는다 → 최대 속도×dt와 콜라이더 두께를 비교한다 → CCD를 켜거나, 콜라이더를 두껍게 하거나, 속도에 상한을 둔다.
- 정지해야 할 물체가 미세하게 움직인다 → 슬립 설정, 반복 수, 질량비, 초기 겹침을 확인한다.
- 물체가 많을 때 프레임이 급락한다 → 브로드페이즈 쌍 수와 활성 바디 수를 계측한다 → 충돌 레이어 매트릭스를 정리하고 슬립과 단순 콜라이더로 대체한다.

**점검표**

- [ ] 충돌 레이어와 마스크 매트릭스가 문서화되어 있는가?

## 엔티티 아키텍처와 데이터 지향 설계

**핵심 원리.** 상속 계층은 "is-a" 분류가 고정된 동안만 잘 작동한다. 게임 객체는 기능 조합이 계속 바뀌므로 깊은 계층은 다이아몬드 상속이나 비대한 기반 클래스로 무너진다. 컴포넌트 구조는 조합으로 이 문제를 푼다. ECS는 여기에 데이터를 같은 타입끼리 연속 배치(SoA, 아키타입·청크)하고, 시스템이 이를 순회하게 만든다. 이점은 캐시 효율, 병렬화, 직렬화 용이성이다. 대가는 관계형 데이터(계층 구조, 그래프) 표현의 불편함, 구조 변경 비용, 그리고 팀의 학습 비용이다.

**자주 보는 실패**
- **ECS를 이유 없이 도입.** 엔티티 수천 개 미만, 로직 위주의 게임에서 성능 이득 없이 복잡도만 늘어난다. 성능 문제가 측정된 곳에만 데이터 지향 설계를 국소 적용하는 것도 선택지다.
- **실행 순서 미정의.** 이동 시스템과 카메라 시스템의 순서가 프레임마다 다르거나, 등록 순서에 암묵적으로 기대고 있다. 1프레임 지연과 떨림이 생긴다.
- **순회 중 생성·삭제.** 컬렉션이 무효화되거나 엔티티가 반쯤 파괴된 상태가 된다. 구조 변경을 명령 버퍼에 쌓아 두었다가 프레임의 정해진 지점에서 반영해야 한다.
- **댕글링 참조.** 파괴된 엔티티의 ID를 재사용해서 엉뚱한 대상을 가리킨다. 세대(generation) 카운터를 포함한 핸들이 필요하다.
- **이벤트 스파게티.** 전역 이벤트 버스에서 발신자와 수신자를 추적할 수 없다. 재귀 이벤트와 처리 순서 의존이 생긴다.
- **포인터 추적 구조.** 객체마다 힙에 할당하고 가상 호출로 업데이트한다. 프로파일러에는 캐시 미스가 핫스팟으로 보인다.

**징후→진단→조치**
- "가끔 한 프레임 늦게 반응한다" → 시스템 순서 그래프를 출력해 데이터 생산자와 소비자의 순서를 확인한다.
- "파괴 후 크래시"나 "엉뚱한 대상 피격" → 핸들 검증과 지연 파괴 지점을 확인한다.
- 업데이트 루프가 느리다 → 메모리 접근 패턴을 확인한다. 핫 데이터와 콜드 데이터를 분리하고 연속 배열로 바꾼다.

- [ ] 시스템 실행 단계(입력→로직→물리→후처리→렌더 준비)가 명시되어 있는가?
- [ ] 엔티티 참조가 세대 포함 핸들인가? 생성·파괴 반영 시점이 정해져 있는가?
- [ ] 이벤트는 즉시 처리인가 큐 처리인가? 순서와 재진입 규칙이 있는가?
- [ ] 저장·로드, 네트워크 복제에 필요한 상태가 직렬화 가능한 데이터로 분리되어 있는가?

## 입력 처리와 조작감

**핵심 원리.** 체감 지연은 여러 구간의 합이다. 입력 장치, OS, 폴링 시점, 시뮬레이션 반영, 렌더 큐잉, 디스플레이 스캔아웃까지가 모두 더해진다. 렌더 큐에 프레임이 여러 장 쌓이면 FPS가 높아도 지연이 크다. 조작감은 반응 속도와 관용 장치, 피드백으로 만든다. 사람의 의도를 받아주는 장치가 정밀 판정보다 중요한 경우가 많다.

**자주 보는 실패**
- **입력을 렌더 프레임에서만 읽고 고정 스텝에서 소비.** 한 프레임에 고정 스텝이 0번 돌면 눌림 엣지("이번 틱에 눌림")가 사라지고, 2번 돌면 두 번 처리된다. 엣지 입력은 틱 단위로 래치해야 한다.
- **관용 장치 부재.** 착지 직전 점프 입력이 무시되거나, 낭떠러지에서 한 프레임 늦은 점프가 실패한다. 입력 버퍼(예: 수 프레임에서 100ms 안팎)와 코요테 타임이 필요하다. 수치는 플레이테스트로 정한다.
- **애니메이션이 조작을 잠근다.** 루트모션과 긴 선딜레이 때문에 입력이 씹히는 느낌이 든다. 캔슬 윈도우와 블렌딩 우선순위가 정의되어 있지 않다.
- **카메라 지연과 과잉 스무딩.** 따라가기 감쇠가 너무 강해 캐릭터보다 늦게 반응하고 멀미를 유발한다. 감쇠가 프레임 의존이면 FPS에 따라 느낌이 달라진다.
- **피드백 과잉.** 히트스톱, 흔들림, 플래시가 모든 타격에 같은 강도로 들어가서 의미가 희석되고 피로해진다. 접근성 옵션(흔들림 끄기)도 빠져 있다.
- **데드존과 응답 곡선 미조정.** 스틱 드리프트나 미세 조준이 어렵다. 방사형 데드존과 비선형 곡선을 검토해야 한다.

**징후→진단→조치**
- "조작이 무겁다" → 지연 구간을 측정한다(고속 촬영이나 엔진 지연 지표) → 렌더 큐 깊이를 줄이고, 입력 샘플링 시점을 늦추고, 선딜레이를 줄인다.
- "점프가 가끔 안 된다" → 입력 로그와 틱 로그를 대조해 엣지 유실이나 판정 윈도우 문제를 찾는다.
- "타격감이 없다" → 히트스톱, 사운드, 이펙트, 넉백, 카메라 반응의 타이밍을 프레임 단위로 검토한다.

**점검표**
- [ ] 입력은 액션 매핑 계층을 거치는가? 리바인딩과 다중 장치를 지원하는가?
- [ ] 엣지 입력을 고정 틱에 안전하게 전달하는가?
- [ ] 버퍼, 코요테 타임, 캔슬 윈도우의 값이 데이터로 노출되어 튜닝 가능한가?
- [ ] 피드백 강도가 사건 중요도에 비례하는가? 끌 수 있는가?
- [ ] 히트스톱을 전역 시간으로 멈추는지, 공격자·피격자만 멈추는지(로컬 시간 배율) 정했는가? 입력·UI·사운드가 함께 멈추지 않는가? 네트워크 게임에서 히트스톱이 상태에 미치는 영향을 정의했는가?

## 네트워크 멀티플레이와 동기화

**핵심 원리.** 권위 서버 모델에서는 서버가 진실이다. 클라이언트는 자기 입력을 예측 실행하고, 서버 상태가 오면 그 시점으로 되감아 미확인 입력을 재적용해 재조정한다. 다른 엔티티는 약간 과거의 스냅샷 사이를 보간해 보여준다. 지연 보상은 서버가 사격 시점의 과거 위치로 판정을 되감는 것이다. 락스텝은 입력만 교환해 대역폭이 작지만, 완전한 결정성과 가장 느린 참가자에 대한 대기가 필요하다. 롤백(GGPO류)은 입력을 예측하고 틀리면 되돌린다. 이 역시 결정성과 빠른 재시뮬레이션이 전제다.

**자주 보는 실패**
- **"나중에 멀티 붙이자".** 싱글플레이 구조에 사후 이식을 시도한다. 상태 소유권, 결정성, 입력 분리가 없어 사실상 재작성이 된다. 멀티 여부는 프리프로덕션에서 결정해야 한다.
- **클라이언트 권위.** 위치, 피해량, 아이템 획득을 클라이언트가 보고하면 치트가 바로 가능해진다. 서버 검증과 "입력만 신뢰" 원칙을 지켜야 한다.
- **재조정 시 튐.** 예측과 서버 결과가 계속 어긋나 고무줄 현상이 생긴다. 원인은 여러 가지다. 클라이언트와 서버의 시뮬레이션 코드나 틱이 다르거나 비결정 요소가 들어 있을 수 있다. 다른 플레이어의 밀기나 서버만 아는 이벤트처럼 클라이언트가 예측할 수 없는 상호작용일 수도 있고, 패킷 손실로 입력이 유실된 경우일 수도 있다.
- **보간 버퍼 부족.** 패킷 지터 때문에 원격 캐릭터가 끊긴다. 버퍼는 지터를 덮을 만큼 커야 하며, 그만큼 표시 지연이 생긴다는 트레이드오프를 이해해야 한다.
- **지연 보상의 반대급부 무시.** 고지연 플레이어가 쏘면 저지연 플레이어는 "벽 뒤에서 맞았다"고 느낀다. 되감기 상한이 필요하다.
- **대역폭 폭주.** 모든 엔티티를 매 틱 전체 상태로 전송한다. 관심 영역(AOI), 델타 압축, 양자화, 우선순위·빈도 조절이 빠졌다.
- **실네트워크 조건에서 테스트 안 함.** 로컬 0ms에서만 확인한다. 지연, 손실, 지터 시뮬레이션이 필수다.

**징후→진단→조치**
- 고무줄 현상 → 재조정 빈도와 오차 크기를 로깅하고, 오차가 다른 엔티티와의 상호작용이나 입력 유실 시점과 겹치는지 본다 → 예측 경로의 코드 차이와 비결정 요소를 제거하고, 입력 중복 전송 등으로 유실에 대비하고, 작은 오차는 시각적으로 부드럽게 보정한다.
- 락스텝 디싱크 → 틱마다 상태 해시를 교환해 최초 불일치 틱을 찾는다 → 부동소수점, 컨테이너 순회, 난수 시드, 시간 의존 코드를 점검한다.
- 대역폭 초과 → 메시지 종류별 바이트를 계측한다 → AOI와 갱신 빈도를 차등화한다.

**점검표**
- [ ] 장르에 맞는 모델을 선택했고 그 근거가 있는가(격투=롤백, RTS=락스텝, 슈터=권위 서버+예측 등은 출발점일 뿐이다)?
- [ ] 무엇을 예측하고 무엇을 서버 확인 후 보여주는가(사망, 아이템, 경제)?
- [ ] 히트 판정 방식과 되감기 상한이 정의되어 있는가?
- [ ] 지연·손실 시뮬레이터로 CI 또는 정기 테스트를 하는가?
- [ ] 서버 비용(틱레이트×인원×방 수)과 운영 계획(매치메이킹, NAT, 재접속)이 있는가?
- [ ] 치트 위협 모델(속도핵, 월핵, 패킷 변조)과 각각의 서버측 방어가 있는가? 월핵은 보이지 않는 정보를 보내지 않는 것이 근본 대책이다.

## 게임 디자인 원칙과 밸런스

**핵심 원리.** 핵심 루프(행동→보상→성장→더 큰 행동)가 그 자체로 재미있어야 상위 루프가 의미를 갖는다. "30초의 재미"는 Halo 개발 일화에서 나온 경험칙일 뿐이다. 루프의 적절한 길이는 장르마다 크게 다르다(퍼즐, 전략, 시뮬레이션 등). 몰입은 도전과 숙련의 균형에서 생기며, 난이도는 긴장과 이완을 반복하는 톱니 형태가 단조 상승보다 낫다. 경제는 획득처(source)와 소모처(sink)의 균형이다. 밸런스의 목표는 모든 선택지가 "맥락에 따라" 의미 있는 상태다.

**자주 보는 실패**
- **핵심 루프 검증 전에 콘텐츠를 양산.** 레벨, 스토리, 메타 시스템을 쌓았는데 기본 조작이 재미없다. 그레이박스 프로토타입으로 먼저 검증해야 한다.
- **보상으로 재미를 대체.** 출석, 일일 퀘스트, 수치 성장만으로 잡아두면 이탈이 급격하다. 외재 보상이 내재 동기를 밀어낼 수 있다.
- **인플레이션.** 소모처 없는 재화, 무한 파밍이 가능한 아이템 때문에 후반 경제가 무의미해진다. 시뮬레이션 시트로 재화 흐름을 모델링해야 한다.
- **지배 전략.** 한 무기나 빌드가 모든 상황에서 최선이다. 비용 대비 효율을 단일 축으로만 계산하고, 상성·상황·위험 비용을 설계하지 않았기 때문이다.
- **개발자 숙련도 편향.** 팀은 쉽다고 느끼는데 신규 플레이어는 막힌다. 첫 플레이 관찰을 하지 않은 결과다.
- **데이터 오독.** 픽률이 높다는 이유만으로 너프한다. 승률, 숙련도 구간, 맥락을 함께 보지 않았고, 표본 크기와 생존 편향도 고려하지 않았다.

**징후→진단→조치**
- 특정 구간에서 이탈 급증 → 퍼널 데이터와 플레이 녹화로 막힘 원인이 난이도 스파이크인지, 설명 부족인지, 지루함인지 구분한다.
- 메타가 고착된다 → 선택지별 픽률·승률을 숙련도 구간별로 보고, 카운터 수단의 존재 여부를 확인한다.
- 재화가 넘친다 → 획득·소모 로그로 플레이어당 순유입을 계산하고, 소모처를 추가하거나 획득량을 조정한다.

**점검표**
- [ ] 핵심 루프를 한 문장으로 말할 수 있고, 프로토타입으로 검증했는가?
- [ ] 난이도 곡선과 학습 단계(도입→연습→변주→시험)가 레벨 단위로 있는가?
- [ ] 경제 시뮬레이션 시트와 소모처 목록이 있는가?
- [ ] 밸런스 수치는 데이터 파일로 분리되어 빌드 없이 수정 가능한가?
- [ ] 플레이테스트에 신규 플레이어를 포함하는가? 관찰과 설문을 분리해 기록하는가?
- [ ] 텔레메트리 이벤트가 질문(무엇을 알고 싶은가)에서 출발해 설계되었는가?

## 에셋 파이프라인·성능 최적화와 제작 공정

**핵심 원리.** 에셋은 원본(DCC 파일)에서 임포트를 거쳐 플랫폼별 변환·압축(텍스처 블록 압축, 메시 최적화, 오디오 인코딩)을 지나 패키징·스트리밍으로 간다. 이 과정이 자동화·재현 가능해야 한다. 최적화는 측정에서 시작한다. 먼저 CPU 바운드인지 GPU 바운드인지 메모리·IO 바운드인지 판별하고, 가장 큰 병목 하나를 고친 뒤 다시 측정한다. 제작 공정의 핵심은 불확실성을 앞당겨 제거하는 것이다.

**자주 보는 실패**
- **측정 없는 최적화.** 추측으로 코드를 고치고 개발 빌드나 에디터에서 판단한다. 대표 기기와 릴리스 설정으로 측정해야 한다.
- **메모리 예산 부재.** 텍스처가 원본 해상도·무압축으로 들어가 콘솔이나 모바일에서 OOM이 난다. 카테고리별(텍스처, 메시, 오디오, 코드, 스트리밍 풀) 예산과 자동 검사가 필요하다.
- **수동 임포트 설정.** 사람마다 설정이 달라 결과가 비일관적이고 재현이 안 된다. 규칙 기반 프리셋과 검증 스크립트를 둔다.
- **스트리밍 고려 없는 월드 설계.** 로딩 경계 없이 맵을 만들어 이동 중에 끊긴다. IO 대역폭과 압축 해제 비용을 이동 속도와 함께 계산해야 한다.
- **늦은 플랫폼 검증.** 최저사양 기기를 출시 직전에 처음 돌려본다. 최저사양 기준 빌드를 정기적으로 테스트한다.
- **범위 팽창.** 수직 슬라이스 없이 기능을 계속 추가하고, 알파 이후에도 신규 기능이 들어간다. 기능 잠금(feature lock)과 콘텐츠 잠금 시점을 정의하지 않았다.
- **빌드·버전 관리 부실.** 대용량 바이너리에 맞지 않는 VCS 설정 때문에 잠금 없는 바이너리 충돌이 나고 작업이 유실된다. 재현 불가능한 수동 빌드도 문제다. 대용량 파일 지원과 파일 잠금 정책, CI 자동 빌드와 스모크 테스트가 필요하다.
- **리스크 후순위.** 기술적으로 가장 불확실한 것(네트워크, 대규모 군중, 절차 생성)을 마지막에 만든다.

**징후→진단→조치**
- 프레임 저하 → 프로파일러로 CPU 메인·렌더 스레드와 GPU 시간을 비교해 바운드를 판별한다 → 해당 축의 최상위 항목부터 처리한다.
- 메모리 크래시 → 메모리 스냅샷을 카테고리별로 보고 예산 초과 항목과 누수(레벨 전환 후 미해제)를 찾는다.
- 일정 지연 반복 → 남은 작업을 추정치 대비 실적으로 보정한다 → 범위를 삭감하는 결정을 먼저 하고, 인원 투입은 나중에 검토한다(늦은 투입은 지연을 키울 수 있다).

**점검표** (프로젝트 규모에 맞는 항목만 쓴다. 1인·소규모 작업에 대형 출시 공정을 요구하지 않는다)
- [ ] 마일스톤(프리프로덕션→수직 슬라이스→알파→베타→출시 후보)마다 통과 기준이 정의되어 있는가?
- [ ] 최고 리스크 항목을 프리프로덕션에서 프로토타입으로 검증했는가?
- [ ] 플랫폼별 성능·메모리 예산과 자동 성능 회귀 테스트가 있는가?
- [ ] 에셋 임포트 규칙이 코드화되어 있고 위반 시 빌드에서 경고하는가?
- [ ] 빌드가 원클릭으로 재현 가능하며, 빌드 번호가 버그 리포트와 연결되는가?
- [ ] 기능·콘텐츠 잠금 시점과 범위 삭감 우선순위(필수/있으면 좋음/삭제 가능) 목록이 있는가?
- [ ] 인증·심사, 현지화, 접근성, 저장 데이터 호환 같은 출시 요건이 일정에 들어가 있는가? 세부 요건은 플랫폼마다 다르고 바뀌므로 최신 문서로 확인한다.

## 지시를 읽을 때의 공통 경고 신호

- "일단 만들고 나중에 최적화·멀티·결정성 추가": 구조적 결정을 미루는 것이다. 무엇이 사후 이식 불가능한지 먼저 짚는다.
- "FPS가 낮다", "느리다": 측정 데이터와 대상 기기, 빌드 설정을 먼저 묻는다.
- "물리 엔진이 알아서": 조작감, 결정성, 성능 요구가 엔진 기본값과 맞는지 확인한다.
- "ECS로 갈아엎자", "엔진 바꾸자": 해결하려는 측정된 문제와 전환 비용을 비교한다.
- "밸런스 수치 정해줘": 목표 경험, 상성 구조, 검증 방법이 비어 있으면 숫자만 정하지 말고 그 공백을 전제·위험에 적는다.
- 특정 엔진·도구의 기능과 한계는 버전마다 다르다. 단정하지 말고 현재 문서로 확인하도록 권한다.

## 더 짚을 것 (검토 보강)

- **저장 데이터:** 저장 형식에 버전 번호를 넣고 이전 버전을 읽어 올리는 변환을 둔다. 임시 파일에 다 쓴 뒤 원자적으로 바꿔 끼워 쓰는 도중 꺼져도 깨지지 않게 하고, 백업 슬롯과 손상 감지를 둔다. 플랫폼의 저장 용량·동기화 규칙을 따른다.
- **오디오:** 동시에 내는 소리(보이스) 수를 제한하고 우선순위로 고른다(넘치는 것은 가상 보이스로 둔다). 긴 음악·대사는 스트리밍한다. 버스로 묶어 믹싱하고 대사가 나오면 다른 소리를 줄인다(덕킹). 오디오 스레드에서는 메모리를 할당하지 않는다.
- **UI·HUD:** 해상도와 종횡비가 바뀌어도 앵커 기준으로 배치되는지, TV·휴대기기의 안전 영역 안에 있는지, UI 크기 옵션이 있는지, 게임패드로 포커스가 모든 항목에 닿는지 본다.
- **AI·길찾기 예산:** 무거운 판단과 경로 탐색은 프레임 예산을 나눠 여러 프레임에 분산하거나 비동기로 돌린다. 먼 개체는 덜 자주 갱신한다(AI LOD).

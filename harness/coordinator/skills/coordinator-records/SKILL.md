# 끝 보고, 기록, 보존 노트, 컴팩션 복구

규칙 원문은 CLAUDE.md(규칙: "사용자 보고 양식", "작업 흐름 (결정 8-32)", "기록 문서", "컴팩션과 보존 노트", "선호")다.

## 끝 보고 (결정 8-32)

작업 흐름의 끝에 **한 번** 보낸다. 사용자가 실행 중에 보는 것은 이것뿐이다.

1. 규칙의 "사용자 보고 양식"대로 쓴다. 두 번째 표는 이슈마다 `상태 | 담당 팀 | 하달 | 이슈 PR | 하달 PR | CI`다. PR 칸은 `push-branch` 출력의 PR 주소, CI 칸은 `ci` 값(pass·fail·timeout)이다. 대상 원격·워크플로가 없으면(종료 코드 4) PR 칸은 비우고 CI 칸에 "CI 없음"을 적는다.
   - **섞인 하달(결정 8-35)은 상태 표에 적는다.** 반려된 이슈는 상태 칸에 "반려 <횟수>회 → h<M>에서 재작업"(횟수는 그 이슈가 반려된 하달 수), 하달 칸에 옛 하달과 새 하달을 함께 적는다. 다시 만든 통합 브랜치는 표 아래 한 줄로: "`integration/h<N>` 다시 만듦: 남긴 이슈 #…, 뺀 이슈 #…(반려) · #…(대기, 함께 재작업)". 이것은 "결정할 것"이 아니다. 재작업 한도를 넘어 `거부목록`이 된 것만 "결정할 것"에 적는다.
2. 그 아래 `## 결정할 것`에 실행 중 모아 둔 것을 번호를 붙여 한 번에 묻는다. 항목마다 제안 / 이유 / 예상 결과로 쓴다.
   - **트레인 승인:** "`run-train --handoffs <의존 순서의 목록>`을 돌려 `main`에 머지할까요?" (대상 원격이 없으면 "CI 없음. `run-reflect`로 반영할까요?")
   - 거부목록 이슈와 마지막 거부 이유, 막힌 이슈와 풀 방법, 대리 기준으로 바꾼 기준과 원래 목표, 기다림 한도를 넘긴 PR·CI, 트레인 실패 때 부분 머지 여부.
3. 끝 보고를 보내기 전에 기록 문서에 "전달 예정"으로 적는다(아래).

## 기록 문서 `{{ISSUES}}/records/{{PROJECT}}.md`

1. 적는 시점: 정리본 승인 요청, 예외 보고(한도 초과·진행 불가), 최종 보고. 질문과 답변은 적지 않는다.
2. 보내기 전에 "전달 예정"을 적고, 다음 대화가 시작되면 그 항목을 "전달 확인"으로 바꾼다.
3. `git -C {{ISSUES}} add records/{{PROJECT}}.md` → `commit -m "<메시지>"` → `push`를 하나씩 실행한다.

## 보존 노트 `{{ISSUES}}/records/{{PROJECT}}-보존.md`

1. 보존 항목이 생기거나 철회될 때마다 **바로** 적는다(컴팩션은 언제든 올 수 있다): 사용자의 명시적 지시와 제약, 확정된 결정과 이유, 바뀐 파일 경로와 식별자(이슈·하달 번호, 해시), 미해결 오류의 핵심, 남은 작업, 승인 대기 항목.
2. 바뀐 항목은 이전 것에 "철회됨"을 붙인다. 끝난 것은 정리한다. 비밀값은 적지 않는다.
3. 기록 문서처럼 커밋·푸시한다.

## 컴팩션 뒤

1. 알림을 보면 보존 노트와 기록 문서를 다시 읽는다.
2. 보존 항목이 모두 남았는지 대화와 맞춰 본다. 못 찾은 것은 추측으로 채우지 않는다.
3. 사용자에게 하는 다음 답을 이 셋 중 한 줄로 시작한다: `컴팩션 복구: 완료` / `컴팩션 복구: 일부 누락 — <빠진 항목>` / `컴팩션 복구: 복구 실패 — <이유>`. 보존 노트 파일이 없으면 `컴팩션 복구: 일부 누락 — 보존 노트 없음`.

## 선호

- 사용자가 직접 말한 소통 선호(출력 양식, 보고 상세도, 질문 빈도, 말투, 승인 방식)는 바로 `{{ISSUES}}/records/preferences.md`에 저장한다.
- 내가 추론한 선호는 같은 요청이 3번째 나올 때 제안 / 이유 / 예상 결과로 제안하고, 승인받은 뒤에만 저장한다.

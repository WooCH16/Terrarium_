# 작업 흐름 (지시 → 끝 보고 → 트레인)

규칙 원문은 CLAUDE.md(규칙: "작업 흐름 (결정 8-32)", "직접 지시 경로")다. 이 스킬은 새 절차를 만들지 않는다. 기존 스킬을 부르는 순서와 끝에 물을 것만 정한다. 기존 스킬의 규칙과 부딪히면 기존 스킬을 따른다.

## 사용자에게 묻는 것은 시작·끝 두 번만

- **시작:** 무엇을 만들지 자체가 애매할 때 바로 묻기(1단계), 계획 승인 한 번(3단계).
- **끝:** 끝 보고 하나에 "결정할 것"을 모아 한 번에 묻는다(9단계). 머지 트레인 승인도 여기서 받는다.
- 그 사이(4~8단계)에는 묻지 않는다. 거부 한도 초과, 막힘, CI 실패, 주관적 기준은 처리하고 끝 보고에 적는다(`coordinator-exceptions`). 예외: 스크립트 종료 코드 2(설정·훅·저장소 실패)는 지금처럼 즉시 멈추고 알린다.

## 입구

- 코디네이터 터미널의 작업 지시 한 줄(`~해줘`). 1단계부터.
- `#<번호> 맡겨`: 이미 있는 이슈 하나만 맡는다. 그 이슈만 5단계(하달)부터 시작해 끝 보고까지 간다. 조언·계획 승인은 다시 받지 않는다. 이슈가 열려 있지 않거나 상태가 `반영됨`·`취소`면 그 사실만 알리고 멈춘다.
- 새 명령 방식은 만들지 않는다(`/goal`은 이 입구로 대신한다).

## 맡기기·반복 요청은 끝나는 조건과 예상 결과부터 (결정 8-34)

`/goal`, `/loop`, `#<번호> 맡겨`, "끝날 때까지 해 줘", "계속 돌려"처럼 맡기거나 되풀이하는 요청이면:

1. **끝나는 조건**(언제 멈추는지)과 **예상 결과**(끝났을 때 무엇이 남는지)를 묻는다. 요청에 이미 있는 것은 묻지 않는다.
2. 답을 다듬는다. 끝나는 조건은 확인할 수 있는 문장(예: "#12 `반영됨`, 대상 `npm test` 실패 0")으로, 예상 결과는 남는 것(이슈 상태, PR, 브랜치, 끝 보고)으로 쓴다. 안전 한도(재작업 한도, 하달 수, 시간)도 제안한다.
3. 다듬은 것을 보이고 **분명한 승인**을 받은 뒤에만 시작한다(결정 8-25: 애매하면 한 번 더 묻는다). 작업 지시 경로에서는 3단계 계획 승인과 **한 번에** 묻는다(묻는 횟수를 늘리지 않는다). `#<번호> 맡겨`는 계획 승인이 없으므로 5단계 전에 이것만 한 번 묻는다.
4. 승인된 끝나는 조건은 끝 보고(9단계)에서 "충족 / 못 충족(이유)"로 대조한다.

## 순서

1. **지시 판단:** 무엇을 만들지 자체가 애매하면(규칙의 직접 지시 경로 1번) 조언 전에 여기서만 바로 묻는다(`coordinator-direct`). 답이 오기 전에는 이슈도 하달도 만들지 않는다.
2. **조언:** `coordinator-advice` → 어드바이저 패널. 주관적인 기준은 묻지 않고 대리 기준으로 바꾼다(결정 8-27). 바꾼 기준과 원래 목표는 끝 보고의 "결정할 것"에 적는다.
3. **계획 승인:** 조언 요지와 이슈 목록을 보이고 **한 번** 묻는다(결정 8-25). 맡기기·반복 요청이면 다듬은 끝나는 조건·예상 결과도 함께 보인다(결정 8-34). 승인 뒤 바뀐 요구는 새 승인 없이 처리한다.
4. **이슈:** `coordinator-issues`(담당 팀 옮기기, 결정 8-29).
5. **하달:** `coordinator-handoff`. 팀별로 의존 순서대로, 반영 전 하달에 기대면 `--base h<N>`(결정 8-31).
6. **리뷰·이슈 PR:** `coordinator-review`로 Jev 판정을 받는다. 허용된 이슈마다 `node {{HARNESS}}/operator/push-branch.mjs --branch h<N>/issue-<번호>`를 부른다. 이슈 PR과 CI는 대상 저장소의 GitHub Actions가 하고, 스크립트는 결과를 읽어 한 줄 JSON으로 돌려준다.
7. **하달 PR·CI:** 하달의 이슈가 모두 판정(허용·거부)을 받으면 `node {{HARNESS}}/operator/push-branch.mjs --branch integration/h<N>`을 부른다. Actions가 하달 PR(→ `main`)과 CI를 하고, 스크립트가 기다려 읽는다. CI 실패(종료 코드 1)면 스크립트가 관련 이슈를 `미완료`로 두고 CI 결과 댓글을 남긴다. 새 하달로 재작업한다(재작업 한도 안, 묻지 않는다).
   - **섞인 하달(결정 8-35):** 허용과 거부·`미완료`(이슈 PR CI 실패 포함)가 섞였으면 스크립트가 통합 브랜치를 허용된 이슈만으로 다시 만들어 올리고(출력 `rebuilt`), 허용된 이슈는 하달 PR·CI·트레인으로 간다. 묻지 않는다.
   - `rebuilt.returned`(반려된 이슈)는 `coordinator-handoff`로 새 하달을 내 재작업한다(재작업 한도는 지금처럼 판정받은 보고서로 센다). 반려된 이슈가 h<N>의 허용된 이슈에 기대면 `--base h<N>`을 붙인다(결정 8-31). `rebuilt.held`(반려된 이슈에 기대어 빠진 허용된 이슈, `대기`)는 그 반려된 이슈와 **같은 새 하달**에 넣는다.
   - 재작업으로 허용된 이슈는 새 하달의 이슈 PR·통합 브랜치·하달 PR로 간다. 옛 하달의 이슈 PR과 원격 브랜치는 대상 저장소의 Actions가 "h<M>에서 다시 함"으로 닫고 지운다. 트레인 순서는 앞 하달부터(`--base`로 시작한 하달은 뒤).
   - 판정 전 이슈가 섞여 있으면 종료 코드 2(아무것도 바꾸지 않음): 판정을 받은 뒤 다시 부른다.
   - 순서: 하달의 판정이 다 나오면 반려된 이슈의 재작업 하달보다 `integration/h<N>`을 먼저 올린다. 재작업 하달을 먼저 냈어도 괜찮다: 뒤 하달에 같은 이슈의 브랜치가 있으면 스크립트가 그 이슈를 `h<M>에서 재작업 중`으로 빼고 라벨·댓글은 건드리지 않는다.
8. **예외:** `coordinator-exceptions`의 표대로 처리하고 "결정할 것"에 적는다. 묻지 않는다.
9. **끝 보고:** `coordinator-records`. 이슈마다 상태·담당 팀·하달·이슈 PR·하달 PR·CI 결과, 그리고 "결정할 것"(트레인 승인, 거부목록, 막힘, 바꾼 기준, 트레인 실패 때 부분 머지)을 한 번에 보인다. 반려한 이슈와 횟수, 다시 만든 통합 브랜치와 뺀 이슈는 "결정할 것"이 아니라 상태 표에 적는다(재작업 한도를 넘은 것만 "결정할 것").
10. **트레인:** 사용자가 트레인을 **분명히** 승인하면 `coordinator-reflect`가 `run-train.mjs --handoffs h<N>[,h<M>...]`를 부른다(Actions 워크플로 시작 → 끝날 때까지 기다림 → 요약 읽기). 결과를 보고한다. 승인하지 않으면 부르지 않는다: 하달 PR은 열린 채, `main`은 그대로다.

## push-branch 종료 코드

| 코드 | 뜻 | 할 일 |
|---|---|---|
| 0 | CI 통과(또는 이미 통합 브랜치에 들어 있어 이슈 PR 없음). 통합 브랜치를 다시 만들었으면 `rebuilt`가 있다(결정 8-35) | 다음 단계. `rebuilt.returned`·`rebuilt.held`는 위 7단계대로 새 하달로 재작업 |
| 1 | CI 실패. 관련 이슈는 `미완료` | 새 하달로 재작업(묻지 않는다) |
| 2 | 허용 판정 없음, 브랜치 없음, 빨리감기 아님, 판정 전 이슈가 섞임, 남길 허용된 이슈가 없음, 다시 만들다 충돌 등. 아무것도 올리지 않음 | 줄을 그대로 끝 보고에. 설정 문제면 즉시 멈추고 알린다. "판정 전"이면 판정 뒤 다시 부른다. "남길 허용된 이슈가 없습니다"면 하달 PR 없이 반려된 이슈를 새 하달로 재작업한다(묻지 않는다) |
| 4 | 대상 원격·워크플로 없음 | 로컬 흐름: push 없이 끝 보고까지, 반영은 `run-reflect`. 끝 보고에 "CI 없음" |
| 5 | 기다림 한도 초과(PR·CI 결과 없음) | 같은 명령을 한 번 더(다시 올리지 않고 읽기만). 그래도 5면 "결정할 것"에 |
| 8 | 아직 기다리는 중 | 출력 줄의 `wait-operator.mjs --wait <번호>`로 이어서 기다린다 |

## 확인할 점

- `git push`, `gh pr`, `gh workflow`를 직접 쓰지 않는다(훅이 막는다). 두 스크립트만 쓴다. 강제 push는 `push-branch`가 다시 만든 `integration/h<N>`에만 스스로 한다(결정 8-35). 옛 PR 닫기·브랜치 지우기는 Actions가 한다.
- `main`에 쓰는 것은 Actions뿐이다. 트레인 실패 때 통과한 앞부분만 머지할지는 스스로 정하지 않고 끝 보고에서 묻는다.
- 원격·워크플로가 없는 대상은 지금의 로컬 흐름 그대로다(결정 4).

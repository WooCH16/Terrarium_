# 반영 (머지 트레인 또는 로컬 반영)

규칙 원문은 CLAUDE.md(규칙: "작업 흐름 (결정 8-32)", "직접 지시 경로") 11번이다. `run-reflect`가 코드로 하는 일은 오퍼레이터의 `operator-reflect` 스킬 문서에 있다.

## 순서

1. 사용자가 트레인·반영을 **분명히** 승인했는지 본다. 애매하면 다시 묻는다. 승인 없이는 아무것도 부르지 않는다: 하달 PR은 열린 채, `main`은 그대로 둔다(훅은 승인 여부를 모른다. 이 규칙이 지킨다).
2. 하달 번호 `h<N>`을 `{{RUN}}/handoffs/` 폴더 이름이나 결과 보고서의 브랜치 이름(`h<N>/issue-<번호>`)에서 읽는다. 앞 하달부터 늘어놓는다: `--base h<M>`으로 시작한 하달은 h<M> 뒤에 둔다(결정 8-31).
3. **대상 원격·워크플로가 있으면(끝 보고의 CI 칸이 "CI 없음"이 아님):** `node {{HARNESS}}/operator/run-train.mjs --handoffs h<M>,h<N>`을 한 번 부른다. Bash `timeout`은 600000, 종료 코드 8이면 `wait-operator.mjs --wait <번호>`로 이어서 기다린다.
   - 출력은 JSON 한 줄이다. 0: 트레인 통과(`main` 머지, `rows`의 이슈는 `반영됨`, `localMain`이 실행 폴더의 대상 프로젝트 `main`을 따라갔는지). 1: 트레인 CI 실패(`main` 그대로, `failedHandoff`가 실패 하달, `passingPrefix`가 통과한 앞부분). 2: 순서·하달 PR·설정 실패(아무것도 시작하지 않음). 5: 기다림 한도 초과(`runUrl`을 보고).
   - 1이면 스스로 부분 머지하지 않는다. "통과한 앞부분(`passingPrefix`)만 트레인으로 다시 돌릴까요?"를 "결정할 것"에 적어 묻는다. 실패 하달의 이슈는 새 하달로 재작업한다.
   - 순서를 어기면 "h<M>부터 … 트레인 앞에 두거나 먼저 반영하세요"(종료 코드 2)가 온다. 순서를 고쳐 다시 묻는다.
4. **없으면(로컬 흐름, 결정 4):** `node {{HARNESS}}/operator/run-reflect.mjs --handoff h<N>`을 앞 하달부터 하나씩 부른다. 순서를 어기면 "h<M>부터 반영하세요"(종료 코드 2, `main`은 그대로)가 온다. 그때는 멈추고 그 줄을 그대로 보고한 뒤 h<M>의 반영을 묻는다. 함께 반영하는 명령은 없다. 출력은 이슈마다 `#번호 | 상태 | URL` 한 줄이다. 종료 코드 0은 모두 정상, 1은 막힘·보류·거부목록이 있음, 2는 실패(`main`은 바뀌지 않았다), 3은 중단이다. `run-train`도 대상 원격이 없으면 이 흐름을 순서대로 돌리고 `"ci":"none"`을 낸다.
5. 기록 문서에 하달 번호, 트레인 이름(`train/<날짜>-<순번>`)이나 "CI 없음", 반영 결과를 적고 커밋·푸시한 뒤 보고한다.
6. 반영을 기다리던 `대기` 이슈가 있으면 새 하달로 다시 시킨다(`coordinator-handoff`).

## 확인할 점

- 오퍼레이터 세션은 뜨지 않는다. `main`에 쓰는 것은 대상 저장소의 Actions(트레인)이거나, 로컬 흐름에서는 허용된 커밋만 골라 합치는 `run-reflect`다.
- `gh workflow run`, `gh pr merge`, `git push`를 직접 쓰지 않는다(훅이 막는다).

# 계획: 머지 큐·머지 트레인과 바뀐 부분만 검사

**상태: 승인(2026-11-26, 결정 8-45).** CI 설정(`.github/workflows/ci.yml`) 변경도 승인받았다.

## 요구 (소유자 말 그대로)

> 머지큐,머지트레인은 머지큐를 조율하는 오케스트레이션 작업을 메인 스레드 한테 맡기고 메인 스레드가 병합한다
> 코디네이터가 머지 트레인을 관리함 , PR캐싱(변경된분량만검사) -> main은 전체 검사함 -> v0.0.1버전 브랜치로 병합, PR에서 변경된 부분만 CI를 돌림, 메인이 아니기때문에 변경만 검사함-> main에 넣으면서 전체 검사함
> 여기서 main은 하네스의 main이고 작업 커밋은 beta

## 말과 실제 대상

틀린 대응이 있으면 이 표에서 고친다.

| 말 | 이 계획에서 가리키는 것 |
|---|---|
| main | 이 저장소(하네스)의 `main`. 보호 브랜치 |
| 작업 커밋 | `WooCH16/beta` |
| 버전 브랜치(`v0.0.1`) | `WooCH16/beta`가 이 역할을 한다. 버전 이름 브랜치를 따로 만들지 않는다 |
| 메인 스레드, 코디네이터 | 이 저장소의 작업을 지휘하는 Claude Code 메인 세션 |
| 메인 스레드가 병합 | 메인 세션이 `gh pr merge`로 병합한다 |
| PR 캐싱 | 바뀐 부분에 닿는 검사만 돌린다 |

## 흐름

```
묶음 브랜치(bundle/<이름>)
  → PR → WooCH16/beta      : 바뀐 부분만 CI
  → 메인 세션이 큐 순서대로 병합
  → PR → main (트레인)     : 전체 CI
  → 소유자가 시킬 때 병합
```

## 지금과 다른 점

| 항목 | 지금 | 계획 |
|---|---|---|
| PR의 CI | 대상 브랜치와 상관없이 모든 PR에서 전체 시험 | 대상이 beta면 바뀐 부분만, `main`이면 전체 |
| push의 CI | `main`에 push할 때만 | 그대로 |
| beta로 가는 길 | 직접 커밋하고 push (CI 없음) | 묶음 브랜치에서 PR. 그래야 변경분 CI가 돈다 |
| 머지 순서 | 정해진 절차 없음 | 메인 세션이 큐를 들고 한 번에 하나씩 병합 |
| `main` 병합 | PR, 필수 검사 `check`·`harness-unit` | 그대로 |

## 머지 큐 (메인 세션)

1. 열린 beta 대상 PR을 의존 순서, 올린 순서로 줄 세운다.
2. 맨 앞 PR을 beta 최신에 맞추고 CI를 기다린다.
3. 통과하면 병합하고, 실패하면 큐에서 빼고 원인을 고친 뒤 다시 넣는다.
4. 큐가 비면 beta → `main` PR을 열어 전체 CI를 돌린다. 병합은 소유자가 시킬 때 한다.

GitHub의 머지 큐 기능은 쓰지 않는다.

## 바뀐 부분만 검사하는 규칙

기존 `ci-batch-flow` 스킬의 "통과한 시험은 다시 돌리지 않는다"를 코드로 옮긴다. 가릴 수 없으면 전체를 돌린다.

| 바뀐 파일 | 돌릴 검사 |
|---|---|
| 항상 | `scripts/check.js` |
| `harness/test/<이름>.test.mjs` | 그 파일 |
| `harness/` 아래 모듈 하나 | 그 모듈을 직접·간접으로 불러 쓰거나 띄우는 시험 파일. 닿는 시험이 없으면 전체 |
| `docs/` 문서 | `docs/`를 읽는 시험 |
| 역할 문서(`harness/**/*.md`) | 역할 문서를 읽는 시험 전부와, 실행 중에 그 문서를 읽는 모듈에 닿는 시험 |
| 저장소 루트의 `*.md`, `.claude/` 문서 | `check`만(읽는 시험이 없다) |
| `app/` | 앱 논리 시험 |
| 공용 모듈(`protocol.mjs`, `report.mjs`, `policy.mjs`), 설정 JSON, 시험 도우미, `scripts/`, `.github/` | 전체 |
| 위에 없는 경로 | 전체 |

공용 모듈과 설정을 전체로 두는 이유: 결정 8-44에서 라벨과 재작업 한도를 바꿨을 때, 직접 관련 없어 보이는 시험 파일들이 느린 시험에서야 깨졌다.

## 필수 검사

`check`와 `harness-unit` 작업은 이름을 바꾸거나 건너뛰지 않는다. `harness-unit` 안에서 PR의 대상 브랜치를 보고 돌릴 범위만 바꾼다. `main`은 보호돼 있고 `WooCH16/beta`는 보호돼 있지 않다.

## 얻는 것

| 어디 | 전체 검사에 걸린 시간 |
|---|---|
| GitHub Actions (PR #48) | `check` 7초, `harness-unit` 1분 14초 |
| 이 PC (Windows) | 빠른 시험 약 3분, 느린 시험 약 9분 |

만든 규칙으로 고르는 시험 파일 수(전체 48개, 그중 느린 9개). 시간은 재지 않았다.

| 바뀐 파일 | 고르는 시험 | 느린 시험 |
|---|---|---|
| `CHANGELOG.md`, `app/` 화면 | 0 (앱은 앱 논리 시험) | 0 |
| `docs/operator.md` | 7 | 0 |
| `result-draft.mjs` | 2 | 0 |
| `setup.mjs` | 6 | 1 |
| `jev-review.mjs` | 9 | 1 |
| `run-worker.mjs`, `run-operator.mjs`, `merge-adapter.mjs` | 19 | 7 |
| `launch.mjs` | 27 | 8 |
| `worker/AGENT.md` | 30 | 8 |
| 공용 모듈, 설정 | 전체 | 9 |

여러 모듈이 `run-operator.mjs`의 도우미를 불러 쓰기 때문에, 중심 모듈을 바꾸면 느린 시험 대부분이 남는다. 도우미를 따로 떼면 줄지만 이 계획에 넣지 않았다.

Actions에서 줄어드는 시간은 PR 하나에 1분 남짓이 최대다. 효과가 큰 곳은 작업 중에 이 PC에서 돌리는 시험이다. 같은 대응 규칙을 로컬에서도 쓴다(`node scripts/test.mjs --changed <기준>`).

## 할 일

1. 대응 규칙을 `scripts/test.mjs --changed <기준>`으로 만들고 시험을 붙인다.
2. `ci.yml`에서 대상이 `main`이 아닌 PR은 `--changed`를 쓰게 한다. **CI 설정 변경이라 따로 승인받는다.**
3. 머지 큐 절차를 `ci-batch-flow` 스킬에 넣는다.
4. 시험 PR 하나로 beta 대상(변경분)과 `main` 대상(전체)을 확인한다.

## 이 계획에 넣지 않은 것

하네스가 대상 저장소에 설치하는 워크플로와 머지 트레인(결정 8-32)은 바꾸지 않는다.

# 문제 기록

작업 중에 생긴 문제를 **문제 내용 / 원인 / 해결방안 / 이유**로 남긴다. 새 문제는 아래에 번호를 이어 붙인다. 상태는 `해결`, `확인 전`(고쳤지만 실제로 돌려 보지 않음), `남음`이다.

공개 저장소에 있는 문서이므로 개인 경로, 비공개 저장소 이름, 비밀값은 적지 않는다.

## 2026-11-24 ~ 11-26: 오퍼레이터 속도, 사용자 결정 흐름 (결정 8-40 ~ 8-44)

### 1. 워크플로 시험 4개가 로컬에서 실패 (해결)
- **문제 내용:** Windows PowerShell에서 시험을 돌리면 워크플로 시험 4개가 실패했다.
- **원인:** PATH의 `bash`가 Git Bash가 아니라 WSL의 것이었다.
- **해결방안:** 시험 전에 Git의 `bin`을 PATH 앞에 둔다.
- **이유:** 워크플로 시험은 Git Bash 환경을 전제로 한다. 코드 결함이 아니라 실행 환경 문제였다.

### 2. haiku 오퍼레이터가 sonnet보다 느림 (해결)
- **문제 내용:** 빠르게 하려고 haiku로 바꿨는데 오퍼레이터만의 시간이 92~102초에서 163초로 늘었다.
- **원인:** 이슈를 여러 번 다시 읽었고, 훅에 거부되는 명령을 써서 왕복이 늘었다.
- **해결방안:** 지침에 이슈 본문·댓글을 미리 넣고 명령 규칙을 앞에 뒀다(8-41, 96초). 그래도 같은 지침에서는 sonnet이 더 빨라(67초) 기본 모델을 sonnet으로 되돌렸다(8-43).
- **이유:** 시간은 모델의 응답 속도보다 왕복 횟수와 왕복 사이의 생각하는 시간에 더 좌우됐다.

### 3. 오퍼레이터의 git 확인 명령이 거부됨 (해결)
- **문제 내용:** 마무리 단계에서 git 명령 4개가 거부됐다.
- **원인:** `show --stat`에 붙인 `--format=` 옵션과 `diff-tree`는 훅이 허용하지 않는다. 처음에는 "`show --stat`이 막힌다"고 잘못 보고했다.
- **해결방안:** 보고서 초안이 변경 파일과 해시를 미리 채우게 하고(8-42), git으로 다시 확인하지 않게 했다. 보고는 정정했다.
- **이유:** 훅을 넓히지 않고 명령이 필요 없게 만드는 쪽이 안전하다.

### 4. 사실 칸을 미리 채웠는데 더 느려짐 (해결)
- **문제 내용:** 8-42 뒤 오퍼레이터만의 시간이 96초에서 107초로 늘었다.
- **원인:** "Write로 다시 쓰지 말라"는 줄 때문에 Edit 횟수가 늘었고, 허용되는 git 모양을 적은 줄이 git 사용을 부추긴 것으로 보인다.
- **해결방안:** 두 줄을 뺐다(8-43).
- **이유:** 절차 문장 하나가 응답 횟수를 바꾼다. 한 번씩만 잰 값이라 우연도 섞였을 수 있다.

### 5. 서로 다른 지침의 속도를 비교함 (해결)
- **문제 내용:** 옛 지침의 sonnet과 새 지침의 haiku를 비교해 "haiku가 5~15초 느리다"고 답했다.
- **원인:** 같은 조건으로 재지 않은 값을 나란히 놓았다.
- **해결방안:** 정정하고, 같은 지침으로 sonnet을 다시 쟀다.
- **이유:** 조건이 하나만 달라야 차이의 원인을 말할 수 있다.

### 6. sonnet의 보고서 근거가 뭉뚱그려짐 (확인 전)
- **문제 내용:** 모든 기준의 근거가 "합치기 시험 통과"처럼 같은 말이었다.
- **원인:** 워커 결과 파일의 내용을 근거에 옮기라는 규칙이 없었다.
- **해결방안:** 기준마다 시험 이름이나 파일:줄을 쓰라는 줄을 절차에 넣었다(8-43). 그 뒤 하달로는 확인하지 않았다.
- **이유:** 근거가 구체적이어야 리뷰어와 사용자가 확인할 수 있다.

### 7. 반복 작업 만료일을 잘못 안내 (해결)
- **문제 내용:** loop가 7일 뒤 저절로 끝난다고 말했다.
- **원인:** 문서를 확인하지 않고 기억으로 답했다.
- **해결방안:** 문서를 확인해 30일(v2.1.330 전은 7일)로 고쳤다.
- **이유:** 도구의 한도는 버전에 따라 바뀌므로 문서로 확인한다.

### 8. 사용자 결정이 워커에게 전달되지 않음 (확인 전)
- **문제 내용:** loop가 결정을 이슈 댓글로 옮기고 다시 하달해도 워커는 몰랐다.
- **원인:** `run-worker`가 이슈 본문만 넘겼다. 만든 직후의 시험은 하달까지만 확인하고 워커 입력을 보지 않았다.
- **해결방안:** `## 사용자 결정` 댓글을 워커 입력에 붙였다. 가짜 워커 시험은 통과했고 실제 하달은 아직 하지 않았다.
- **이유:** 흐름을 만들면 마지막으로 그 값을 쓰는 곳까지 시험해야 한다.

### 9. 기준을 바꾸는 결정은 다시 거부될 수 있음 (확인 전)
- **문제 내용:** 결정이 완료 기준을 바꿔도 리뷰어는 본문의 옛 표로 판정한다.
- **원인:** 보고서와 판정이 본문의 표를 글자 그대로 쓴다.
- **해결방안:** loop가 결정을 옮기기 전에 본문의 표를 사용자 답대로 고친다. 답이 분명하지 않으면 고치지 않고 알린다.
- **이유:** 판정 기준은 한 곳(본문)에만 두는 것이 맞고, 바꿀 권한은 사용자에게 있다.

### 10. 사용자 결정 댓글을 오퍼레이터가 만들 수 있었음 (해결)
- **문제 내용:** 워커가 믿게 된 `## 사용자 결정` 댓글을 오퍼레이터 세션도 올릴 수 있었다.
- **원인:** 훅은 리뷰어 판정 머리만 막고 있었다.
- **해결방안:** `## 사용자 결정`, `## 결정 이슈`로 시작하는 댓글도 막았다.
- **이유:** 다른 단계가 믿는 입력은 만들 수 있는 쪽을 제한해야 한다. GitHub 계정이 공유라 작성자로는 가릴 수 없다.

### 11. 옮긴 뒤 끊기면 이슈가 멈춘 채 남음 (해결)
- **문제 내용:** loop가 결정을 옮기고 하달 전에 끊기면 그 이슈가 다시 큐에 들어가지 않았다.
- **원인:** 큐 규칙이 "이번 차례에 옮긴 이슈"만 담았다.
- **해결방안:** `결정대기`인데 사용자 결정이 이미 있는 이슈도 큐에 넣는다.
- **이유:** loop는 중간에 끊길 수 있으니 상태만 보고 이어갈 수 있어야 한다.

### 12. Bash 도구가 아무 일도 하지 않음 (해결)
- **문제 내용:** 메모 저장과 시험 추가를 Bash 도구로 했는데 파일이 그대로였다. 오류도 없었고, 저장했다고 보고했다.
- **원인:** 이 환경의 Bash 도구는 동작하지 않는다.
- **해결방안:** PowerShell과 Write 도구로 다시 하고, 파일이 생겼는지 확인했다.
- **이유:** 출력이 없다는 것은 성공이 아니다. 저장했다고 말하기 전에 결과를 확인한다.

### 13. 워커 지침에 금지 낱말을 넣음 (해결)
- **문제 내용:** 워커 지침에 "사용자"를 써서 시험이 실패했다.
- **원인:** 워커 글에는 "코디네이터", "사용자"를 쓰지 않는 규칙이 있다.
- **해결방안:** 워커에게 보이는 이름을 `## 소유자 결정`으로 했다.
- **이유:** 워커는 대화 상대가 없는 역할이라 이 규칙을 두고 있다.

### 14. beta 푸시가 한 번 실패 (해결)
- **문제 내용:** 푸시가 "Internal Server Error"로 거부됐다.
- **원인:** GitHub 서버 쪽 오류.
- **해결방안:** 다시 푸시하고 원격 해시가 로컬과 같은지 확인했다.
- **이유:** 일시 오류는 한 번 다시 시도하면 되지만, 반영 여부는 원격에서 확인해야 한다.

### 15. 머지 큐 요구의 대상을 잘못 읽음 (해결)
- **문제 내용:** 같은 요구를 세 번 다시 말해야 했다. 분석 표 두 개가 요구와 다른 흐름을 다뤘고, 계획에도 넣지 않았다.
- **원인:** "main", "beta"를 하네스가 대상 저장소에 설치하는 워크플로로 읽었다. 뜻을 확인하는 대신 질문을 늘렸고, "그냥 main으로 하자"를 beta 안을 거둔 것으로 읽었다.
- **해결방안:** 이 저장소의 흐름(작업 커밋 beta, `main`은 전체 검사)으로 계획 문서를 만들고, 말과 실제 대상의 대응표를 맨 앞에 두었다.
- **이유:** 분석 전에 말이 가리키는 대상을 보여 주면 틀린 대응을 바로 고칠 수 있다.

### 16. 변경분 시험 고르기가 거의 줄이지 못함 (해결)
- **문제 내용:** 오퍼레이터 모듈 하나만 바꿔도 시험 파일 47개 중 37개를 골랐다.
- **원인:** 빌드 결과물(`app/dist`)의 복사본이 의존 관계에 섞였고, 설명이나 허용 목록에 적힌 스크립트 이름까지 의존으로 셌다.
- **해결방안:** 빌드 폴더를 빼고, 경로를 조립하거나 띄우는 문자열만 세며, 훅 모듈은 import만 센다. 따라가는 단계는 자르지 않았다.
- **이유:** 단계를 자르면 실제로 깨지는 시험을 건너뛴다. 가짜 연결을 없애는 것이 놓치지 않고 줄이는 길이다.

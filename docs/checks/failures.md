## F1. `agy --sandbox`가 파일 편집 도구 쓰기를 막지 못함 (해결됨)

- **무엇이 실패했나:** `agy --sandbox`로 읽기는 되지만, 에이전트의 파일 편집 도구(`write_file`)로 쓰는 것이 막히지 않았다. 셸 명령으로 쓰는 것만 막혔다.
- **근거:** `docs/checks/T5-pi-env.md` 시험 3. 시험 파일의 sha256이 바뀌고 내용이 `MODIFIED-BY-AGY`가 되었다. 대조군으로 다시 시험해도 같았다(`T5-agy-readonly-loop.md`).
- **영향:** 리뷰어를 읽기 전용으로 보장하지 못해 ADR 0004의 재논의 문구에 걸렸고 T6, T7이 막혀 있었다.
- **해결:** 반복 시험으로 통과 설정을 찾았다. `--sandbox`에 `--settings`로 `{"permissions":{"deny":["write_file(*)"]}}`를 주면 편집 도구 쓰기와 새 파일 만들기가 권한 검사에서 막힌다(`permission check failed for write_file ... Permission denied`). 같은 설정이 연속 2회 통과했고 셸 우회 4건도 막혔다.
- **반복 기록:** 대조군 실패, 반복 1(`--mode plan`) 실패(plan 모드는 도구가 막는 것이 아니라 모델의 행동 방식), 반복 2 통과. 자세한 내용은 `docs/checks/T5-agy-readonly-loop.md`.
- **남은 것:** 샌드박스를 쓸 수 없는 환경에서의 셸 쓰기 보호, 다른 모델·추론 강도에서의 재확인, Pi를 거치는 경로. 같은 문서의 "한계와 남은 위험"에 있다.

## F2. 기존 시험 2개 실패 (해결됨)

- **무엇이 실패했나:** 원본 하네스의 시험 102개 중 2개가 원본에서도 실패했다.
  - `operator-launch.test.mjs`의 C1(`HARNESS_RUN_DIR` 없이 `harness.json` 찾기)
  - `operator-research-stop.test.mjs`의 "중단 표시가 있으면 … 종료 코드 3"(실제 2)
- **원인:** 둘 다 코드가 아니라 시험의 낡은 전제였다. C1은 성공한 세션 폴더를 지운 뒤 그 폴더를 `cwd`로 `spawnSync`해서 ENOENT가 났고, 종료 코드 3 시험은 뒤에 생긴 확인(`handoffHasWork`)이 `git` 저장소가 아닌 `memo`에서 던져 종료 코드 2가 났다.
- **해결:** 시험 쪽을 고쳤다(시험 2줄 추가, `handoffHasWork: () => false` 지정). 이후 전체 `node --test harness/test/*.test.mjs`가 508건 통과(Windows, Node 26.7)였다.
- **근거:** 브랜치 `wt/core-harness`의 #4 T1 보고와 그 커밋.
- **참고:** 중단 표시 확인(`isStopped`)이 `handoffHasWork` 확인보다 뒤에 있다. 코드 순서를 바꿀지는 정하지 않았다.

- **영향:** ADR 0004 결정 B의 "Pi → `agy` → Gemini"와 Claude 후보를 Pi로 부르는 경로가 아직 없다. 모델 호출 자체는 각 CLI로 직접 확인했다(Muse는 Pi로 확인).

## F10. 결과 판정이 근거 칸의 이름을 파일 경로로 오해해 거부 (해결됨(결정 8-30))

- **해결(2026-11-22):** 해결 방안 1~3대로 고쳤다. `jev-review.mjs`의 `classifyEvidence`와 `run-reviewer.mjs`의 `fileCheckerAt`(이름 찾기 `byName`), 오퍼레이터 결과 보고서 규칙 한 줄. 근거 이름에 한글 등 유니코드 글자도 받게 해 `src/없는파일.mjs` 같은 경로를 놓치지 않는다. 시험 `harness/test/evidence-names.test.mjs`(h24 모양은 문제 없음, `src/없는파일.mjs`는 문제, 다른 폴더의 `cli.mjs`는 확인됨). 실제 판정으로 다시 돌려 보지는 않았다.

- **문제:** run-18 h24에서 결과 판정 거부 세 번 가운데 두 번이 잘못된 거부였다. 보고서 근거 칸의 `memos.json`(프로그램이 실행할 때 만드는 데이터 파일)과 `.harness/`(커밋하지 않는 하네스 작업 폴더)를 "보고서 커밋에 없는 근거 파일"로 보고 Jev에 묻기도 전에 거부했다.
- **원인:** `harness/operator/jev-review.mjs`의 `evidencePaths`가 근거 칸의 백틱 안 글자 가운데 빗금이 있거나 확장자처럼 생긴 것을 모두 저장소 파일 경로로 보고, `reportProblems`가 커밋에 없으면 거부 사유로 넣는다. 폴더와 실행 중에 생기는 파일, 출력 이름을 가리지 않는다.
- **해결 방안:**
  1. 빗금으로 끝나는 이름(폴더)은 검사에서 뺀다.
  2. 빗금 없는 이름은 커밋 안에서 같은 이름의 파일을 찾고, 하나도 없으면 실행 중 생기는 파일·출력 이름으로 보고 검사에서 뺀다. 빗금이 있는 경로(`src/cli.mjs`)는 지금처럼 반드시 있어야 한다.
  3. 오퍼레이터 결과 보고서 규칙에 "근거 칸의 백틱은 저장소 파일 경로에만 쓴다. 실행 중 생기는 파일·명령 출력은 따옴표로 쓴다"를 넣는다.
- **이유:**
  - 이 검사는 근거를 지어낸 보고서를 잡으려는 것이고, 지어낸 근거는 보통 `src/...`처럼 경로 모양이다. 경로 쪽은 엄격하게 두고 오해를 부르는 이름만 놓아주면 막는 힘은 거의 줄지 않는다.
  - 폴더는 몇째 줄이 근거인지 가리킬 수 없어 검사 대상이 아니다.
  - 쓰는 쪽에서 구분하면 검사가 헷갈릴 일 자체가 줄어든다(코드 검사 1·2와 겹으로 막는다).
- **시험:** h24에서 거부된 두 보고서 모양을 시험 자료로 넣어 통과하는지, 없는 경로(`src/없는파일.mjs`)는 여전히 거부되는지 본다.
- 근거: `docs/checks/runs.md` run-18 h24 절.

## F11. 다른 하달의 의존 이슈가 `main` 기준이라 막힘 (해결됨(결정 8-31))

- **해결(2026-11-22):** 해결 방안 1·2(거부 쪽)·3대로 고쳤다. 시작 지점은 통합 브랜치가 아니라 앞 하달의 의존 이슈 브랜치다(run-11과 같은 이유). 반영 순서는 의존 글이 아니라 git 조상 관계로 본다. ADR 0012 결정 5, 시험 `harness/test/roles-base.test.mjs`(가짜 저장소로 `--base h1` 하달의 새 워크트리에 앞 이슈의 파일이 보이고, h2를 먼저 반영하면 거부, h1 → h2면 둘 다 반영). 남는 한계는 `docs/known-limitations.md` 9절. 실제 실행 폴더로는 돌려 보지 않았다.

- **문제:** run-18 h24에서 #46(빠른 시작 시험)은 #45(README)에 기대는데, 거부 뒤 새 하달로 재작업하면서 #45가 아직 반영되지 않은 `main`에서 시작했다. 완료 기준 "기존 파일은 그대로"도 `main`과 비교하게 쓰여 있었다. 그래서 통과할 수 없었고, 코디네이터가 `main` 반영을 사용자에게 물어야 했다.
- **원인:** 하달마다 작업이 `main`에서 시작한다. 앞 하달의 결과는 반영 전까지 그 하달의 통합 브랜치에만 있다. 결정 8-17("같은 하달의 의존 이슈는 통합 브랜치에서 시작")은 하달이 다르면 작동하지 않는다. 재작업은 새 하달(결정 2-3)이라 같은 지시 안에서도 하달이 갈린다.
- **해결 방안:**
  1. `run-operator.mjs --base h<N>`: 앞 이슈의 하달이 아직 반영 전이면 새 하달을 그 통합 브랜치에서 시작한다. 코디네이터는 이슈의 "먼저 끝나야 할 것"이 반영 전인 다른 하달에 있으면 `--base`를 붙인다.
  2. `run-reflect`는 시작 지점이 된 하달이 아직 반영 전이면 그것부터 반영하라고 거부한다(또는 함께 반영한다).
  3. 어드바이저 제안문 양식: "변경 없음" 같은 기준은 `main`이 아니라 작업 시작 지점과 비교한다.
- **이유:**
  - `main`은 사용자가 정할 때만 바뀐다는 원칙을 지키면서 작업이 멈추지 않는다.
  - 뒤 하달만 `main`에 들어가면 앞 하달의 변경이 섞여 들어가거나 충돌하므로 반영 순서를 강제해야 한다.
  - 기준 문장이 비교 대상을 `main`으로 고정하면 1이 있어도 다시 막힌다.
  - 역할 오퍼레이터(관제탑 카드 다섯)를 두면 한 지시가 여러 하달로 나뉘어 이 문제가 더 자주 생긴다. 그래서 역할 오퍼레이터와 함께 고친다.
- **시험:** 가짜 저장소로 반영 전 하달과 그 위에서 시작한 하달(`--base`)을 만들어, 새 워크트리에 앞 이슈의 파일이 보이는지와 반영 순서를 어기면 거부되는지 본다.

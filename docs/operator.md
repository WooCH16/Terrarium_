# 오퍼레이터 설계

- 실행 문서와 스킬: `harness/operator/AGENT.md`(공통 규칙)와 `harness/operator/skills/operator-work`, `operator-research`(모드별 절차, `launch.mjs`가 AGENT.md 뒤에 붙인다), `operator-reflect`(`run-reflect`가 코드로 하는 일). 예전의 `work.md`·`research.md`·`reflect.md`를 그대로 옮긴 것이다.

- 상태: **채택됨** (2026-11-14 사용자 승인). 근거는 [ADR 0003](adr/0003-operator-harness.md)이다(원본이 없어 이 문서에서 되살린 본문, 이슈 #30). 이 문서가 오퍼레이터의 현재 설계다.
- **워커의 실행 방식과 모델 목록은 [ADR 0004](adr/0004-pi-worker-reviewer.md) 결정 A(채택됨, 2026-11-18)가 대체했다.** 워커는 Pi 하네스로 실행하고 모델은 `claude`, `gemini`, `muse`다(`codex`는 뺐다). 대체된 곳에는 "대체됨 → ADR 0004" 표시를 달았다. 2단계 구현의 임시값은 "임시(이슈 #2)"로 표시했다.
- `docs/history/`(이 저장소에 없음)는 사람이 확인하려고 만든 이력 문서이므로 **읽지 않는다.** 이 문서의 근거로도 링크하지 않는다.
- `[보충]` 표시는 인터뷰 답을 문서로 풀어 쓰며 작성자가 덧붙인 해석이나 판단이다. 인터뷰에서 직접 정한 것이 아니므로 확인이 필요하다.
- 코디네이터, 어드바이저, 리뷰어, 워커의 내부는 설계하지 않는다. 접점만 정한다. 코디네이터 쪽 규칙은 [01-overview.md](01-overview.md)를 따른다.
- 스크립트 이름과 인자는 설계를 설명하는 예시다. 정확한 이름은 구현 계획에서 확정한다.

## 1. 개요

오퍼레이터는 영역 팀을 운영하는 **합치기·보고 담당**이다. 코디네이터가 하달한 이슈를 워커에게 맡기고, 워커의 결과를 머지 큐로 통합 브랜치에 합치고, 결과 보고서를 이슈 댓글로 올린다. `main`은 사용자가 반영을 결정한 뒤 반영 모드에서만 바꾼다.

- 오퍼레이터는 **Claude 모델의 독립 세션**이다. 코디네이터가 시작 스크립트로 띄우고, 일이 끝나면 종료한다.
- 워커는 ~~`claude`, `codex`, `gemini`, `muse` 중~~ 이슈에 적힌 모델로 부른다. **(대체됨 → ADR 0004 결정 A: 모델은 `claude`, `gemini`, `muse` 중 하나이고 워커는 Pi로 실행한다. 지금은 `muse`만 Pi를 거치고 `gemini`는 `agy` 직접, `claude`는 `claude -p` 직접이다: 임시(이슈 #2).)** 오퍼레이터와 코디네이터는 Claude로 고정한다.
- 가장 먼저 풀 문제는 **안전과 격리**다. 병렬, 예산, 영역 확장은 이 위에 얹는 것이라 이번 범위 밖이다.

```
사용자 ── 코디네이터 ──(시작 스크립트)──▶ 오퍼레이터 [독립 세션, Claude]
                                            └──(워커 호출, 모델 선택)──▶ 워커 [claude / gemini / muse]
```

(그림의 워커 모델은 ADR 0004 결정 A에 맞췄다. `codex`는 뺐다.)

## 2. 하는 일과 하지 않는 일

| 하는 일 | 하지 않는 일 |
|---|---|
| 하달된 이슈를 읽고 시작 전에 검토한다 | 이슈를 만들거나 쪼개거나 완료 기준을 바꾸지 않는다(코디네이터와 사용자) |
| 의존 순서를 정하고 워커를 이슈에 적힌 모델로 부른다 | 작업을 위한 코드는 직접 고치지 않는다(워커) |
| 워커 결과를 머지 큐에 넣어 통합 브랜치에 합친다 | 허용/거부 판정을 하지 않는다(리뷰어) |
| 합칠 때 생기는 충돌을 영역 담당 브랜치 폴더에서 해결한다 | 제안문을 쓰지 않는다(어드바이저) |
| 결과 보고서와 조사 결과를 이슈 댓글로 올리고 상태 라벨을 갱신한다 | 사용자와 직접 대화하지 않는다(코디네이터) |
| 반영 모드에서 허용된 이슈만 `main`에 병합한다 | 반영 모드가 아닐 때 `main`을 바꾸지 않는다 |

편집 도구는 **영역 담당 브랜치 폴더**(통합 브랜치 폴더)에서만 쓸 수 있다. 쓰임새는 충돌 해결이라고 `[보충]` 해석했다. 훅은 충돌 해결과 일반 수정을 구분하지 못하므로, 오퍼레이터가 만든 커밋은 작성자로 표시하고 CI를 한 번 더 돌린다(6.3절).

## 3. 세션과 스크립트

### 3.1 진입점

코디네이터와 오퍼레이터는 **하네스가 정한 스크립트의 정해진 모양만** 실행할 수 있다. `main`에 쓰는 경로는 `run-reflect` 하나다.

| 스크립트 | 호출하는 쪽 | 하는 일 | 세션 |
|---|---|---|---|
| `run-operator` | 코디네이터 | 작업 모드: 이슈 묶음 처리(4절) | 오퍼레이터(Claude), 하달 하나에 세션 하나 |
| `run-research` | 코디네이터 | 조사 모드: 조사 이슈 처리(7절) | 오퍼레이터(Claude), 기다리지 않고 바로 시작 |
| `run-reflect` | 코디네이터 | 반영 모드: 허용된 이슈를 `main`에 병합(8절). 오퍼레이터 세션을 띄우지 않고 스크립트가 직접 병합한다 | 없음 |
| `stop-operator` | 코디네이터 | 진행 중인 하달의 모든 세션을 프로세스 단위로 종료하고 이름 공간을 정리 | - |
| `run-worker` | 오퍼레이터 | 워커 하나를 지정한 모델로 시작(5절) | 워커(지정 모델) |
| `run-reviewer` | 코디네이터 | 결과 보고서 리뷰어 판정(6.4절). 리뷰어는 Jev(TypeSafe System One, HTTP API)다. 코드 검사 뒤 완료 기준마다 Jev에 묻고 스크립트가 허용·거부를 정해 이슈 댓글로 남긴다(ADR 0008이 ADR 0004 결정 B·C의 리뷰어 실행을 대체). 조언 판정(`--advice <파일> --advice-id <id>`)은 어드바이저가 부른다(ADR 0006) | 리뷰어(Jev) |

### 3.2 하달 번호와 수명

- 시작 스크립트가 **하달 번호** `h<N>`을 발급한다. 단조 증가하는 번호로 `[보충]` 해석했다. 하달 번호는 브랜치, 워크트리, 로그, 정리의 단위다.
- 한 하달은 오퍼레이터 세션 하나다. 일이 끝나면(결과 보고서를 올리면) 세션은 닫힌다.
- **같은 하달 안의 재작업은 지원하지 않는다**(이 버전). 재작업은 **새 하달**로 한다. 앞선 하달의 허용된 결과를 먼저 반영하지 않아도 된다(소유자 결정 2-3, 2026-11-18). 그래서 재작업 한도 안에서는 사용자 개입 없이 돈다(시나리오 7·9).
  - `run-operator`는 새 하달을 시작할 때 이슈 상태를 본다. 합치기 스크립트가 건너뛰는 상태(`허용됨`, `보류`, `막힘`)와 라벨 없음은 `진행중`으로 되돌린다. 그래야 새 하달의 결과가 통합 브랜치에 합쳐지고 다시 리뷰된다. `반영됨`, `거부목록`은 건드리지 않는다.
  - **재작업 한도:** 이슈에 올라온 `## 결과 보고서` 댓글 수가 거부 한도(`rejectLimit`, 이슈당 2)+1 이상이면 이미 재작업을 한도만큼 한 것이다. 그 이슈는 `막힘`으로 두고 세션에서 빼며, 보고 줄에 `막힘`으로 나온다(종료 코드 1). 코디네이터는 이것을 막힌 이슈로 모아 보고한다(소유자 결정 2-1). 보고서 없이 끝난 하달(결과 없음)은 여기에 세지 않는다.
  - **결과 없음 한도:** 보고서 수가 늘지 않고 끝난 새 하달을 이슈마다 연달아 센다(`handoffs/no-report.json`, 보고서가 늘면 지운다). 1 + `noReportRetries`(2)번이면 그 실행에서 `막힘`으로 두고 보고 줄도 `막힘`이다. 한도를 넘긴 이슈는 다시 하달해도 `막힘`이다. 중단(3)·시작 실패(2)·`--handoff` 재시작은 세지 않는다(소유자 결정 2-4, 8-4).
  - 반영(`run-reflect --handoff h<N>`)은 더 뒤의 하달에 같은 이슈의 브랜치가 있으면 그 이슈를 반영하지 않는다(대체된 결과). 허용 판정 뒤에 새 결과 보고서가 올라온 이슈도 새 판정이 나올 때까지 반영하지 않는다.
  - 새 하달의 이슈 브랜치는 `main`에서 시작한다. 그래서 `## 의존하는 이슈` 가운데 이번 하달 밖의 이슈가 허용됐지만 아직 반영되지 않았으면 그 이슈를 `대기`로 두고 세션에서 뺀다. "허용됨"은 라벨이 아니라 합치기 스크립트와 같은 허용 판정 기준(최신 판정이 허용이고 보고서 해시와 묶임, 그 뒤에 새 보고서 없음)으로, "반영됨"은 `run-reflect`와 같이 `main`의 병합 커밋(`병합: 이슈 #N`)으로 본다(허용된 이슈의 라벨은 `리뷰대기`로 남기 때문, 이슈 #23). 보고 줄은 `대기`이고 종료 코드는 1이다. 코디네이터가 사용자 결정으로 의존 이슈를 반영한 뒤 다시 하달한다. 같은 `--issues` 안의 의존은 보지 않는다(소유자 결정 8-5).
- `--handoff h<N>`은 이미 있는 하달의 재시작용이고, 그 하달에 이슈·통합 브랜치가 남아 있으면 사람이 `--force-restart`를 붙여야만 시작한다(실패 시 정리가 그 하달의 허용된 작업까지 지우므로 코디네이터의 허용 모양에는 없다). 재시작은 재작업으로 세지 않는다.
- **조사**는 진행 중인 하달과 상관없이 기다리지 않고 별도 세션으로 바로 시작한다.
- 이름 규칙: 통합 브랜치 `integration/h<N>`, 이슈 브랜치 `h<N>/issue-<번호>`, 워크트리 폴더 `worktrees/h<N>/issue-<번호>`.

## 4. 작업 하달 흐름

1. 코디네이터가 이슈를 올린다. 본문에 `워커 모델`과 `유형`이 있고 상태는 `진행중`이다. 코디네이터가 `run-operator`를 호출한다.
2. 오퍼레이터 세션이 뜨고 이슈를 읽는다.
3. **시작 전 검토:** 완료 기준이 모호하거나 서로 충돌하거나 확인 방법이 실행 불가능하면, 그 이슈를 `막힘`으로 두고 **제안 / 이유 / 예상 결과** 양식의 질문을 보고서 댓글로 올린다. 다른 이슈는 계속한다.
4. 의존 순서를 정한다. 의존 없는 이슈는 **상한 없이 동시에** 처리한다.
5. 워커를 부른다(5절). 워커는 이슈별 워크트리에서 일하고 결과 파일을 쓰고 끝낸다. 못 끝내면 **2회 재시도**(총 3번 시도)하고, 그래도 안 되면 그 이슈를 `막힘`으로 두고 의존 이슈만 `보류`한다. 나머지는 계속한다.
6. 워커 결과를 **머지 큐**에 넣어 순차 CI를 돌리고, 통과하면 통합 브랜치에 합친다(6절).
7. 오퍼레이터가 이슈마다 결과 보고서를 댓글로 올린다(10.2절). 상태는 `리뷰대기`다.
8. **리뷰어**가 판정한다(6.4절). 거부되면 `미완료`로 둔다. 같은 하달의 재작업은 지원하지 않고 새 하달로 다시 한다. 앞선 허용 결과를 반영하지 않아도 된다(3.2절).
9. 허용된 보고서를 코디네이터가 완료 기준과 대조하고 사용자에게 보고한다.
10. 사용자가 `main` 반영을 결정하면 코디네이터가 `run-reflect`를 호출한다(8절).

세션이 죽거나 멈추면 **그 하달의 이름 공간을 정리하고 처음부터 1회 다시 시작**한다. 두 번째 실패는 그 이슈를 `보류`하고 사용자에게 보고한다.

## 5. 워커 접점

### 5.1 모델 선택

- 어드바이저가 작업 단위마다 맞는 모델을 구분해 제안문에 적고, 코디네이터가 이슈의 `워커 모델` 칸에 적고, 오퍼레이터가 그 모델로 워커를 부른다.
- 모델은 ~~`claude`, `codex`, `gemini`, `muse`~~ **`claude`, `gemini`, `muse`(대체됨 → ADR 0004 결정 A, `codex`는 뺐다)**다. 설정 파일의 **허용 목록** 안에서만 쓸 수 있다. 목록은 사용자만 고친다. `[보충]` 샌드박스를 확인하지 못한 모델은 확인될 때까지 목록에서 뺀다.
- 지정된 모델을 쓸 수 없으면(CLI 없음, 허용 목록 밖) `run-worker`가 설정 파일의 **대체 표**대로 다른 모델을 쓴다. 대체 모델도 허용 목록 안이어야 한다. 대체 표는 **순환형** `claude` → `gemini` → `muse` → `claude`다(소유자 결정 5-3). 대체 모델도 쓸 수 없으면 표의 다음 모델로 가고, 한 바퀴 돌아 지정 모델로 돌아오면 멈춘다(쓸 모델이 없으면 종료 코드 2). 러너를 띄우지 못한 경우(실행 실패)는 대체하지 않고 종료 코드 2다.
- **`muse`로 대체할 때의 공개 확인:** **(실행 폴더의 `operator.local.json`으로 끌 수 있다 → ADR 0007, 소유자 결정 8-6. 아래는 공개 기본 설정의 동작이다.)** `muse`는 Contributor 등급이라 입력이 학습에 쓰일 수 있다. 그래서 대체로 `muse`에 들어가는 것은 이슈 본문에 `공개 가능: 예` 줄이 정확히 한 줄 있을 때만이다(설정의 `runners.muse.publicOnly`). 표시가 없으면 `muse`를 건너뛰고 다음 모델로 간다. 건너뛴 뒤 쓸 모델이 남지 않으면 그 이슈는 `막힘`(종료 코드 1)이다. `muse`가 지정 모델이면 이 확인을 하지 않는다.
- 대체가 일어나면 `run-worker` 출력에 `requestedModel`(지정), `model`(실제로 띄운 모델 타입), `replacedReason`(사유)이 남는다. 오퍼레이터는 결과 보고서 사실 칸에 `모델: <지정> → <실제>`와 사유, 그리고 `실제 워커 모델: <실제 모델 타입>` 한 줄을 적는다. `run-reviewer`는 이 줄이 있으면 이슈 본문의 `워커 모델` 대신 이 값으로 리뷰어를 고른다(실제로 쓴 모델 타입과 다른 리뷰어).

### 5.2 입력과 출력

- **입력:** 이슈 본문, 워크트리 경로, 재시도 때 이전 실패 이유뿐이다. 다른 이슈, 코디네이터와 사용자의 대화는 넘기지 않는다.
- **출력:** 워커는 워크트리 안의 고정 파일 `.harness/worker-result.md`에 결과를 쓰고 종료한다(커밋 대상 아님). 칸은 이슈 번호, 변경 요약, 테스트 명령과 결과, 커밋 해시다. `[보충]` 워커에게는 이슈 댓글 같은 외부 쓰기 권한을 주지 않는다.
- 결과 보고서는 언제나 오퍼레이터가 쓴다. 워커의 파일은 입력 재료다.

## 6. 합치기와 CI

### 6.1 통합 브랜치

- 워커 결과는 `main`이 아니라 **통합 브랜치** `integration/h<N>`에 합친다. `main`은 사용자가 반영을 결정할 때까지 바뀌지 않는다.
- 리뷰어가 거부하면 그 이슈를 **미완료로 표시**한다. 같은 하달 안의 재작업(통합 브랜치에 그 범위만 다시 포함)은 이 버전에서 지원하지 않는다: `run-worker`가 이미 있는 이슈 브랜치를 거부하고, 이미 거부된 병합이 남은 통합 브랜치 위에서는 충돌한다. 재작업은 새 하달로 한다(3.2절). 미완료 표시는 상태 라벨 `미완료`와 보고서의 미완료 범위 표기로 한다고 `[보충]` 해석했다.
- 재작업이 정해진 횟수(이슈당 2회, 시작값)를 넘으면 `run-operator`가 그 이슈를 `막힘`으로 두고 다시 하지 않는다(3.2절, 소유자 결정 2-1). (옛 문구: 거부 이슈 목록 `거부목록`에 등록한다. 코디네이터 규칙이 결정 2-1에 맞춰 바뀌면 함께 정리한다.)

### 6.2 머지 큐 (GitHub 머지 큐 기능 사용)

- 워커 결과를 큐에 줄 세운다. 대기열용 임시 브랜치에서 앞선 변경이 모두 반영된 상태를 가정하고 CI를 순차로 돌린다. 합쳐진 상태에서도 깨지지 않는지 확인하고 병합 순서를 통제하려는 것이다.
- **테스트 캐싱:** 입력(코드, 의존성)이 바뀌지 않은 통과 테스트는 다시 돌리지 않는다. 대기열이 길어져도 CI 시간이 선형으로 늘지 않게 하는 장치다.
- **실패 처리:** 큐의 변경을 순서대로 CI에 통과시킨다. 하나라도 실패하면 그 변경을 반려해 큐에서 뺀다. 워커가 고쳐 다시 큐에 넣는다. 반려된 변경 뒤의 항목은 그 변경을 뺀 상태로 CI를 다시 돌린다.
- **병합 후 정리:** 병합이 끝나면 대기열용 임시 브랜치, 워크트리, 캐시 중 필요 없는 것을 정리한다. 원문의 "CI Compact"가 정확히 무엇을 뜻하는지는 확인하지 못했고, 이 정리는 `[보충]` 해석이다.
- **CI에 올리지 않는 것:** 스모크 테스트와 오케스트라 테스트. 사고별 어겨 보기 시험(13절)은 CI 밖에서 돌린다.
- **전제(미확인):** GitHub 머지 큐는 조직 소유 저장소 등 조건이 있고 개인 계정 저장소에서는 쓸 수 없어 보인다. 시험용 메모 저장소는 로컬 전용이라 머지 큐를 쓸 수 없고, 로컬에서 같은 순서(이슈별 순차 테스트)를 흉내 내는 시험 방법이 따로 필요하다. 지금 메모 저장소는 **시험용**임을 잊지 않는다. ADR 0003 미확인 사항 표를 보라.

### 6.3 오퍼레이터의 편집

- 편집 도구는 영역 담당 브랜치 폴더(통합 브랜치 폴더)에서 **항상 허용**한다.
- 훅은 "무엇을 위한 편집인가"를 구분하지 못하므로 다음으로 보완한다. `[보충]`
  - 오퍼레이터가 만든 커밋은 작성자를 따로 표시해 워커의 커밋과 구분한다.
  - 작성자가 오퍼레이터인 커밋이 있으면 머지 큐 CI를 **한 번 더** 돌린다.
  - 결과 보고서에 "오퍼레이터 편집 있음"과 변경 파일을 적어 리뷰어가 보게 한다.
- "작업을 위한 코드는 직접 고치지 않는다"는 훅이 아니라 이 표시와 재검사로 확인한다. 훅이 막지 못한다는 한계는 ADR 0003에 적는다.

### 6.4 리뷰어 판정

- 순서는 **워커 완료 → 머지 큐(CI) → 통합 브랜치에 합침 → 리뷰어 판정**이다. 리뷰어는 CI 통과 기록을 근거로 본다.
- **(ADR 0008, 이슈 #44)** 리뷰어는 Jev다. 스크립트가 실제로 보는 것: 보고서 머리줄과 `커밋 해시:` 한 줄, 네 칸, 이슈의 완료 기준 표, 근거 위치에 적힌 파일이 보고서 커밋에 있는지(코드), 완료 기준마다 충족으로 적혔는지와 근거 위치가 구체적인지(Jev Noul, 0.7 이상만 예). 아래 세 검사는 지금 스크립트가 보지 않는다(코디네이터의 대조와 훅이 일부를 맡는다).
- 리뷰어의 사후 검사는 세 가지다. 리뷰어 내부는 설계하지 않으므로 접점으로만 적는다.

| 검사 | 확인하는 것 | 오퍼레이터가 보고서에 적어야 하는 자료 |
|---|---|---|
| 변경 파일 범위 | 변경 파일이 해당 이슈 워크트리 안에만 있다 | 이슈별 변경 파일 목록(`git diff --stat`) |
| `main` 해시 불변 | 하달 시작 때의 `main` 해시와 같다 | 시작 때와 지금의 `main` 해시 |
| 비밀값 | 보고서와 변경에 비밀값이 없다 | 없음(리뷰어가 직접 확인) |

- CI 통과는 머지 큐가 강제하므로 리뷰어 검사 항목에 넣지 않는다.
- 거부되면 그 이슈를 큐에서 빼고 `미완료`로 표시하며, 뒤 항목의 CI를 그 이슈를 뺀 상태로 다시 돌린다.

## 7. 조사 모드

- 조사도 **이슈로 하달**하고 **최우선**으로 처리한다. 이슈 `유형`은 `조사`다. 코디네이터가 이슈를 올리고 `run-research`를 호출하면 진행 중인 작업을 기다리지 않고 별도 오퍼레이터 세션이 바로 뜬다.
- 조사 세션은 대상 프로젝트에 대해 **읽기 전용**이다. 쓸 수 있는 것은 지정 저장소의 이슈 댓글(결과 파일 작성 포함)뿐이다.
- 결과는 **오퍼레이터가 직접** 이슈 댓글로 올린다. 훅이 올리기 전에 본문 파일의 비밀값과 양식을 검사한다. 리뷰어는 거치지 않는다. 결과는 세 칸(답, 근거 위치, 못 찾은 것) 50줄 이하이고 **기준 커밋 해시**를 붙인다(조사하는 동안 `main`이 바뀔 수 있기 때문이다).
- **어드바이저의 조사 요청:** 어드바이저가 코디네이터에게 어느 영역의 자료가 필요한지 명시해 요청하면, 코디네이터가 영역을 읽고 해당 영역 오퍼레이터에게 어느 어드바이저에게 전달할지 알려 조사를 요청한다. 오퍼레이터가 정리본을 지목된 어드바이저에게 직접 전달하고 코디네이터에게는 **전달 완료**만 알린다.
- **"직접 전달"의 구현은 `[보충]` 해석이다.** 어드바이저는 코디네이터의 하위 에이전트라서 독립 세션인 오퍼레이터가 내용을 밀어 넣을 통로가 없다. 그래서 조사 이슈 댓글에 `전달 대상 어드바이저`를 명시하고, 어드바이저가 다음에 불릴 때 그 댓글을 읽는다. 코디네이터는 내용을 읽지 않고 어드바이저를 부를 때 URL만 넘긴다.

## 8. 반영 모드

- 사용자가 코디네이터의 보고를 보고 `main` 반영을 결정하면, 코디네이터가 `run-reflect`를 호출한다. 이 스크립트가 오퍼레이터 세션 없이 직접 허용 수집, 의존 제외, 병합, `반영됨` 표시를 한다. (`MODES`·`TOOLS`·훅 프로필의 `reflect` 항목은 현재 쓰이지 않는다.)
- **허용된 이슈의 커밋만** 골라 `main`에 병합한다. 거부 이슈와 거기에 의존하는 이슈는 빠진다. 반영할 때 허용된 이슈를 설명(병합 설명)에 적는다. `[보충]` 설명에는 이슈 번호, 허용된 해시, 리뷰어 허용 댓글 URL을 적는다.
- 반영도 **머지 큐**를 거친다. 허용된 조합은 앞에서 테스트한 통합 브랜치와 같지 않을 수 있으므로, 큐가 그 조합에 대해 CI를 다시 돌린 뒤 `main`에 병합한다.
- 병합 방식(병합 커밋, 스쿼시 등)은 큐 설정에 달려 있고 **미확인**이다.
- `main`을 쓸 수 있는 순간은 **사용자 결정 뒤 반영 모드 세션**뿐이다. 훅은 반영 모드에서 리뷰어 허용 기록이 있는 해시만 `main`에 쓰도록 판정한다.

## 9. 안전과 격리

### 9.1 막을 사고와 어겨 보는 시도

| 사고 | 어겨 보는 시도 | 기대 결과 | 막는 장치 |
|---|---|---|---|
| a. `main` 훼손 | 작업 모드의 오퍼레이터가 `git -C <대상> checkout main` 후 커밋, `reset --hard` | 거부 | 훅(반영 모드가 아니면 `main` 쓰기 거부). 훅 없는 워커는 샌드박스(확인 필요)와 리뷰어의 `main` 해시 검사 |

| d. 비밀값 노출 | 보고서나 이슈 댓글에 가짜 토큰(`ghp_`+36×A)을 적으려는 시도 | 거부 또는 게시 전 차단 | 훅의 토큰 모양 검사, 다른 모델은 리뷰어의 비밀값 검사 |
| e. 다른 이슈 침범 | 이슈 8 워커가 이슈 7 워크트리의 파일을 수정 | 거부 | 훅(자기 하달·이슈의 이름 공간 밖 쓰기 거부), 다른 모델은 리뷰어의 변경 파일 검사 |

끝없는 재시도(f)는 이번에 막지 않는다(15절).

### 9.2 훅 프로필

판정은 `policy.mjs`를 확장해 한 곳에서 한다. 아래는 `[보충]`으로 정리한 프로필이며 구현 계획에서 확정한다.

| 모드 | 읽기 | 쓰기와 편집 | 명령 | 하위 에이전트 |
|---|---|---|---|---|
| 작업(오퍼레이터) | 대상 프로젝트, 워크트리, 지정 저장소(비밀값 파일도 참조로 읽기 가능) | 쓰기: 지정 저장소 클론의 `.drafts/`. 편집: 영역 담당 브랜치 폴더만 | `gh issue … --repo <지정 저장소>`(댓글, 라벨), 자기 하달 이름 공간의 `git`, 워커 시작 스크립트. `main` 쓰기 없음 | ~~Claude 워커만(`isolation: "worktree"`)~~ (대체됨 → ADR 0004 결정 A: 워커는 `run-worker`로 부른다) |
| 조사(오퍼레이터) | 위와 같음 | 쓰기: `.drafts/`만. 대상 프로젝트는 읽기 전용 | `gh issue comment`(자기 조사 이슈), `gh issue view` | 없음 |
| 반영(오퍼레이터) | 위와 같음 | 쓰기: `.drafts/`만 | `main` 병합은 허용된 해시와 큐를 거칠 때만 | 없음 |
| 워커(모든 모델) | 자기 워크트리, 비밀값 파일 참조 가능 | 자기 워크트리 안만. 하네스·실행 폴더 제어 파일은 모든 역할이 쓸 수 없다 | 자기 워크트리 안의 테스트·빌드 명령 | 없음 |

훅이 없는 모델의 워커는 이 프로필을 훅으로 강제할 수 없다. 모델별 샌드박스와 리뷰어 검사가 대신하며, 그 확인이 선행 작업이다(15절).

### 9.3 비밀값

- 오퍼레이터와 워커는 비밀값 파일(`.env` 등)을 **참조로 읽을 수 있다.** 값을 이슈 댓글, 보고서, 커밋, 로그에 쓰는 것은 금지한다.
- 토큰 모양(`ghp_`, `sk-`, `AKIA` 등)은 훅이 막고, 비밀값 확인은 리뷰어의 검사 항목이다. 토큰 모양이 아닌 값(일반 비밀번호 등)은 걸리지 않을 수 있다는 한계가 있다.

### 9.4 감사 로그

- 훅 판정(허용, 거부, 이유)은 **하달별로** `logs/<하달 번호>/`에 남긴다. 동시 세션의 기록이 섞이지 않고, 어겨 보기 시험의 증거를 하달 번호로 찾는다.
- 모든 역할이 이 폴더를 고칠 수 없다. 오래된 하달 로그를 지우는 규칙은 이번 범위 밖이다.

## 10. 양식과 신호

### 10.1 이슈에 추가되는 칸 (overview 4.1절에 더해짐)

| 칸 | 내용 |
|---|---|
| 워커 모델 | `claude`, `gemini`, `muse` 중 하나(허용 목록 안. ADR 0004 결정 A로 `codex`는 뺐다). 어드바이저의 구분을 코디네이터가 옮겨 적는다 |
| 유형 | `작업` 또는 `조사` |
| 전달 대상 어드바이저 | 유형이 `조사`일 때만. 정리본을 받을 어드바이저. `[보충]` |
| 공개 가능 | `공개 가능: 예`이면 공개해도 되는 이슈다. 대체로 `muse`에 들어갈 수 있다(5.1절). 없으면 공개 불가로 본다. 실행 폴더의 로컬 설정이 제한을 끄면 영향이 없다(ADR 0007) |

### 10.2 결과 보고서 (overview 4.2절에 더해짐)

| 항목 | 내용 |
|---|---|
| 기준별 충족 여부, 근거 위치, 변경 요약, 남은 문제 | overview 4.2절과 같다 |
| 커밋 해시 | 이슈 브랜치와 통합 브랜치의 해시(반영 모드가 허용된 해시를 찾는 연결 고리) |
| 모델(지정 → 실제) | 대체가 없었으면 같은 값. 대체가 있었으면 사유. 실제 모델 타입은 `실제 워커 모델: <타입>` 한 줄로도 적는다(리뷰어 순환이 읽는다) |
| 시도 횟수 | 워커 시도 횟수와 막힘 사유 |
| 사후 검사 자료 | 변경 파일 목록, 하달 시작과 지금의 `main` 해시, 오퍼레이터 편집 여부. 판정은 리뷰어가 한다. `[보충]` |

사실 칸(해시, 모델, 시도 횟수, 사후 검사 자료)을 **오퍼레이터가 모두 작성**한다. 스크립트가 자동 생성하지 않는다.

### 10.3 상태 라벨

| 상태 | 뜻 | 바꾸는 쪽 `[보충]` |
|---|---|---|
| `진행중` | 워커가 작업 중 | 오퍼레이터 |
| `리뷰대기` | 합쳐서 리뷰어에게 올림 | 합치기 스크립트(enqueue) |
| `허용됨` | 리뷰어가 허용 | 코디네이터(리뷰어 판정을 읽고) |
| `미완료` | 합치기가 거부했거나 리뷰어가 거부함. 같은 하달에서는 다시 하지 않는다 | 합치기 스크립트(enqueue) |
| `막힘` | 워커가 3번 시도하고도 못 끝냈거나 시작 전 검토에서 걸림, 재작업 한도 초과(3.2절), 쓸 모델이 없음(5.1절) | 오퍼레이터, `run-operator`(재작업 한도) |
| `거부목록` | 거부 횟수 한도를 넘겨 거부 이슈 목록에 등록(옛 규칙. 결정 2-1로 재작업 한도 초과는 `run-operator`가 `막힘`으로 둔다. 코디네이터 규칙 정리 대기) | 코디네이터 |
| `대기` | 의존하는 이슈가 허용됐지만 아직 반영되지 않아 이번 하달에서 뺌(3.2절) | `run-operator` |
| `보류` | 의존 이슈 막힘, 중단, 모델 문제 등으로 멈춤 | 오퍼레이터 |
| `반영됨` | 사용자 결정으로 `main`에 병합됨 | `run-reflect` |

합치기 스크립트(enqueue)는 이미 `막힘`·`보류`·`거부목록`·`반영됨`·`허용됨`·`대기`인 이슈를 합치지도 라벨을 바꾸지도 않고, 이미 `main`에 있는 이슈도 건너뛴다. 새 하달로 다시 하는 이슈는 `run-operator`가 세션 전에 `진행중`으로 되돌린다(3.2절). 상태 라벨 9개(`대기` 포함)와 `취소` 라벨은 `setup`·`run-operator`·`run-research`가 세션 전에 만들고(`gh label create --force`), 조사 이슈처럼 라벨이 없는 이슈는 보고에서 `라벨 없음`으로 나온다.

상태 갱신에는 갱신 시각을 함께 적어, 오퍼레이터가 죽어 낡은 상태가 남았는지 알 수 있게 한다. `[보충]`

### 10.4 스크립트 출력과 종료 코드

- 스크립트가 코디네이터에게 돌려주는 출력은 **이슈마다 번호, 상태, URL뿐**이다. 한 줄 요약은 돌려주지 않는다. 더 알고 싶으면 사용자가 해당 작업만 요청한다.
- 종료 코드:

| 코드 | 뜻 | 코디네이터의 행동 |
|---|---|---|
| 0 | 정상 | 계속 진행 |
| 1 | 일부 이슈가 `막힘`, `보류`, `거부목록` | 계속 진행하고 모아서 보고 |
| 2 | 스크립트·설정 실패(설정 오류, 모델 CLI 없음, 훅 거부, 저장소 접근 불가) | 즉시 멈추고 사용자에게 알림 |
| 3 | 중단 스크립트로 멈춤 | 보류로 기록하고 보고 |

### 10.5 조사 결과 (overview 4.4절에 더해짐)

세 칸(답, 근거 위치, 못 찾은 것) 50줄 이하에 **기준 커밋 해시**를 붙여 이슈 댓글로 올린다.

## 12. 실패와 복구

| 상황 | 처리 |
|---|---|
| 완료 기준이 모호·충돌 | 시작 전 검토에서 `막힘`과 질문. 나머지 이슈는 계속 |
| 워커가 못 끝냄 | 2회 재시도 후 `막힘`, 의존 이슈만 `보류`, 나머지 계속 |

| 진행 중인 하달을 멈추려 함 | `stop-operator`가 세션을 프로세스 단위로 종료하고 이름 공간을 정리 |
| 스크립트·설정 실패 | 종료 코드 2, 코디네이터가 즉시 멈추고 사용자에게 알림 |

## 13. 시험

- **완료 기준:** 9.1절의 사고별 어겨 보기와 정상 경로 종단 시험(이슈 하달부터 보고까지)이 모두 통과한다.
- **훅 없는 모델:** 샌드박스나 리뷰어 검사로 막히면 통과로 본다. 모델마다 어느 장치가 어느 사고를 막는지 표로 정하고, 막는 장치별로 한 번씩 시험한다.
- **실행 시점:** 하네스 파일(훅, 스크립트, 설정, 역할 문서)을 바꿀 때와 `main`에 올리기 전에 **한 명령으로 수동 실행**한다. CI에는 올리지 않는다. 결과는 날짜별 기록으로 남긴다.

## 16. 구현 때 함께 고칠 것 (이번에는 고치지 않음)

구현 계획은 사용자가 따로 요청할 때 시작한다. 이번 인터뷰로 바뀌어 구현 때 맞춰야 하는 파일은 다음과 같다.

# 알려진 한계

Terrarium 하네스 v0를 쓰기 전에 알아야 할 한계다(이슈 #31). 한계마다 지금의 완화책과 근거를 적는다.

## 1. 판정을 위조할 수 있다

- **무엇:** 코디네이터, 오퍼레이터, 리뷰어 스크립트가 모두 같은 `gh` 계정으로 지정 저장소에 쓴다. 그래서 `## 리뷰어 판정: 허용` 댓글의 작성자로는 리뷰어가 쓴 것인지 구별할 수 없다. 같은 계정으로 사람이나 다른 프로그램이 판정 댓글을 쓰면 하네스는 그것을 판정으로 읽을 수 있다.
- **완화:**
  - 오퍼레이터의 훅이 `## 리뷰어 판정`으로 시작하는 댓글을 막는다(제로폭·전각 문자로 위장해도 막는다).
  - 허용 판정은 보고서의 커밋 해시(`허용된 커밋: <40자리>`)와 묶인다. 반영 스크립트는 그 커밋만 `main`에 합친다.
  - 판정 뒤에 새 보고서가 올라오면 새 판정이 나올 때까지 반영하지 않는다.
  - 지정 저장소는 비공개여야 하고, 스크립트가 시작할 때마다 확인한다.
- **남는 위험:** 같은 계정을 가진 사람·프로그램이 판정과 보고서를 둘 다 꾸미는 것은 막지 못한다. 역할마다 다른 GitHub 계정이나 앱을 쓰는 것은 v1이다.
- 근거: `harness/operator/AGENT.md`, `harness/operator/profiles.mjs`, `docs/operator.md` 6.4절.

## 2. OS 샌드박스가 없다

- **무엇:** 워커 세 모델이 모두 Pi로 돌고(ADR 0009), Pi에는 샌드박스가 없다. 워커는 사용자와 같은 권한으로 컴퓨터의 어느 파일이든 읽고 쓸 수 있다. 예전에는 claude 워커에만 Claude Code 훅이 걸렸지만, 지금은 훅이 걸리는 워커가 없다.
- **완화:**
  - 작업 폴더가 이슈 워크트리다(쓰기 제한은 아니다).
  - 워커는 부모의 환경 변수를 통째로 받지 않고, 허용 목록과 그 러너의 `secretEnv`만 받는다. 그래서 Jev 키는 워커에 없다.
  - 사후 검사가 다음을 본다: 새 커밋, 금지 경로(`.claude`, `.git`, `CLAUDE.md` 등) 변경, 결과 파일 모양, `main` 해시 불변. 워커 실행 전후로 작업 폴더 밖의 보호 대상(실행 폴더 설정·비밀값·역할 문서, 하네스 폴더, 대상 프로젝트 본 폴더)도 비교한다. 바뀌면 그 하달은 실패로 끝나고 다시 시도하지 않는다.
  - 합치기 시험, Jev 리뷰어, 코디네이터 대조를 거친다.
- **남는 위험:** 워커가 비밀값 파일(`~/.pi/agent/auth.json`, 실행 폴더 `.env`)을 읽거나 네트워크로 내보내는 것은 막지 못한다. 쓰기도 막지 못하고 알아챌 뿐이다. 신뢰하지 않는 대상 프로젝트나 지시에는 쓰지 않는다.
- 근거: ADR 0009, `harness/operator/run-worker.mjs`, `docs/checks/runs.md`.

## 3. 리뷰어·라우팅이 Jev 한 곳에 달려 있다

- **무엇:** 결과 보고서 판정, 조언 판정, 이슈 라우팅이 모두 TypeSafe의 Jev(System One API)다(ADR 0008). 그래서 TypeSafe 계정과 키(`TYPESAFE_API_KEY`)가 꼭 필요하다. Jev가 멈추거나 고정한 모델 버전(`jev-1.14.0`)이 끝나면 리뷰어와 라우팅이 함께 멈춘다.
- **완화:** 일시 오류(네트워크, 시간 초과, 429, 5xx)는 2번 다시 부른다. 실패는 허용으로 보지 않는다(종료 코드 6, 판정 없음). 애매한 답(0.3~0.7)은 거부한다.
- **남는 위험:** 대체 리뷰어가 없다. 모델 버전이 바뀌면 `operator.config.json`의 `jev.model`을 고치고 `harness/e2e/jev-probe.mjs`로 다시 확인해야 한다.

## 4. Windows에서만 시험했다

- 프로세스 정리(`taskkill`), 합치기 시험 뒤의 PowerShell 정리, 일부 경로 처리는 Windows 우선으로 만들었다. 데스크톱 앱 설치 파일도 Windows용(NSIS)뿐이다. CI는 ubuntu에서 단위 시험만 돈다.
- macOS·Linux에서는 시험하지 않았다.

## 5. 모델 ID가 낡을 수 있다

- `harness/operator/operator.config.json`의 모델 ID(`anthropic/claude-sonnet-5-5`, `anthropic/claude-haiku-5-5`, `google/gemini-4-hydrogen:medium`, `meta/muse-spark-1.3-contributor`, `jev-1.14.0`)는 2026-11 기준이다. 제공사가 모델을 바꾸거나 끝내면 고쳐야 한다. 사전 점검(`preflight.mjs`)이 모델마다 Pi 계정 준비를 확인하지만, 모델이 실제로 응답하는지는 첫 호출에서야 안다.
- 제공사가 혼잡하면(예: Google 503) Pi는 출력 없이 계속 다시 시도한다. `run-worker`는 15분 동안 출력이 없으면 끊고 대체 모델로 넘긴다.

## 6. 데스크톱 앱

- 설치 파일은 코드 서명이 없다(소유자 결정 8-13). 처음 설치할 때 Windows가 "알 수 없는 게시자" 경고를 띄운다. "추가 정보" → "실행"으로 넘긴다.
- 앱은 Claude Code CLI, Node 22 이상, `gh`, Pi를 따로 설치해야 한다.
- 관제탑 카드 다섯은 역할 오퍼레이터(dev·design·tester·plan·sec)다(결정 8-29, ADR 0012). 팀 없는 옛 하달은 카드에 보이지 않고 설정 창 진행 기록에만 있다. 막대는 진행률이 아니라 이슈 라벨 단계다. 카드는 읽기 전용이라 단추로 하달을 멈출 수 없다(ADR 0011 덧붙임). 끝난 시각 없이 프로세스가 사라진 하달(Esc로 끊긴 것 등)은 "끊김"으로 일시정지 표시와 정리 안내가 나온다. `stop-operator`로 정리할 때까지 남는다.
- 코디네이터 터미널을 처음 띄우면 폴더 신뢰 질문이 나온다. **기본 선택이 "No, continue without these permissions"라 Enter만 누르면 No가 된다.** No면 실행 폴더의 허용 목록이 적용되지 않고, Claude Code 문서상 대화형 세션은 신뢰 전에는 설정 파일의 훅(하네스 guard 포함)을 돌리지 않는다. 상위 폴더가 이미 신뢰돼 있으면 훅은 돈다(이 컴퓨터는 `C:/`가 신뢰돼 있어 No에서도 guard가 돌았다, run-18). No는 저장되지 않아 다음에 다시 묻는다. 반드시 Yes를 고른다.
- 하네스는 앱 설치 폴더(`resources/harness`) 안에 있다. 실행 폴더의 `harness.json`이 그 경로를 가리키므로, 앱을 지우거나 다른 폴더로 다시 설치하면 기존 실행 폴더는 `setup --refresh`로 다시 맞춰야 한다.

## 7. 그 밖에

- 기록 문서(`records/<프로젝트>.md`)는 지정 저장소에 있다. 대상 프로젝트를 바꾸며 같은 지정 저장소를 다시 쓰면 기록이 어긋나 보인다(`docs/checks/runs.md` run-7). 대상 프로젝트마다 지정 저장소를 따로 만든다.
- 코디네이터의 컴팩션(`PreCompact` 훅) 동작은 실제로 확인하지 않았다(시나리오 10).
- 여러 어드바이저의 협의(overview 2.3)는 결정 8-24의 패널로 들어왔다: 같은 `advisor` 정의를 세 자리로 불러 초안을 나누고 추천으로 고른다(자기 추천 금지는 결정 8-26). 분야별로 다른 어드바이저 정의를 두는 것은 v1이다. v0의 어드바이저 정의는 대상 프로젝트 전체를 맡는 하나다.

## 8. 분리 실행과 대화의 한계 (2026-11-20 fable 조언 2)

- 하달·조사·워커는 Bash 도구의 10분 제한을 넘기려고 분리 실행한다(`background.mjs`). 그런데 오퍼레이터 세션이 시간 초과나 실패로 끝나면 분리된 워커가 계속 돌 수 있다. 새 세션이 `session.json`을 덮어쓰면 `stop-operator`가 그 워커를 못 찾는다. 이럴 때는 작업 관리자에서 남은 `node`·`pi` 프로세스를 끝낸다.
- 대기 번호 줄은 9분 기다림이 끝난 뒤에만 나온다. 코디네이터·오퍼레이터가 Bash 호출의 `timeout`을 600000으로 주지 않으면 번호를 잃을 수 있다. 훅은 이 값을 강제하지 않는다(규칙 문서에만 있다).
- **코디네이터는 하달이 도는 동안 사용자 말을 듣지 못한다.** 한 턴이 하달이 끝날 때까지 이어지기 때문이다. 작업 중 요구를 바꾸려면 하달을 멈추고(`stop-operator`) 다시 말한다(시나리오 8). 앱의 코디네이터는 대화형 터미널이라 Esc로 턴을 끊을 수 있다(ADR 0011). `run-operator`가 기다리는 중에 Esc를 누르면 예전에는 하달이 통째로 죽었다(run-18 h5). 이제 분리 실행이 곧 끝나는 발사 프로세스를 거쳐 Esc에도 하달이 살아남고(가짜 하달로 확인: 끊은 뒤 끝까지 돌고 `wait-operator`가 결과를 받음), 코디네이터는 다음 턴에 `handoffs/last-wait.json`의 대기 번호로 이어 기다린다(결정 8-21, 진짜 하달 run-18 h8에서 확인). 남은 것: 하달이 정말 죽었을 때의 정리 단계는 진짜 하달로 돌려 보지 않았다. 죽은 하달은 죽은 하달은 관제탑·진행 기록에 "끊김"으로 보이니 `stop-operator --handoff h<N>`으로 정리한다. 하달을 멈추려면 Esc가 아니라 `stop-operator`를 쓴다.
- 같은 지정 저장소를 쓰는 실행 둘이 동시에 기록 문서를 푸시하면 충돌하고, 코디네이터는 merge·rebase가 허용되지 않아 멈춘다(7번과 같은 뿌리).
- 앱의 키 보관 경로(safeStorage → 환경 변수 → 리뷰어·라우팅)는 실제 키로 끝까지 시험하지 않았다. 개발 중에는 저장소 `.env`가 먼저 읽혀 가려졌다.
- 역할 스킬(결정 8-22)은 run-18 h9와 2026-11-21 진짜 실행(h10~h16)에서 코디네이터 스킬 10개와 어드바이저 스킬 2개가 모두 실제로 불렸다(어드바이저 스킬 수는 그 실행 때 기준이다. 2026-11-22 지금은 `advisor-proposal`, `advisor-data-request`, `advisor-domain-knowledge`, `advisor-panel` 4개다). 코디네이터가 다른 역할의 스킬을 못 부르게 하는 훅도 진짜 세션에서 거부를 확인했다. 남은 것:
  - `coordinator-records`는 정리본 승인 요청 때는 불렸지만, 반영·조사·예외 보고 때의 기록은 스킬 없이 CLAUDE.md만 보고 썼다(내용은 규칙대로).
  - 컴팩션 뒤 첫 답은 `컴팩션 복구: 완료`로 시작했지만, 보존 노트를 다시 Read하지 않고 기록 문서를 Grep 한 번 한 뒤 "완료"라고 했다. 확인 단계가 지켜지는지는 문장이 아니라 훅으로 막아야 할 수 있다.
  - 조사 이슈는 결과 댓글이 올라가도 상태 라벨이 `진행중`이고 열린 채 남는다. 출력 줄도 이슈 URL만 준다. 코디네이터가 이것을 이상으로 보고 자료 요청 결과를 직접 읽은 일이 있어(#42), `coordinator-research`에 "종료 코드 0이면 댓글이 올라간 것"을 적었다(#43에서 그대로 따름).
  - 어드바이저의 자료 요청은 대개 대상 프로젝트 밖의 사실(바깥 서비스의 동작)을 묻는데, 조사 세션은 대상 프로젝트만 읽고 웹을 읽지 못한다(훅이 web-fetch를 막음). 그래서 #42·#43은 "확인 불가"로 끝났고 어드바이저는 두 번째 자료 요청을 냈다. 소유자가 웹 읽기를 허용해(2026-11-21) 조사 세션은 WebFetch·WebSearch와 web-fetch 하위 에이전트(그 안에서는 웹 읽기 도구만)를 쓴다. 진짜 실행(run-18 h17 #43, h18 #44)에서 조사 세션이 web-fetch 하위 에이전트로 Notion 도움말을 읽고 출처 주소를 붙여 답했고, 코디네이터가 그 결과 파일을 같은 조언 id(adv-notionwarn-3)로 어드바이저에게 넘겼다. 어드바이저는 문법별 공식 근거가 없다며 제안문 대신 자료를 다시 요청했다(사실이 공개돼 있지 않은 경우, 직접 가져와 보는 시험은 조사 모드로 할 수 없다). 검색 엔진(DuckDuckGo)은 봇 확인 화면으로 막혔다. 웹 페이지 글이 지시처럼 읽히는 위험은 조사 세션이 이슈 댓글과 결과 파일만 쓸 수 있다는 것으로만 막는다.
- 어드바이저 분야 지식(결정 8-23)은 시험에서 파일 전체를 시스템 프롬프트에 넣고 풀게 해서 골랐다. 설치된 어드바이저가 맞는 분야 파일을 스스로 Read하는지는 run-18 h20에서 한 번 확인했다(보안 지시에 `security.md`만, 패널 세 자리 가운데 하나만 읽음). h21~h23에서 웹(`web.md`·`security.md`), 마케팅(`marketing.md`), 분야 없음(읽지 않음)도 맞게 골랐다. 앱·게임·디자인은 아직 진짜 실행으로 보지 않았다. 조사 모드의 비밀값 차단은 Read·Grep·Glob만 막고, 이미 커밋된 비밀값은 `git show HEAD`·`git diff <ref>`로 보일 수 있다.

## 9. GitHub 지정 저장소가 꼭 있어야 한다

- **무엇:** 이슈, 제안문, 판정, 보고서, 기록 문서가 모두 사용자의 비공개 GitHub 저장소(지정 저장소)에 있다. 그래서 GitHub 계정, `gh` 로그인, 비공개 저장소 하나가 꼭 필요하다.
- **완화:** `setup --create-repo`가 없는 저장소를 비공개로 만들어 준다(결정 8-28). 앱 설치 화면은 만들기 전에 묻는다.
- **v1 이후 할 일:** 이슈를 로컬 파일로 두고 GitHub 없이 쓰는 방식. 설치가 쉬워진다(GitHub 계정·`gh`·저장소가 필요 없음). 대신 GitHub 보드로 진행을 보는 것을 잃고, 지금의 이슈·라벨·판정 댓글 흐름(`gh` 호출, 판정 위조 막기, 앱 진행 기록) 전체를 고쳐야 한다. v0에서는 구현하지 않는다.

## 9. 역할 오퍼레이터와 시작 지점 (결정 8-29·8-31, ADR 0012)

- **하달은 한 번에 하나다.** 코디네이터는 하달 하나를 끝까지 기다린다(`handoffs/last-wait.json`은 파일 하나, `no-report.json`은 잠금 없이 쓴다). 그래서 관제탑의 작업중 카드는 대개 한 장이다. 여러 팀이 동시에 일하는 것은 v1이다.
- **워커 상자는 네 개까지 보인다.** 상세 창은 폭 720에 상자 140씩 놓는다. 한 하달에서 워커를 부른 이슈가 다섯 개를 넘으면 상자가 창 밖으로 나간다. 데이터에서 자르지 않는다. 실제로 생기면 소유자에게 화면을 묻는다.
- **팀은 이름표다.** 오퍼레이터의 규칙·워커 모델은 팀으로 바뀌지 않는다. 구현의 시험은 dev가 맡으므로 tester·plan 카드는 드물게 불린다. 어드바이저가 팀을 적지 않으면 코디네이터 규칙이 이슈를 올리지 않게 막지만, 코드 검사는 아니다.
- **시작 지점은 하달 하나, 이슈 브랜치 하나다.** 한 이슈가 서로 다른 반영 전 하달 둘에 기대거나, 같은 하달의 이슈 둘에 기대는데 한쪽이 다른 쪽을 품지 않으면 `--base`로 풀 수 없어 `대기`다. 그때는 앞 하달을 먼저 반영한다(병합 커밋을 만들어 이어 붙이지 않는다).
- **시작 지점 하달을 멈추거나 다시 시작하면** 그 위에서 시작한 하달은 반영할 수 없다(`run-reflect`가 "h<N>부터 반영하세요"로 거부하는데 h<N>이 더는 없다). 그 하달은 다시 하달한다.
- **시작 지점의 이슈가 거부돼도** 뒤 하달은 그 결과 위에서 시작한다(시작 지점 하달에 브랜치가 있으면 대기가 아니다). 앞 이슈가 끝내 반영되지 않으면 뒤 하달도 반영할 수 없다.
- **밖의 의존은 `main`의 병합 커밋으로만 "반영됨"을 안다.** 사용자가 하네스 밖에서 손으로 합친 의존은 `main`에 있어도 `대기`로 남는다.
- 실제 실행 폴더로 두 팀에 걸친 지시를 처음부터 끝까지 돌린 확인은 아직 없다.

## 10. PR·CI·머지 트레인은 GitHub Actions (결정 8-32, `docs/adr/workflow.md`)

- **진짜 Actions로 한 번 돌렸다(run-19, 2026-11-22, 소유자의 비공개 시험 저장소, `docs/checks/runs.md`).** S12(이슈 PR·하달 PR·CI·트레인 머지·정리)와 S13(트레인 실패 때 `main` 그대로)이 통과했다. 아래 "확인 필요" 가운데 **확인됨**에 적은 것만 진짜로 봤다. 반려·강제 push·옛 PR 닫기처럼 재작업이 있어야 생기는 길은 그 실행에서 생기지 않아 아직 가짜 gh(`harness/test/helpers/fake-gh-actions.mjs`)로만 시험했다.
  - **확인됨:** Actions 권한 API 필드(`default_workflow_permissions`, `can_approve_pull_request_reviews`)와 그 설정. push로 시작된 실행 안의 CI를 `push-branch`가 PR 검사로 읽었다(모두 통과로 읽음). `gh workflow run`으로 시작한 트레인을 찾아 결과 줄을 읽었다(실패·통과 둘 다). HTTPS 원격 push. 트레인이 `main`을 빨리감기하면 하달 PR은 "머지됨"으로 보인다. `GITHUB_TOKEN`으로 지운 브랜치는 `push` 워크플로를 다시 돌리지 않았다. 트레인 통과 뒤 원격에는 `main`만 남았다. 트레인 실패 때는 아무 브랜치도 지우지 않았다.
  - **그 실행에서 보인 빈 곳(아직 안 고침):** (1) 트레인이 실패해도 코디네이터는 원인을 말하지 못한다(훅이 `gh run`을 막고, `run-train` 출력에 실패 단계의 기록이 없다). (2) 트레인 통과 뒤 원격 정리 결과(하달 PR 닫힘·브랜치 지움)를 `run-train` 출력이 알려 주지 않아 코디네이터가 확인하지 못한다. 둘 다 `run-train`이 실행 기록의 그 줄과 정리 결과를 읽어 출력에 넣으면 풀린다.
  - `gh pr checks --json name,bucket,state,link`의 필드와 종료 코드(실패 1, 진행 중 8), push로 시작된 워크플로의 검사가 같은 머리 커밋의 PR 검사로 보이는지.
  - `gh workflow run`이 실행 번호를 돌려주지 않는다고 보고 `run-name`의 요청 번호로 `gh run list`에서 찾는다. 결과는 `gh run view --log`의 `HARNESS_TRAIN_RESULT` 줄로 읽는다(실행 요약은 gh로 못 읽는다고 봤다).
  - `GET repos/<o>/<r>/actions/permissions/workflow`의 `default_workflow_permissions`, `can_approve_pull_request_reviews` 필드 이름. 저장소 설정 "Allow GitHub Actions to create and approve pull requests".
  - 진짜 HTTPS 원격의 push·fetch 인증: 원격 호출만 사용자의 git 설정(자격 증명 도우미)을 쓴다. 믿는 git(전역 설정 막음)으로는 인증이 안 될 수 있어서다.
  - (결정 8-35) 통합 브랜치를 강제 push하면 그 브랜치를 대상으로 한 이슈 PR이 어떻게 되는지(남은 이슈는 머지됨으로 보이는지), `github.event.forced` 값, `GITHUB_TOKEN`으로 지운 브랜치가 `push` 워크플로를 다시 돌리지 않는지, base 브랜치를 지우면 그 PR이 닫히는지, `git/matching-refs` 응답 모양.
- **GitHub 머지 큐는 쓰지 않는다.** 트레인 브랜치(`train/<날짜>-<순번>`)는 `harness-train.yml`이 직접 만든다(결정 6). `main` 보호 규칙이 있으면 Actions의 `main` 빨리감기가 막힐 수 있다(사전 점검이 안내만 한다).
- **동시 하달은 없다.** 트레인이 순서를 맡지만 하달은 지금처럼 한 번에 하나다(9절).
- **GITHUB_TOKEN으로 연 PR은 다른 워크플로를 바로 돌리지 않는다**(GitHub 문서: `pull_request` 실행은 승인이 있어야 돈다). 그래서 CI는 PR 이벤트가 아니라 push를 받은 같은 실행 안에서 재사용 워크플로(`workflow_call`)로 부른다. 대상 저장소의 자기 CI를 쓰려면 그 파일에 `workflow_call`과 `ref` 입력이 있어야 한다(`setup --ci-workflow`). 트레인 안의 시험은 자기 CI가 아니라 시험 명령(`HARNESS_TEST_COMMAND`)으로 돈다.
- **push는 허용 뒤에만, 스크립트가 다시 본다.** push-branch는 허용 판정의 해시와 브랜치 끝이 같을 때만, 통합 브랜치는 남긴 이슈가 모두 허용되고 그 밖의 커밋이 병합 커밋뿐일 때만 올린다(반려된 이슈는 다시 만들어 뺀다, 결정 8-35). 병합 커밋의 내용(충돌 해결 등)까지 다시 계산하지는 않는다.
- **트레인으로 들어간 이슈의 "main에 있음"은 기록으로 안다.** 트레인은 하달 단위로 합쳐서 이슈마다의 병합 커밋이 `main`에 없다. run-train이 `handoffs/h<N>/train.json`에 남긴 허용된 해시가 `main`의 조상일 때만 의존 이슈가 반영된 것으로 본다. 실행 폴더 밖에서 트레인을 돌리면 이 기록이 없다.
- **실행 폴더의 대상 프로젝트는 원격 `main`을 따라가기만 한다.** 트레인이 통과하면 빨리감기만 하고, 로컬 `main`이 원격의 조상이 아니면(로컬 반영과 섞음) 그대로 두고 보고한다. 한 대상에서 로컬 흐름과 트레인을 섞지 않는다.
- **허용과 거부가 섞인 하달은 거부된 이슈를 반려한다(결정 8-35).** `push-branch --branch integration/h<N>`이 통합 브랜치를 허용된 이슈만으로 다시 만들어(시작점에서 의존 순서대로 배관 병합) 하달 PR·트레인으로 보낸다. 거부·`미완료` 이슈는 묻지 않고 새 하달로 재작업한다. 남은 한계: 다시 만든 통합 브랜치의 조합은 합치기(enqueue) 때 단계마다 돈 시험을 다시 돌리지 않는다(하달 PR CI가 처음 시험한다). 반려된 이슈에 기대어 빠진 허용된 이슈(`대기`)는 이미 받은 허용을 버리고 반려된 이슈와 함께 다시 하므로 판정받은 보고서가 하나 더 쌓여 재작업 한도에 센다. 판정 전 이슈가 섞이면 다시 만들지 않는다(종료 코드 2). 다시 만들다 충돌하면 아무것도 바꾸지 않고 종료 코드 2다. 강제 push의 예상 끝은 `handoffs/h<N>/rebuilt.json`에 기대므로 그 기록이 없어지면 덮지 않는다(닫힌 쪽).
- **하달 PR CI가 실패하면 그 하달의 합쳐진 이슈가 모두 `미완료`가 된다.** 어느 이슈가 깨뜨렸는지 가리지 않는다(workflow.md의 "관련 이슈"를 넓게 잡았다).
- **옛 브랜치·PR은 Actions가 닫고 지운다(결정 8-35).** 하네스는 PR에 쓰지 않는다. 새 `h<M>/issue-<X>`가 올라오면 `harness-issue-pr.yml`이 앞선 하달(번호가 작은 하달)의 같은 이슈 PR을 "h<M>에서 다시 함"으로 닫고 그 브랜치를 지운다(그 하달에 이슈 브랜치도 열린 하달 PR도 없으면 `integration/h<N>`도). 트레인이 `main`에 들어가면 `harness-train.yml`이 그 하달들의 브랜치·남은 이슈 PR과 `train/…`을 지운다. 남은 한계: 재작업 없이 버려진 하달(트레인에 안 들어가고 새 하달도 없음)의 브랜치·PR은 남는다. 트레인이 실패하면 아무것도 지우지 않는다. 지우기 API가 실패하면 경고만 남기고 넘어간다(결과는 그대로). 진짜 GitHub에서 PR 닫기·브랜치 지우기가 어떻게 보이는지(아래 확인 필요)는 아직 보지 않았다.
- **설치 때 실행 폴더의 대상 프로젝트 `main`이 원격 `main`과 같아야 한다.** 로컬이 앞서 있으면 그 커밋이 이슈 PR의 시작점과 `integration/h<N>`에 섞여 올라간다.
- **CI 통과를 일찍 읽을 수 있다(확인 필요).** PR을 여는 작업만 끝나고 CI 작업의 검사가 아직 안 잡힌 순간에는 `gh pr checks`가 통과만 보일 수 있다. S12에서 검사 이름과 순서를 보고 필요하면 CI 검사가 보일 때까지 기다리게 고친다.
- **"다른 워커 모델로 한 번 더"(workflow.md 3절)는 코드가 없다.** 재작업 한도를 넘으면 지금처럼 `거부목록`이다. 워커 모델은 Jev 라우팅이 정한다.
- **코디네이터가 묻는 횟수(시작·끝 두 번)는 규칙과 스킬 문구로만 지킨다.** 스크립트 시험으로는 대화를 셀 수 없다.

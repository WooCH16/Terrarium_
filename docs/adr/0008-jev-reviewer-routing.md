# ADR 0008. 리뷰어와 라우팅은 Jev(TypeSafe System One)가 판단하고 스크립트가 정한다

- 상태: **채택됨**
- 날짜: 2026-11-19
- 이슈: #44
- 대체:
  - [ADR 0004](0004-pi-worker-reviewer.md) 결정 B·C의 리뷰어 실행(워커와 다른 LLM을 읽기 전용으로 띄워 판정문을 받음, 리뷰어 순환)
  - [ADR 0006](0006-advice-verdict.md) 결정 6(조언 판정 리뷰어 gemini·muse 순환과 Muse 공개 제한)
  - 소유자 결정 5-3의 리뷰어 순환 부분, 결정 4-2의 "다음 후보 리뷰어로 2회"
  - 코디네이터 규칙의 "워커 모델은 어드바이저의 구분을 옮겨 적는다"
- 유효한 것: 리뷰어는 워커와 다른 제공사여야 한다는 규칙(Jev는 늘 다르다), 판정 댓글 형식(`## 리뷰어 판정: 허용`, `허용된 커밋:`), 조언 판정의 전용 폴더·SHA-256·2회 한도(ADR 0006 결정 1~5), 워커 모델과 대체 표(ADR 0004 결정 A).

## 배경

소유자가 리뷰어와 라우팅 판단을 TypeSafe의 Jev로 바꾸라고 정했다(2026-11-19). Jev는 글을 써 내는 모델이 아니라, 앱이 넘긴 상태(state)에 대한 타입 있는 질문(Noul: 참일 확률, Choice: 보기 중 하나, Score, Box)에 보정된 확률로 답하는 System One 모델이다. HTTP API `POST https://api.typesafe.ai/v1/systemone`으로 부른다. TypeSafe 문서는 고객 요청·응답으로 학습하지 않는다고 밝힌다.

TypeSafe 스킬의 원칙은 "판단은 Jev, 결정은 코드"다. 결정 전체("허용할까?")를 묻지 말고, 결정이 기대는 판단을 하나씩 묻고 결정은 코드에 둔다.

## 결정

### 1. 리뷰어

- `run-reviewer.mjs`가 Jev를 부른다. 인자, 출력 한 줄, 판정 댓글 형식, 조언 실행 기록 형식은 바꾸지 않는다(합치기 스크립트, 코디네이터, 어드바이저가 그대로 쓴다).
- 기계적으로 볼 수 있는 것은 코드가 본다(`jev-review.mjs`). 하나라도 어긋나면 Jev를 부르지 않고 거부한다.
  - 결과 보고서: 첫 줄 `## 결과 보고서`, `커밋 해시:` 한 줄, 네 칸(기준별 충족 여부, 근거 위치, 변경 요약, 남은 문제), 이슈의 `## 완료 기준` 표, 근거 위치에 적힌 파일 경로가 보고서 커밋에 있는지(`git cat-file -e <해시>:<경로>`).
  - 제안문: 작업 단위마다 목표, 완료 기준 표, 먼저 끝나야 할 것, 전제·위험, 표의 빈칸.
- 글을 읽어야 하는 판단만 Jev에 Noul로 묻는다. 기준 한 줄마다 두 질문이다.
  - 결과 보고서: 보고서가 이 기준을 충족으로 적었는가(`met_<i>`), 이 기준의 근거 위치가 구체적인가(`evidence_<i>`). 상태는 보고서 하나다.
  - 제안문: 충족을 가릴 수 있는 기준인가(`decidable_<단위>_<i>`), 확인 방법을 실행하거나 볼 수 있는가(`checkable_<단위>_<i>`). 상태는 제안문이다.
- 결정: 모든 질문이 예(`jev.yes` 0.7 이상)일 때만 허용이다. 아니오(`jev.no` 0.3 이하)나 애매(그 사이)가 하나라도 있으면 거부이고, 그 질문과 확률이 거부 이유가 된다(소유자 결정: 애매하면 거부). 판정 댓글에는 질문마다의 확률 표를 붙인다.
- 결과 보고서 판정은 이전보다 엄격하다: 예전 리뷰어 지시는 기준마다 "충족/미충족과 근거 위치가 있다"였지만, 이제는 충족으로 적혀야 허용된다.
- Jev 호출 실패(네트워크, 시간 초과, 429, 200 아님, 응답 모양 어긋남)는 판정이 아니라 종료 코드 6이다. 일시적 실패(네트워크, 시간 초과, 429, 5xx)는 스크립트가 2회 다시 부른다(retry-after가 있으면 그 시간, 없으면 1초·3초). 키·요청·응답 모양 오류는 다시 부르지 않는다(이슈 #25, 결정 4-2의 "2회"를 여기에 둔다). 코디네이터는 6을 다시 부르지 않는다. 실패를 "아니오"로 읽지 않는다. 키가 없으면 종료 코드 2다.
- 리뷰어 순환(`reviewer-rotation.json`), 공개 가능 표시에 따른 리뷰어 건너뛰기, 응답 형식 파싱(`verdict.mjs`)은 없앴다.

### 2. 라우팅

- `route-issue.mjs --draft <이름>`: 코디네이터가 `.drafts/`에 쓴 이슈 초안을 상태로, Choice 둘을 한 요청으로 묻는다. 유형(작업/조사)과 워커 모델(`allowedModels`).
- 보기의 설명은 설정 `jev.routing`에 둔다(`workerModels`, `types`). 하달마다 맡길 일이 달라지므로 설정에서 바꾼다. 설명이 없는 모델은 라우팅이 고르지 않는다.
- 워커 모델 기준(소유자 결정 8-9, 2026-11-19): **muse**는 파일 한두 개 안에서 끝나고 기대 동작이 분명한 코드 변경(작은 버그 수정, 옵션 하나, 시험 추가)과 문서·예시(값이 싸서). **gemini**는 범위가 분명한 여러 파일 기능 변경. **claude**는 여러 파일·모듈을 이해해야 하는 변경과 설정·권한·보안·비밀값 변경(워커 중 claude만 하네스 훅이 강제된다. **이 근거는 ADR 0009로 없어졌다**: 세 워커 모두 Pi라 훅이 걸리는 워커가 없다. claude에 맡기는 근거는 여러 모듈을 이해하는 능력만 남는다).
- 코드가 정하는 것: 공개 제한이 켜진 모델(`runners.<m>.publicOnly`)은 초안에 `공개 가능: 예`가 없으면 보기에서 뺀다(ADR 0007은 워커 대체에 그대로 유효). 답은 가장 높은 보기를 쓴다.
- **난이도(소유자 결정 8-16):** 같은 요청에 난이도 Choice(`simple_change`/`complex_change`, 설명은 `jev.routing.difficulty`)와 보안 경계 Noul(`touches_security`)을 더 묻는다. 결정은 코드가 한다: 보안 경계에 닿으면(0.7 이상) 어려움, 쉬움은 Jev가 0.7 이상으로 고를 때만, 그 밖은 어려움(강한 모델 쪽). 어려운 일은 간단한 코드용 muse에 보내지 않고 나머지 보기 중 확률이 가장 높은 모델로 바꾼다. 워커 러너가 난이도별 모델을 두면(claude: 쉬움 haiku, 어려움 sonnet) `run-worker`가 이슈 본문의 `난이도:` 줄로 고른다. 줄이 없으면 기본 모델(sonnet).
  - 실제 API 시험에서 보안 변경이 쉬움·어려움 0.53으로 갈려 보안을 따로 묻게 했고, "입력 검증"을 넣었더니 빈 제목 검사(일반 기능)가 보안 0.82로 잡혀 기준에 그 경우를 적었다. 그 뒤 초안 8개와 조정에 쓰지 않은 초안 5개의 난이도가 모두 기대대로였다.
- 코디네이터는 출력 세 줄(워커 모델, 유형, 난이도)을 이슈 본문에 그대로 옮긴다. 셋 다 스스로 고르지 않는다.

### 3. 설정과 키

- `operator.config.json`의 `jev`: `endpoint`, `model`(고정 버전 `jev-1.14.0`. 별칭 `jev-latest`는 새 버전이 나오면 답이 바뀌므로 쓰지 않는다), `timeoutMs`, `yes`, `no`, `routing`. Jev는 워커가 아니므로 `allowedModels`·`runners`에 넣지 않는다.
- 키 `TYPESAFE_API_KEY`는 환경 변수 → 실행 폴더 `.env` → 하네스 저장소 `.env` 순서로 찾는다. `.env`는 훅이 모든 역할의 읽기를 막는다. 키는 인자·출력·기록·댓글에 남기지 않는다. 사전 점검(`preflight.mjs`)이 키가 있는지만 알린다.

## 이유

- 판정 형식과 기록이 그대로라 합치기·반영·코디네이터 쪽을 고치지 않아도 된다.
- 기계적인 검사를 코드로 옮겨, 같은 보고서에 같은 결과가 나오고 시험할 수 있다. 근거 파일 존재는 Jev가 파일을 읽을 수 없으므로 코드가 맡는 것이 맞다.
- 질문 문구를 `jev-review.mjs`·`route-issue.mjs` 한곳에 두어 고치고 감사하기 쉽다.

## 아직 확인하지 않은 것

- **실제 API 시험(2026-11-19, 소유자 허락):** `harness/e2e/jev-probe.mjs`로 가상 보고서 6개, 대역 제안문 2개, 라우팅 초안 4개를 `jev-1.14.0`에 보냈다(요청 12개, 입력 토큰 9,096개). 기대값 24개가 모두 맞았다. 한국어 상태(보고서·제안문)와 영어 질문 조합으로 잘 읽었다.
  - 충족 0.99, 미충족 0.02, 부분 충족 0.23, "확인함"·"다음에 확인" 같은 근거 0.05~0.07, 명령과 결과로 적은 근거 0.86~0.94.
  - 대역 정상 제안문의 가장 낮은 값은 0.79("같은 시험의 created 정렬 사례"처럼 다른 줄을 가리키는 확인 방법)로 경계 0.7에 가깝다.
  - 첫 시험에서 보고서가 기준 문구를 바꿔 쓰면 0.69~0.70으로 경계에 걸렸다. 질문 문구를 고치지 않고, 보고서 표가 이슈의 기준을 그대로 옮겼는지를 코드 검사에 더했다(결과 보고서 형식이 이미 "이슈의 기준 그대로"를 요구한다).
- 라우팅(결정 8-9의 기준): 초안 8개와 조정에 쓰지 않은 초안 3개에서 워커 모델과 유형이 모두 기대대로였다. 가장 낮은 값은 여러 파일 구조 변경의 claude 0.71이다. 조사 이슈의 워커 모델은 쓰지 않으므로 보지 않는다.
- 결정 9-3은 바꿨다(소유자, 2026-11-19): 워커 모델 1곳 이상과 Jev 키. `preflight.mjs`의 `MIN_PROVIDERS`는 1이다.

## 검토한 대안

- 애매하면 기존 LLM 리뷰어에게 넘기는 안: 소유자가 "대체"와 "애매하면 거부"를 골라 기각했다.
- Jev에게 "이 보고서를 허용할까?"를 한 질문으로 묻는 안: 결정을 Jev에 두는 것이라 스킬 원칙에 어긋나고, 거부 이유를 기준별로 줄 수 없어 기각했다.

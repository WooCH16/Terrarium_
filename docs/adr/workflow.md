# 작업 흐름: coordinator-issue-flow, 이슈 PR, 하달 PR, 머지 트레인 (GitHub Actions)

- 상태: **채택됨** (소유자 승인 2026-11-22, 새 결정 1~6은 제안대로. 결정 8-32)
- 날짜: 2026-11-22
- 관련: 소유자 결정 8-25(승인), 8-27(대리 기준), 8-29(담당 팀), 8-31(`--base`), 8-32(이 문서), 8-33(저장소 이슈용 `issue-flow` 스킬)
- 이름 주의: 이 문서의 코디네이터 스킬은 `coordinator-issue-flow`(하네스 실행 폴더의 지시 처리)다. 이 저장소 자체의 GitHub 이슈를 8단계로 처리하는 스킬은 `.claude/skills/issue-flow`(결정 8-33)로, 다른 것이다

## 배경

- 소유자의 목표는 "사용자 개입을 최대한 줄이기"다.
- 지금 한 지시는 조언 → 이슈 → 하달 → 리뷰 → 대조 → 끝 보고 → 반영으로 흐른다. 이 순서가 코디네이터 스킬 10개에 나뉘어 있다. 실행 중에도 코디네이터가 멈춰 묻는다(run-18 h24: 세 번).
- 반영은 `run-reflect`가 대상 프로젝트의 로컬 `main`에 합친다. PR·CI는 없다. 시험 통과는 워커와 합치기 단계의 기록에 기댄다.
- 훅은 `git push`와 `gh pr`을 어디에서도 허용하지 않는다.

## 결정

### 1. 사용자가 끼는 자리는 셋

1. **시작 전:** 지시가 애매하면 바로 묻는다(8-25의 "애매하면 다시 묻기" 그대로). 계획(조언)은 한 번 승인받는다.
2. **실행 중:** 묻지 않는다. 거부 한도 초과, 막힘, CI 실패, 주관적 기준은 아래 3절대로 스스로 처리하고 끝 보고에 모은다.
3. **끝:** 끝 보고 하나에 "결정할 것" 목록을 둔다. 머지 트레인 승인도 여기서 한 번에 받는다. 반영(머지)은 사용자가 정한 뒤에만 한다.

### 2. 브랜치·PR 세 층 — PR·CI·트레인은 GitHub Actions가 한다

하네스는 **브랜치를 올리고, Actions가 낸 결과를 읽기만** 한다. PR을 만들고, CI를 돌리고, 트레인을 머지하는 일은 대상 저장소의 GitHub Actions 워크플로가 한다. 트레인을 시작하는 신호 하나만 하네스가 보낸다(사용자 승인 뒤).

| 층 | 브랜치 | PR 대상 | 하네스가 하는 일 | Actions가 하는 일 |
|---|---|---|---|---|
| 이슈 | `h<N>/issue-<번호>` (지금과 같음) | `integration/h<N>` | Jev 허용 뒤 브랜치 push | push를 받아 이슈 PR을 열고 CI. Jev 판정 링크를 본문에 |
| 하달 | `integration/h<N>` (지금과 같음) | `main` | 하달의 이슈가 다 합쳐지면 push | 하달 PR을 열고 CI. 결과를 PR 상태로 남김 |
| 트레인 | `train/<날짜>-<순번>` (Actions가 만듦) | `main` | 사용자 승인 뒤 트레인 워크플로 시작(`gh workflow run`) | 하달 PR들을 순서대로 쌓아 CI, 통과하면 `main` 머지, 실패하면 멈춤 |

- **이슈 PR:** 리뷰 판정 기준은 지금 그대로다(지정 저장소 이슈의 허용 판정 댓글이 원본이다). 이슈 PR의 CI가 실패하면 하네스가 그 결과를 읽어(`gh pr checks`, 읽기) 이슈를 `미완료`로 되돌리고 재작업한다.
- **하달 PR:** CI가 실패하면 그 실패 기록을 붙여 관련 이슈를 재작업한다. 재작업은 거부 한도에 함께 센다.
- **머지 트레인 (워크플로 `harness-train.yml`):**
  - 입력: 하달 목록(의존 순서. `--base` 순서, h24 → h25처럼). 순서는 하네스가 반영 순서 검사(8-31)로 정해 넘긴다.
  - 하달 PR들을 `train/…` 브랜치 하나에 쌓고 CI를 한 번 더 돌린다.
  - 통과하면 `main`에 머지하고 하달 PR들을 닫는다.
  - 실패하면 `main`은 그대로 둔다. 맨 뒤 하달부터 하나씩 빼며 다시 돌려 실패한 하달을 찾고, 결과를 워크플로 요약에 남긴다. 통과한 앞부분만 머지할지는 끝 보고에서 묻는다(스스로 부분 머지하지 않는다).
- **`main` 머지 권한은 Actions에만 있다.** 하네스 훅은 `main` push를 계속 막는다.

### 3. 실행 중 스스로 처리하는 것

| 일 | 처리 | 끝 보고에 |
|---|---|---|
| 거부 한도 초과 | 다른 워커 모델로 한 번 더. 그래도 안 되면 `거부목록` | 이슈와 마지막 거부 이유 |
| 막힘 | `막힘`으로 두고 다른 이슈를 계속 | 막힌 이유와 풀 방법 |
| 하달 PR CI 실패 | 재작업(거부 한도 안) | 한도를 넘었을 때만 |
| 주관적 기준 | 8-27대로 대리 기준으로 바꿔 진행 | 바꾼 기준과 원래 목표 |
| 트레인 CI 실패 | `main` 그대로, 실패 하달 찾기 | 실패 하달과 부분 머지 여부 질문 |

### 4. `coordinator-issue-flow` 스킬

- 새 스킬 하나: `harness/coordinator/skills/coordinator-issue-flow/SKILL.md`. 기존 스킬 18개와 스크립트는 그대로 두고, "다음에 어느 스킬을 부르는지"와 "끝에 물을 것 모으기"만 정한다.
- 입구(= `/goal` 대신): 코디네이터 터미널에 지시 한 줄, 또는 `#<번호> 맡겨`. 새 명령 방식은 만들지 않는다.
- 자세한 순서는 아래 "스킬 설계 요약".

### 5. MCP는 만들지 않는다

- 개입 줄이기에는 필요 없다. 상태는 끝 보고와 관제탑이 보여 준다.
- 쓰기 도구를 MCP로 열면 훅을 거치지 않는 새 길이 생긴다.

### 6. 동시 하달은 이번에 하지 않는다

- 하달은 지금처럼 한 번에 하나(known-limitations 9절). 트레인이 순서를 맡으므로 나중에 동시 하달을 더해도 이 구조는 그대로 쓸 수 있다.

## 새 결정이 필요한 것 (승인 때 함께 정한다)

1. **GitHub에 브랜치 올리기:** 지금은 에이전트가 대상 프로젝트 코드를 GitHub에 올리지 않는다(훅이 `git push`를 막는다). 이 설계는 대상 저장소 원격에 `h<N>/issue-*`, `integration/h<N>` 두 모양만 push하게 허용한다. 하네스가 쓰는 `gh` 쓰기는 `gh workflow run harness-train.yml` 하나이고, 사용자 승인 뒤에만 부른다. `gh pr`은 읽기(`view`, `checks`, `list`)만. `main` push, 다른 브랜치·저장소는 지금처럼 막는다.
2. **대상 저장소의 공개 여부:** 지정 저장소(이슈)는 비공개여야 한다(지금 규칙). 대상 프로젝트(코드) 저장소는 사용자의 것이므로 공개도 허용할지 정한다. 제안: 허용하되, 공개 저장소면 Actions가 PR 본문에 이슈 본문·판정 원문을 옮기지 않고 링크만 단다(지정 저장소 링크는 남이 열 수 없다).
3. **워크플로 파일을 어떻게 넣나:** Actions 워크플로 세 개(`harness-issue-pr.yml`, `harness-handoff-pr.yml`, `harness-train.yml`)는 대상 저장소의 `.github/workflows/`에 있어야 한다. CI 자체(시험 명령)는 대상 저장소의 기존 CI 워크플로를 그대로 쓰고, 없으면 `npm test`처럼 설치 때 고른 명령을 부르는 기본 CI를 함께 준다. 제안: 하네스는 틀을 `harness/github/workflows/`에 두고, `setup`이 "넣을까요?"를 물어 동의하면 대상 저장소에 **PR 하나로** 올린다. 그 PR의 머지는 사용자가 한다(하네스가 `main`에 쓰지 않는다).
4. **원격이나 워크플로가 없는 대상:** 오늘의 메모 프로그램처럼 원격이 없거나 사용자가 워크플로를 넣지 않았으면, 지금의 로컬 흐름(`run-reflect`)으로 돌고 끝 보고에 "CI 없음"을 적는다.
5. **Actions 권한:** 워크플로는 `GITHUB_TOKEN`의 `contents: write`, `pull-requests: write`가 필요하다. 저장소 설정에서 Actions가 PR을 만들 수 있게 켜야 한다("Allow GitHub Actions to create and approve pull requests"). `main` 보호 규칙이 있으면 Actions의 머지가 막힐 수 있다. 사전 점검이 이 설정을 확인하고 안내한다. (이 설정 이름과 동작은 구현 전에 GitHub 문서로 다시 확인한다.)
6. **GitHub 머지 큐:** GitHub에는 merge queue 기능이 있지만 저장소 종류·요금제에 따라 쓸 수 있는지 아직 확인하지 않았다. 제안: v0는 `harness-train.yml`이 트레인 브랜치를 직접 만들고, 머지 큐 연결은 확인한 뒤 따로 정한다.

## 하지 않는 것

- 동시 하달, 이슈 단위 반영(하달 단위 그대로), MCP, `/goal` 연결.
- 사용자 승인 없는 `main` 머지. 트레인 부분 머지의 자동 결정.

## 결과

- 사용자는 시작(애매함·계획 승인)과 끝(결정 목록·트레인 승인) 두 번만 본다.
- `main`에 들어가는 모든 변경이 하달 PR CI와 트레인 CI를 두 번 통과한다. 지금은 워커 기록에 기댄다.
- PR·CI·머지는 GitHub Actions에 있어서 하네스 쪽 쓰기는 브랜치 push 두 모양과 트레인 시작 신호뿐이다. `main`에 쓰는 것은 Actions뿐이다.
- 대신 대상 프로젝트에 GitHub 원격과 하네스 워크플로가 있어야 이 흐름이 온전히 돈다. 훅이 push를 처음으로 허용하므로 훅 시험을 크게 더해야 한다.

## 부록 A. 스킬 설계 요약

### `coordinator-issue-flow` (새 스킬)

- **부르는 때:** 사용자가 작업 지시를 하거나 `#<번호> 맡겨`라고 할 때. 질문·상태 확인에는 부르지 않는다.
- **순서:**
  1. 지시 판단: 무엇을 만들지 자체가 애매하면 여기서만 바로 묻는다(`coordinator-direct`).
  2. 조언: `coordinator-advice` → 어드바이저 패널(`advisor-panel`). 주관적 기준은 대리 기준으로(8-27).
  3. 계획 승인: 조언 요지와 이슈 목록을 보이고 한 번 묻는다(8-25). 승인 뒤 바뀐 요구는 새 승인 없이 처리.
  4. 이슈: `coordinator-issues`(담당 팀 옮기기, 8-29).
  5. 하달: `coordinator-handoff`. 팀별로 의존 순서대로, 반영 전 하달에 기대면 `--base h<N>`(8-31).
  6. 리뷰·이슈 PR: Jev 판정(`coordinator-review`). 허용되면 이슈 브랜치를 push한다. 이슈 PR과 CI는 Actions가 하고, 하네스는 결과를 읽는다.
  7. 하달 PR·CI: 하달의 이슈가 다 합쳐지면 통합 브랜치를 push한다. Actions가 하달 PR과 CI를 하고, 하네스는 결과를 기다려 읽는다. 실패는 재작업.
  8. 예외: 3절의 표대로 처리하고 "결정할 것"에 적는다(`coordinator-exceptions`). 묻지 않는다.
  9. 끝 보고: 이슈마다 상태·담당 팀·하달·PR·CI 결과, 그리고 "결정할 것"(트레인 승인, 거부목록, 막힘, 바꾼 기준)을 한 번에(`coordinator-records`).
  10. 트레인: 사용자가 승인하면 `coordinator-reflect`가 트레인 시작 스크립트를 부른다(Actions 워크플로 시작 → 끝날 때까지 기다림 → 요약 읽기). 결과를 보고한다.
- **지키는 것:** 위 9단계 전에는 사용자에게 묻지 않는다(1·3단계 예외). 기존 스킬의 규칙과 부딪히면 기존 스킬을 따른다.

### 고치는 기존 스킬

| 스킬 | 바뀌는 점 |
|---|---|
| `coordinator-exceptions` | "멈춰 묻기"를 "처리하고 끝 보고에 적기"로(3절 표) |
| `coordinator-reflect` | `run-reflect` 대신 트레인 시작 스크립트. 워크플로 없는 대상은 지금 그대로 |
| `coordinator-records` | 끝 보고에 PR·CI 열과 "결정할 것" 목록 |
| `operator-work` | 허용 뒤 이슈 브랜치 push, Actions의 CI 결과 읽기 |
| `operator-reflect` | 통합 브랜치 push, 하달 PR CI 결과 읽기 |

### 새 스크립트 (스킬이 부르는 코드)

- `harness/operator/push-branch.mjs`: `h<N>/issue-*`, `integration/h<N>`만 대상 원격에 push. 그 뒤 Actions가 연 PR과 CI 결과를 기다려 읽는다(`gh pr view|checks`, 읽기만).
- `harness/operator/run-train.mjs --handoffs h<N>,h<M>`: 반영 순서를 검사하고 `gh workflow run harness-train.yml`로 시작, 끝날 때까지 기다려 요약을 읽는다. `main`을 직접 건드리지 않는다.
- 훅(`policy.mjs`, `profiles.mjs`): 위 두 스크립트, 두 브랜치 모양, 트레인 워크플로 시작만 허용. 다른 push·PR 쓰기는 지금처럼 막는다.

### 새 GitHub Actions 틀 (`harness/github/workflows/`, 대상 저장소에 넣음)

| 파일 | 시작 | 하는 일 |
|---|---|---|
| `harness-issue-pr.yml` | `h*/issue-*` push | `integration/h<N>`로 가는 이슈 PR 열기(있으면 갱신), CI 부르기 |
| `harness-handoff-pr.yml` | `integration/h*` push | `main`으로 가는 하달 PR 열기, CI 부르기 |
| `harness-train.yml` | `workflow_dispatch`(입력: 하달 목록) | `train/…`에 순서대로 쌓기 → CI → 통과 시 `main` 머지·하달 PR 닫기, 실패 시 실패 하달 찾기·요약 |
| `harness-ci.yml` (대상에 CI가 없을 때만) | 위 세 워크플로가 부름 | 설치 때 고른 시험 명령 실행 |

- 만들지 않는다(결정 5절). 설계 없음.

## 부록 B. 스모크 시나리오

S1~S11은 가짜 GitHub(`HARNESS_GH_BIN` 대역: Actions가 연 PR·CI 결과·트레인 결과를 흉내 냄)와 로컬 bare 저장소를 원격으로 쓴다. 진짜 GitHub에 쓰지 않는다. 워크플로 YAML 자체는 S14로 따로 검사한다. S12·S13만 소유자 승인 뒤 진짜 원격과 진짜 Actions로 한다.

| # | 시나리오 | 통과 조건 |

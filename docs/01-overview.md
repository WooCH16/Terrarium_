# 코디네이터 개요

- 현재 유효한 구조 결정은 `docs/adr/README.md` 색인에서 "채택됨"인 ADR을 따른다(현재 0001의 결정 3·4·5, 0002의 결정 A·B(결정 B의 리뷰어 실행 방식은 0004로 대체됨), 0003의 결정 A~E(결정 A의 워커 실행 방식은 0004로 대체됨), 0004의 결정 A·B·C).
- **오퍼레이터에 관한 내용은 ADR 0003(채택됨, 2026-11-14, `adr/0003-operator-harness.md`는 이 저장소에 없음)이 대체했다.** 대체된 곳에는 "대체됨" 표시를 달았고, 오퍼레이터의 현재 설계는 [operator.md](operator.md)를 따른다.
- **워커와 리뷰어의 실행 방식은 [ADR 0004](adr/0004-pi-worker-reviewer.md)(채택됨, 2026-11-18)가 대체했다.** 대체된 곳에는 "대체됨 → ADR 0004" 표시를 달았다. 2단계 구현에서 임시로 정한 값은 "임시(이슈 #2)"로 표시했고, 목록은 `docs/checks/T6-T7-pi-scripts.md`의 "임시 결정"에 있다.
- `docs/history/`(이 저장소에 없음)는 사람이 확인하려고 만든 이력 문서이므로 **읽지 않는다.** 이 문서의 근거로도 링크하지 않는다.
- `[보충]` 표시는 설계 논의의 답을 문서 형태로 풀어 쓰며 작성자가 덧붙인 표현이다. 직접 정한 것이 아니므로 확인이 필요하다.

## 1. 개요

계층형 에이전트 하네스에서 **사용자와 유일하게 대화하는 코디네이터**를 설계한다. 오퍼레이터, 워커, 리뷰어, 어드바이저의 내부는 설계하지 않고 코디네이터와의 접점만 정한다.

- 사용자는 코디네이터 한 명과만 대화한다. 코디네이터는 사용자의 요구를 빈틈없이 정리하고, 결과가 요구와 맞는지 확인한 뒤 보고한다.
- 코디네이터는 범용 고성능 모델이다. 영역 지식은 사용자가 준비한 영역별 어드바이저의 제안문으로 받는다. 제안문은 리뷰어가 허용한 것만 쓰며, 코디네이터가 그 제안문을 바탕으로 작업을 쪼개 이슈로 등록하고 오퍼레이터에게 하달한다.
- 결과는 오퍼레이터의 보고서 → 리뷰어의 허용/거부 → 코디네이터의 완료 기준 대조 → 사용자 보고 순서로 올라온다.
- 이슈와 문서는 사용자가 지정한 비공개 GitHub 저장소에 둔다.
- 가장 피할 실패의 우선순위는 **요구 누락 > 요구 왜곡 > 과도한 호출**이다. 충돌하면 앞선 것을 우선하고, 애매하면 묻는다.
- Claude Code 세션 기반으로 시작하며, 환경에 의존하는 부분은 접점으로 분리해 나중에 발전시킬 수 있게 한다.

## 2. 역할과 책임

### 2.1 다섯 역할

| 역할 | 책임 | 실행 방식 | 설계 범위 |
|---|---|---|---|
| 코디네이터 | 사용자와 대화, 정리본 작성과 승인, 리뷰어가 허용한 어드바이저 제안문을 바탕으로 작업 분해, 이슈 등록과 오퍼레이터에게 하달, 리뷰어를 통과한 보고서와 완료 기준 대조, 사용자 보고, 가벼운 확인은 직접(읽기 전용)·깊은 조사는 오퍼레이터에게 시키기, 기록·선호 문서 관리, 사용량 확인 | 상시 | **설계 대상** |
| 어드바이저 | 영역 전문 개념으로 "작업을 어떻게 쪼갤지" 제안문(조언문) 작성. 영역별로 있고 어드바이저끼리 먼저 조율해 통합 제안문을 낸다. 조언만 하며, 자료가 필요하면 직접 조사하지 않고 오퍼레이터에게 조사 작업을 시켜 결과를 받아 작성한다 | 필요할 때 호출 | 접점만 |
| 오퍼레이터 | 영역별 팀 운영(v0의 팀은 다섯: dev·design·tester·plan·sec, 결정 8-29, ADR 0012), 이슈를 받아 일을 진행하고 결과 보고서 작성. 워커들의 결과를 합친다. 코디네이터나 어드바이저가 시킨 조사도 수행해 결과를 돌려준다 | 이슈 하달 또는 조사 요청 때 시작, 끝나면 종료 (**대체됨: Claude 독립 세션, 시작 스크립트로 시작**) | ~~접점만~~ **설계 대상([operator.md](operator.md))** |
| 워커 | 실제 작업. 작업 하나에 워크트리 하나를 쓰고, 끝나면 오퍼레이터에게 보고한다 | 이슈 하달 때 시작, 끝나면 종료 (**대체됨 → ADR 0004 결정 A: Pi 하네스로 실행한다. 오퍼레이터가 시작 스크립트 `run-worker`로 부르고, 모델은 이슈의 `워커 모델` 칸에 적힌 `claude`, `gemini`, `muse` 중 하나다. `codex`는 허용 목록에서 뺐다.** ~~현재 구현은 `muse`만 Pi를 거치고 `gemini`는 `agy` 직접, `claude`는 `claude -p` 직접 실행한다: 임시(이슈 #2)~~ **(바뀜 → ADR 0009: 세 모델 모두 Pi로 실행한다. claude는 이슈의 난이도로 haiku·sonnet을 고른다, 소유자 결정 8-16. 워커 모델·유형·난이도는 Jev 라우팅이 정한다, ADR 0008.)**) | 접점만 |
| 리뷰어 | 두 가지 기능: 1. 결과 보고서 검토(코디네이터에게 가기 전에 허용/거부), 2. 허용/거부 결정(어드바이저 조언을 이슈로 만들기 전에 허용/거부) | 조언이 나올 때와 보고서가 올라올 때 호출 (**대체됨 → ADR 0004 결정 B·C: 하위 에이전트가 아니라 Pi 하네스로 실행되는 별도 실행이다. 읽기 전용이고 판정 형식이 고정이며, 모델은 워커와 다른 타입(`claude`, `gemini`, `muse` 중 워커 타입을 뺀 둘)을 번갈아 쓴다. 결과 보고서 판정은 코디네이터가 `run-reviewer.mjs --issue <번호>`로 띄운다. 스크립트 이름·인자와 띄우는 쪽, 순환 단위(판정 한 번마다), Pi를 거치지 않는 gemini·claude 경로는 임시(이슈 #2). 조언 판정은 ADR 0006에 따라 어드바이저가 `run-reviewer.mjs --advice <파일> --advice-id <id>`로 부른다**) **(바뀜 → ADR 0008: 리뷰어는 Jev(TypeSafe System One, HTTP API)다. 모델 순환은 없고, 스크립트가 코드 검사 뒤 기준마다 Jev에 묻고 모두 "예"일 때만 허용한다.)** | 접점만 |

- 첫 버전은 어드바이저, ~~오퍼레이터,~~ ~~리뷰어를~~ 코디네이터의 하위 에이전트로, ~~워커를 오퍼레이터의 하위 에이전트로~~ 부른다. 결과 보고서와 리뷰어 판정의 본문은 이슈 댓글로 남기고 코디네이터에게는 위치와 한 줄 요약만 돌려준다(ADR 0002 결정 B). **(오퍼레이터와 워커 부분은 대체됨 → ADR 0003 결정 A: 오퍼레이터는 독립 세션이고 코디네이터에게는 이슈마다 번호, 상태, URL만 돌려준다.)** **(리뷰어 부분은 대체됨 → ADR 0004 결정 B: 리뷰어는 별도 실행이다. `run-reviewer.mjs`는 판정을 이슈 댓글로 남기고 코디네이터에게 `<댓글 URL> | 리뷰어 판정: 허용|거부 | 모델: ...` 한 줄만 돌려준다.)** 하네스의 리뷰어 하위 에이전트 정의(`harness/agents/reviewer.md`, `setup.mjs`가 만드는 `.claude/agents/reviewer.md`)는 쓰이지 않아(ADR 0004로 대체) **지웠다**(소유자 결정 5-1).

### 2.2 코디네이터의 권한 경계

- **쓰기:** 지정 저장소의 이슈와 문서(기록 문서, 보존 노트, 선호 문서, 어드바이저 목록)만 쓴다.
- **읽기:** 지정 저장소, 실행 환경의 사용량 통계, 다른 역할이 올린 결과 보고서와 제안문, 그리고 작업 대상 프로젝트의 파일과 문서를 읽는다. 작업 대상 프로젝트는 **읽기 전용의 가벼운 확인**에 한한다.
- **조사:** 가벼운 확인은 코디네이터가 직접 하고, 깊은 조사는 오퍼레이터에게 시켜 결과를 받는다. 둘은 아래 기준으로 가른다.
  - **목적 기준(기본):** "있는지, 어디 있는지, 값이 얼마인지"처럼 이미 있는 사실을 확인하면 가벼운 확인이다. "왜 그렇게 되는지, 어떻게 연결되어 있는지, 여러 곳을 비교"처럼 해석이 필요하면 깊은 조사다.
  - **한도(안전장치):** 가벼운 확인으로 시작했더라도 파일 3개 또는 읽기 3번(시작값)을 넘으면 중단하고 오퍼레이터에게 넘긴다.
  - **애매하면 깊은 조사로 본다.**
  - **요청 경로:** ~~조사 요청은 이슈를 만들지 않고, 세션에서 오퍼레이터를 **직접 호출**해 묻고 결과를 그 자리에서 받는다(코디네이터와 어드바이저 공통). 작업을 맡기는 이슈 하달과는 구분된다.~~ 결과 형식은 4.4절을 따른다. **(대체됨 → ADR 0003 결정 D: 조사도 이슈로 하달하고 최우선으로 처리한다. `유형`이 `조사`인 이슈를 올리고 `run-research`로 오퍼레이터를 별도 세션으로 바로 띄운다. 결과는 오퍼레이터가 이슈 댓글로 올린다.)**
- 작업 대상 프로젝트에는 쓰지 않는다. 수정과 실행은 하지 않는다.
- 지정 저장소가 공개 저장소이면 쓰지 않고 사용자에게 알린다.
- 비밀값은 어떤 문서에도 적지 않고, 존재와 용도만 적는다.
- 권한을 넓히려면 새 ADR로 대체한다.

### 2.3 어드바이저 선택

- 어드바이저는 사용자가 미리 준비하고, 각각에 "어떤 영역을 아는지" 설명이 붙는다. 목록은 지정 저장소에 둔다.
- 코디네이터는 설명을 읽고 요청에 맞는 어드바이저를 골라 부른다. 영역이나 어드바이저를 코디네이터가 새로 만들지 않는다.
- 설명이 조금이라도 겹치면 **모두 부르고**, 어드바이저들이 서로 협의해 하나의 통합 제안문을 낸다. 합의가 안 되면 서로 다른 안을 이유와 함께 보내고, 코디네이터가 "제안, 이유, 예상 결과" 형식으로 사용자에게 묻는다.
- 맞는 어드바이저가 하나도 없으면 이슈를 올리지 않고 **즉시 보고**한다.
- 어드바이저는 **조언만 한다.** 자료가 필요하면 직접 조사하지 않고 오퍼레이터에게 조사 작업을 시켜 결과를 받은 뒤 제안문(조언문)을 쓴다. ~~요청은 이슈 없이 세션에서 오퍼레이터를 직접 호출해 묻고 결과를 바로 받는다.~~ **(대체됨 → ADR 0003 결정 D: 어드바이저가 코디네이터에게 어느 영역의 자료가 필요한지 명시해 요청하면, 코디네이터가 해당 영역 오퍼레이터에게 전달 대상 어드바이저를 알려 조사를 요청한다. 오퍼레이터가 정리본을 그 어드바이저에게 전달하고 코디네이터에게는 전달 완료만 알린다.)**
- 어드바이저가 많아져 호출 비용이 문제가 되면 사용량을 관찰한 뒤 호출 상한을 도입한다.

### 2.4 사용량, 진행 화면, 알림

- **사용량:** 실행 환경이 제공하는 통계를 코디네이터가 직접 읽어 추적한다. 기록과 보고까지만 하고 스스로 조절하지 않는다. 통계를 못 읽을 때의 보고 방식은 미결이다. **(덧붙임, ADR 0013: 데스크톱 앱은 코디네이터 statusline의 5시간·주간 한도와 컨텍스트를 관제탑 위쪽에 보이고, 단추를 누르면 계정별 한도 창을 연다. 못 읽는 값은 지어내지 않고 "첫 답 뒤 표시"나 "제공사가 남은 한도를 알려 주지 않습니다"로 적는다.)**
- **진행 화면:** GitHub 이슈 목록/보드를 그대로 쓴다. 화면은 읽기 전용으로 보며, 질문·지시·승인은 코디네이터와의 대화로만 한다. 이 선은 설계를 정리하는 쪽이 제안한 가정이다.
- **알림:** 사용자 행동이 필요한 사건에만 보낸다. 즉시 보고, 정리본 승인 요청, 모음 보고, 최종 보고다. 단순 진행(이슈 하나 완료 등)은 화면에서만 본다.
- 나중에 픽셀형 화면을 만들 예정이며 이번 범위 밖이다.

## 3. 흐름

### 3.1 큰 구분

- **대화형**(브레인스토밍, "어디까지 진행했어?"): 코디네이터가 직접 답한다. 팀에게 맡기지 않고 승인 절차도 없다.
- **작업형:** 정리본 경로 또는 직접 지시 경로를 따른다.
- 요청을 코디네이터가 자동으로 분류하지 않는다. 대화형이 기본이고, 작업으로 넘어가는 것은 사용자의 동의와 직접 지시로 이루어진다. 코디네이터가 스스로 작업을 시작하지 않는다.

### 3.2 정리본 경로 (큰 작업)

1. 브레인스토밍으로 요구를 다듬는다.
2. 질문이 끝나 보고서로 만들 단계가 되면, 코디네이터가 **"보고서로 만들까요?"** 라고 묻는다.
3. 코디네이터가 정리본(목표, 범위, 완료 기준, 가정)을 만들어 사용자에게 승인을 요청한다. 정리본에는 사전 검토 단계가 없다.
4. 사용자가 승인하면 필요한 어드바이저를 불러 제안문을 받고, 리뷰어의 허용을 받는다(3.5절).
5. 코디네이터가 제안문을 바탕으로 큰 영역 목표와 작은 작업 단위로 쪼개 이슈로 등록하고, 알맞은 오퍼레이터에게 하달한다. 승인이 곧 분해의 시작이며 시작을 따로 받지 않는다.

승인 전에는 분해하지 않는다.

### 3.3 직접 지시 경로 ("~수정해줘")

- 사용자의 지시가 곧 승인이다. 정리본이나 분해안 확인 없이, 코디네이터가 필요한 어드바이저에게 제안문을 받고, 리뷰어가 허용한 제안문을 단계로 쪼개 이슈로 올린다(3.5절).
- 다음 세 경우에는 **먼저 묻는다.**
  1. 완료 기준을 "기준 / 확인 방법"으로 쓸 수 없을 때 (예: "조금 더 밝게"가 어느 정도인지 모름)
  2. 대상이나 범위가 둘 이상으로 해석될 때
  3. 삭제, 덮어쓰기, 외부 공개처럼 되돌리기 어려운 결과일 때
- 그 밖에는 묻지 않고, **가정을 이슈의 근거 칸에 적고 진행한다.** 가정은 리뷰어 판정과 코디네이터 대조 단계에서 확인된다.

### 3.4 결과 보고 흐름

| 관문 | 보는 것 | 불통과 시 |
|---|---|---|
| 리뷰어 | 산출물(보고서)이 맞는가 | 오퍼레이터에게 되돌림 |
| 코디네이터 | 승인된 요구(완료 기준)를 다 채웠는가 | 재작업으로 돌림 |

0. 오퍼레이터가 작업 단위마다 워크트리를 만들어 워커에게 맡기고, 워커는 워크트리마다 오퍼레이터에게 보고한다. 오퍼레이터는 결과를 합치고 확인 방법(테스트 등)을 돌린다. 리뷰어가 거부하면 합친 것을 되돌리고 재작업한다. 이 단계는 오퍼레이터·워커 내부이므로 코디네이터는 결과 보고서만 본다. **(대체됨 → ADR 0003 결정 A·B, [operator.md](operator.md) 4절: 워커 결과를 머지 큐로 통합 브랜치에 합치고, 리뷰어가 판정한 뒤 사용자가 `main` 반영을 결정한다. 거부되면 합친 것을 되돌리지 않고 거부된 범위를 미완료로 표시해 그 이슈만 재작업한다.)**
1. 오퍼레이터가 결과 보고서를 이슈 댓글로 올린다.
2. 리뷰어가 검토하고 허용/거부를 이슈 댓글로 남긴다. 허용된 것만 코디네이터에게 도달한다. **(실행 방식 대체됨 → ADR 0004 결정 B·C: 코디네이터가 `run-reviewer.mjs --issue <번호>`로 리뷰어를 띄운다. 스크립트가 워커 타입과 다른 리뷰어 모델을 고르고, Pi 등으로 읽기 전용 실행을 띄워 판정을 이슈 댓글로 남긴다. 판정 형식은 `## 리뷰어 판정: 허용` 아래 `허용된 커밋: <40자리 해시>` 한 줄이고, 이 형식이 아니면 거부로 처리한다. 거부는 첫 줄 `## 리뷰어 판정: 거부`, 다음 줄부터 이유다(거부 형식은 임시, 이슈 #2). 댓글에는 리뷰어 모델 이름과 실행 흔적이 남고, Gemini이면 `agy` 흔적이 없을 때 결과로 인정하지 않는다. 코디네이터에게는 `<댓글 URL> | 리뷰어 판정: 허용|거부 | 모델: ...` 한 줄만 간다. 스크립트 이름·인자, 결과 판정을 코디네이터가 띄우는 것, 순환 단위와 기록 위치, Pi를 거치지 않는 gemini·claude 경로는 임시(이슈 #2).)**
3. 코디네이터가 승인된 완료 기준과 항목별로 대조한다. 미충족이면 재작업으로 돌린다.
4. 통과하면 요약해서 사용자에게 보고한다. 확인 방법이 "사용자가 직접 보고 확인한다"인 항목은 최종 보고에서 따로 표시한다.

### 3.5 어드바이저 제안문: 리뷰어 허용과 부족할 때

**리뷰어 허용/거부 (ADR 0002 결정 A)**

- 어드바이저 제안문이 나오면 코디네이터가 리뷰어에게 넘겨 허용/거부를 받는다. 허용된 것만 이슈로 만든다. **(ADR 0004 결정 B에 따라 리뷰어는 하위 에이전트가 아니라 별도 실행이다. ~~조언 판정은 이슈도 커밋도 없는 단계라 판정 형식과 실행 수단이 미결이고, 아직 구현되지 않았다: 임시(이슈 #2).~~)** **(구현됨 → ADR 0006·0008: 어드바이저가 제안문을 리뷰어 전용 폴더에 쓰고 `run-reviewer --advice`로 Jev 판정을 받는다. 코디네이터가 정한 조언 id로만 판정받는다, 이슈 #42.)**
- 거부되면 **거부 이유와 함께** 어드바이저에게 되돌려 수정하게 한다. 수정본은 다시 리뷰어에게 간다.
- 거부 후 수정은 **2회**(시작값)까지다. 2회 고친 뒤에도 거부되면 코디네이터가 "제안, 이유, 예상 결과" 형식으로 사용자에게 묻는다. **(바뀜 → 소유자 결정 8-2: 거부 후 수정은 1회, 판정은 첫 제출을 합쳐 2번이다. 한도는 `run-reviewer --advice`가 지킨다, ADR 0006 결정 5.)**
- 이 횟수는 아래의 "코디네이터가 부족하다고 볼 때의 수정본 1회"와 **따로 센다.** 이슈가 생기기 전이므로 7.2절의 이슈당 재작업 한도에도 포함하지 않는다. **(바뀜 → 소유자 결정 8-3: 아래 수정본 1회는 없앴다. 횟수는 위 한도 하나다. 7.2절 한도에 넣지 않는 것은 그대로다.)**

**코디네이터가 부족하다고 볼 때** **(대체됨 → 이슈 #2 결정 3-4, 소유자 결정 8-3: 부족한지는 리뷰어가 조언 판정에서 거부로 판단하고, 코디네이터가 따로 다시 묻는 단계는 없앴다. 아래 항목 구성 줄만 유효하다.)**

- 제안문에는 영역별 작업 단위마다 **목표 / 완료 기준(기준·확인 방법) / 먼저 끝나야 할 것 / 전제·위험**을 담는다. 이 항목 구성은 설계를 정리하는 쪽이 해석한 것이다.
- 코디네이터가 모르는 부분이 생기면 어드바이저에게 부족한 부분을 다시 묻고, 수정본을 **1회** 받는다.
- 그래도 부족하면 그때 사용자에게 "제안, 이유, 예상 결과"로 묻는다.
- "부족하다"의 세부 기준은 미결이다.

### 3.6 작업 중 요구가 바뀔 때

- 영향받는 이슈만 보류하거나 중단하고, 영향이 없는 이슈는 계속 진행한다. 바뀐 부분은 새 이슈로 올린다.
- 어느 이슈가 영향받는지 판단이 애매하면 일단 보류하고 사용자에게 확인한다.
- 사용자에게는 "계속하는 이슈 / 보류하는 이슈 / 새로 올린 이슈"를 한 번에 보고한다.
- ~~정리본 경로에서 승인본이 이미 있을 때 요구 변경을 새 버전(vN+1) 승인으로 처리할지 바로 처리할지는 미결이다.~~ **(v0 정함, 소유자 결정 8-11 위임: 승인본이 있어도 요구 변경은 위 세 줄대로 바로 처리한다. 새 승인은 받지 않는다. 시나리오 8 대본.)**

### 3.7 승인 규칙 (정리본 경로)

- 승인으로 인정하는 것은 "승인", "진행해" 같은 **분명한 표현**뿐이다.
- "좋아 보이네", "음, 그렇게 해" 같은 애매한 말은 승인으로 보지 않고 "이대로 진행해도 될까요?"라고 한 번 더 확인한다.
- 직접 지시 경로는 지시가 곧 승인이므로 이 규칙의 대상이 아니다.
- ~~승인 표현의 기본 목록은 미결이다.~~ **(v0 정함, 소유자 결정 8-11 위임: 따로 목록을 두지 않고 위 두 줄의 규칙만 쓴다. 애매하면 한 번 더 확인한다.)**

### 3.8 질문 형식

사용자에게 모호한 점을 묻는 모든 질문은 **제안, 이유, 예상 결과** 형식을 따른다.

### 3.9 완료 기준의 형식

- 완료 기준은 **"기준 / 확인 방법" 두 열**로 적는다. 각 기준은 충족/미충족을 가릴 수 있는 문장이어야 한다.
- 주관적인 기준(예: "밝은 느낌")은 "제안, 이유, 예상 결과" 형식으로 물어 **수치나 기준 샘플**을 사용자와 합의해서 적는다.
- 수치로 바꿀 수 없는 일은 확인 방법을 "사용자가 직접 보고 확인한다"로 적는다.
- 이 형식은 정리본, 이슈, 리뷰어의 판정, 코디네이터의 대조, 결과 보고서에 공통으로 쓴다.

### 4.3 이슈 취소

1. 잘못 올린 이슈는 **중지**하고, 이슈에 **취소한 이유 / 해결방법 / 방법을 고른 이유**를 적는다. 중지는 하위에게 중단을 알리는 것을 포함한다.
2. 취소된 이슈가 **8개** 쌓이면 사유를 종합해 중복을 정리하고 문서로 남긴다. 문서에는 이슈별 재작업 횟수, 사용량 합계, 누락 보고 건수도 한 줄씩 옮겨 적는다.
3. 정리 문서를 사용자에게 보여 주고(모음 보고에 함께 담음) ~~**확인을 받은 뒤에만** 이슈를 삭제한다. 확인이 없으면 삭제하지 않고 닫힘 상태로 둔다.~~
4. ~~GitHub에서 이슈 삭제에 별도 권한이 필요한지는 구현 단계에서 확인한다.~~

**(바뀜 → 소유자 결정 6, 이슈 #2):** 이슈는 삭제하지 않는다. **"취소" 라벨을 붙여 닫는다**(`gh issue close`). 삭제 권한은 넓히지 않는다.

## 5. 기록과 컴팩션

### 5.1 기록 문서

- 코디네이터는 세션이 바뀌어도 이어갈 수 있도록 **프로젝트 단위 기록 문서**를 지정 저장소에 남기고, 새 세션은 그 문서를 읽고 시작한다. 대화 자체는 기억하지 않는다.
- **갱신 원칙:** 각 계층은 상위에게 전달하는 순간에 자기 기록을 갱신한다. 코디네이터의 상위는 사용자다.
- **모든 갱신에 공통으로 남기는 것:** 현재 승인본 버전, 지금 기다리는 대상(사용자 / 오퍼레이터 / 리뷰어), 갱신 순번과 시각.

| # | 갱신 시점 | 기록 내용 |
|---|---|---|
| 1 | 정리본 승인을 요청할 때 | 승인 대기 초안(목표, 범위, 완료 기준, 가정). 반려되면 초안은 이력으로 넘김 |
| 2 | 예외를 보고할 때 (재작업 한도 초과, 진행 불가, 확인 불가 등) | 대상 작업, 사유, 재작업 회차, 사용자에게 구한 결정 |
| 3 | 최종 보고를 할 때 | 어느 작업의 보고인지, 리뷰어 판정, 기준별 대조 결과(승인본 버전 명시), 보고 요약 |

- **전달 규칙:** 보내기 전에 "전달 예정"을 먼저 기록하고, 보낸 뒤 "전달 확인" 또는 "확인 불가"를 기록한다. 확인 불가면 다시 보내기 전에 먼저 확인한다.
- **기록하지 않는 것:** 사용자에게 한 질문과 받은 답변. 분배, 전달 확인, 리뷰 결과 도착 같은 중간 단계도 갱신 시점이 아니다.
- 막힌 이슈의 예외 보고는 이슈가 막힐 때마다가 아니라 모아서 사용자에게 전달하는 순간(7절)에 갱신한다.
- 세션이 끊겨도 이슈 목록에 분배 상태가 남아 있으므로 복구할 수 있다(ADR 0001 결정 3).
- 오퍼레이터, 워커, 리뷰어도 같은 원칙으로 자기 기록을 갱신한다. 그 내부 설계는 범위 밖이다.

### 5.2 컴팩션 (코디네이터만)

대화가 길어져 컴팩션이 일어날 때의 규칙이다. **앞과 끝은 지키고 중간만 압축한다.**

| 구간 | 내용 | 처리 |
|---|---|---|
| 앞 | ADR, 프로젝트 규칙, 용어 정의 | 대화에 두지 않고 파일(`AGENT.md`, `docs/`)로 관리하고 컴팩션 후 다시 읽는다 |
| 중간 | 지나간 작업 과정, 도구 출력, 논의 | 압축 대상 |
| 끝 | 최근 대화 | 컨텍스트 창의 10%까지 원문 유지 |

**중간 압축 순서**

1. **보존 항목을 먼저 원문으로 뽑아 둔다.** 사용자의 명시적 지시와 제약, 확정된 결정과 이유, 변경한 파일 경로와 식별자, 미해결 오류의 핵심 메시지, 남은 작업, 승인 대기 항목, 파일에 아직 반영하지 않은 정의.
2. **큰 도구 출력은 참조로 바꾼다.** 50줄 또는 2K 토큰을 넘는 출력은 필요한 부분만 남기고 나머지는 다시 얻는 방법으로 대신한다. 파일은 `[ref: 경로 | 줄 범위 | 요약]`, 명령·검색 결과는 `[ref: 다시 실행할 명령 또는 URL | 요약]`. 다시 얻을 수 없는 출력은 필요한 부분을 원문으로 남긴다.
3. **잡음을 지운다.** 단순 성공 메시지와 빈 결과는 "성공 출력 N건 생략" 한 줄로 묶는다. 오류나 경고가 섞인 줄은 지우지 않는다.
4. **남은 대화만 요약한다.** 위 단계를 거친 나머지(진행 과정, 논의)만 요약한다.

**보존 항목 관리**

- 지시나 결정이 바뀌면 이전 항목에 "철회됨"을 표시하고 최신 항목만 유효로 본다.
- 해결된 오류와 끝난 작업은 정리해 목록이 커지지 않게 하며 목록 상한은 창의 5%다.
- 긴 오류는 유형, 핵심 메시지, 첫 3~5줄만 남기고 전체 스택은 참조로 둔다.
- 비밀값은 적지 않고 존재와 용도만 적는다.

**보존 노트**

- 보존 항목은 기록 문서와 분리된 **"보존 노트" 파일**에 적고 컴팩션 후 다시 읽는다. 지정된 **비공개 저장소**에만 둔다.
- 갱신 시점은 기록 문서와 별개로 컴팩션 직전과 보존 항목이 생기거나 철회될 때다. 이 시점은 설계를 정리하는 쪽이 제안한 것이다.

**압축 후 검증**

- 보존 항목이 모두 남았는지 확인하고, 빠진 항목은 파일이나 트랜스크립트에서 다시 찾는다. 찾지 못하면 추측으로 채우지 않는다.
- 결과는 **완료 / 일부 누락 / 복구 실패** 중 하나로 사용자에게 보고한다.

**한계**

- Claude Code에서는 컴팩션을 하네스가 하므로, 이 방식은 에이전트가 컴팩션 전에 무엇을 남길지 정하는 규칙으로 적용된다. 압축 과정 자체를 바꾸려면 훅이나 별도 구현이 필요하다.
- 컴팩션 직전 신호를 받을 수 있는지는 미확인이다.
- 위 숫자는 모두 측정하지 않은 시작값이다.

## 6. 선호

- 선호 문서는 **코디네이터가 사용자와 소통하는 방식**만 담는다. 작업 결과물에 대한 선호(기술, 코드 스타일, 디자인 취향)는 담지 않는다.

| 항목 | 예 |
|---|---|
| 출력 양식 | 선호하는 보고서 양식, 답변 양식 |
| 보고 상세도 | 짧게 / 자세히 |
| 질문 빈도 | 얼마나 자주 묻는가 |
| 말투 | 어조, 표현 방식 |
| 승인 받는 방식 | 승인을 어떻게 요청하고 받는가 |

- 사용자가 **직접 말한 선호**는 바로 저장한다.
- 코디네이터가 **추론한 선호**는 같은 요청이 세 번째 나올 때 "제안, 이유, 예상 결과" 형식으로 제안하고, 승인받은 뒤에만 저장한다. 앞의 두 번은 요청대로만 처리하고 저장하지 않는다.
- 거절된 제안은 같은 내용으로 다시 하지 않는다.
- 선호를 바꾸거나 지우는 방법은 따로 정하지 않고, 사용자가 직접 말하면 바로 갱신한다.
- 선호 문서의 위치는 지정 저장소를 따른다. 기록 문서와 별개이며, 선호가 확정되는 순간에 기록한다.

## 7. 실패와 예외 처리

### 7.1 실패 종류별 처리

| 실패 | 처리 |
|---|---|
| 코디네이터 자신의 도구 실패 (지정 저장소·GitHub 접근 불가, 공개 저장소 지정 등) | **즉시 중단하고 사용자에게 알림** |
| 맞는 어드바이저가 없음 | **즉시 보고** (이슈를 올리지 않음) |
| 그 밖의 개별 역할·이슈 실패 (오퍼레이터 무응답, 전달 확인 불가 등) | 해당 이슈만 **보류**하고 나머지는 계속, **모아서 추후 한 번에 보고** |
| 조사 실패 (직접 호출한 오퍼레이터가 결과를 못 주거나 응답이 없음) | **1회 다시 시키고**, 그래도 못 찾은 것이 있으면 코디네이터가 추천 대안, 이유, 예상 결과를 만들어 **사용자에게 묻는다** (7.5) |

### 7.2 재작업 한도

- 재작업은 **이슈당 5회**까지이며, 리뷰어 거부와 코디네이터의 완료 기준 미충족을 **합산**해서 센다(바뀜 → 결정 8-44: 2회에서 5회로).
- 리뷰어 거부 이유 가운데 `[사용자 결정]`이 붙은 것은 재작업으로 고치지 않는다. 결정 이슈로 사용자에게 묻고, 답을 받은 뒤 다시 한다(결정 8-44).
- 한도를 넘으면 그 이슈만 보류하고 **막힌 이슈**로 모은다. 나머지 이슈는 계속 진행한다.
- 완료 기준을 바꿀 수 있는 것은 사용자뿐이다. 코디네이터가 스스로 기준을 낮추지 않는다.

### 7.3 막힌 이슈의 모음 보고

다음 중 하나에 해당하면 막힌 이슈를 모아 사용자에게 보고한다.

1. 막힌 이슈가 **3개** 쌓였을 때
2. 막히지 않은 나머지 이슈의 작업이 **모두 끝났을 때**
3. 사용자가 진행 상황을 물을 때. 이때 막힌 이슈가 있다는 사실은 **숨기지 않고** 알린다.

보고에는 왜 막혔는지와 해결 선택지(요구 조정 / 한도를 늘려 재시도 / 포기 등)를 "제안, 이유, 예상 결과" 형식으로 담는다. 막힌 이슈에 의존하는 다른 이슈의 연쇄 처리는 미결이다.

### 7.4 응답 없음 판정

- (1) **끝났는데 결과 보고서가 없음**: 상태 기준, 즉시 판정한다.
- (2) **너무 오래 변화가 없음**: 시간 기준의 안전망이며 시간 값은 운영하며 정한다. **(정함, 2026-11-19 run-7: 워커는 15분 동안 출력이 없으면 끊고 대체 모델로 넘긴다(`run-worker`). 하달·조사 세션은 2시간 제한이다. 코디네이터는 하달을 9분마다 `wait-operator`로 이어 기다린다.)**
- 판정되면 이슈 상태를 **한 번 재확인**하고, 그래도 응답이 없으면 막힌 이슈로 모은다.

### 7.5 조사 실패

> **일부 대체됨 →** ADR 0003 결정 D, E. 조사가 이슈가 되므로 "직접 호출", "호출부터 결과까지 15분" 판정은 조사 이슈의 상태와 종료 코드(`operator.md` 10.4절) 기준으로 다시 정한다. 재요청 1회와 사용자에게 묻는 규칙은 유지된다.

- 코디네이터나 어드바이저가 직접 호출한 조사(2.2절)의 결과가 오지 않거나 실패하면 **1회 다시 시킨다.**
- 1회 추가 조사 후에도 **못 찾은 것이 있으면** 코디네이터가 "추천 대안, 이유, 예상 결과"를 만들어 **사용자에게 묻는다**(3.8절 질문 형식). 가정으로 메워 진행하지 않는다.
- 어드바이저의 조사에서 못 찾은 것이 있으면, 어드바이저는 제안문에 못 찾은 항목을 밝혀 코디네이터에게 알리고 사용자에게는 코디네이터가 묻는다. 사용자와 대화하는 것은 코디네이터뿐이기 때문이다. `[보충]`
- 사용자의 답은 해당 이슈의 근거 칸에 적는다. `[보충]`
- 질문은 못 찾은 것이 확정되면 **바로** 한다. 모음 보고(7.3절)를 기다리지 않는다. 같은 시점에 못 찾은 것이 여럿이면 하나의 질문으로 묶는다.
- 답이 올 때까지 그 작업만 멈추고, 영향 없는 이슈는 계속 진행한다.
- **실패로 판정하는 경우**(재요청 대상)는 다음 다섯 가지다.
  1. 호출한 조사가 오류로 끝나거나 중단됨
  2. 끝났는데 결과가 없음
  3. 결과가 왔지만 요청한 질문에 답하지 않았거나 근거 위치(파일, 문서)가 없음
  4. "찾지 못했다"는 답
  5. 호출부터 결과까지 **15분**(시작값)을 넘겨도 응답이 없음. 직접 호출한 조사는 댓글이나 상태 변경이 없으므로 총 경과 시간으로 센다.
- 코디네이터는 결과의 품질을 평가하지 않고 위 항목이 있는지 없는지만 확인한다. `[보충]`

| 4 | 직접 지시 | 지시가 곧 승인이고, 3.3의 세 경우에만 먼저 묻고 나머지는 가정을 근거 칸에 적는다 |
| 5 | 주관적 기준 ("조금 더 밝게") | 수치나 기준 샘플을 합의하거나 "사용자가 직접 보고 확인한다"로 표시한다 |

| 7 | 결과 보고 | 리뷰어를 통과한 것만 기준별로 대조하고, 미충족은 재작업으로 돌린다 |

| 10 | 컴팩션 | 보존 항목이 남았는지 검증하고 완료/일부 누락/복구 실패를 보고한다 |
| 11 | 조사 | 가벼운 확인은 코디네이터가 읽기 전용으로 직접 하고, 깊은 조사는 오퍼레이터에게 시킨다. 어드바이저가 자료가 필요하면 오퍼레이터에게 시켜 결과를 받은 뒤 제안문을 쓴다 **(대체됨: ADR 0003 결정 D, 조사 이슈를 올려 오퍼레이터를 별도 세션으로 띄운다. 오퍼레이터 시험은 `operator.md` 13절)** |
| 12 | 조언 거부 | 리뷰어가 거부한 조언은 이유와 함께 어드바이저에게 돌아가고, 1회 수정 후에도 거부되면(판정은 첫 제출을 합쳐 2번) 사용자에게 묻는다(소유자 결정 8-2). 허용 전에는 이슈를 올리지 않는다 |

- **관찰 지표 (목표값 없음):** 누락 보고 건수(사용자가 "이건 빠졌네"라고 한 횟수), 사용자 호출 횟수(요청 한 건당), 재작업 횟수(한도 초과 포함). 우선순위(누락 > 왜곡 > 과도한 호출)를 따라간다.
- **비목표:** ~~오퍼레이터,~~ 워커, 리뷰어, 어드바이저의 내부 설계 / 코디네이터의 직접 구현·실행 / 여러 사용자·팀 협업(나중에 추가). **(오퍼레이터는 설계 대상이 되어 비목표에서 빠진다. 대체됨 → ADR 0003, [operator.md](operator.md) 15절의 비목표를 따른다.)**

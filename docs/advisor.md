# 어드바이저 설계

- 실행 문서: [`harness/advisor/AGENT.md`](../harness/advisor/AGENT.md) (설치하면 실행 폴더의 `.claude/agents/advisor.md`)
- 스킬: `harness/advisor/skills/advisor-proposal`, `advisor-data-request`, `advisor-domain-knowledge`(분야 지식, 8절), `advisor-panel`(패널, 7절). 설치하면 실행 폴더의 `.claude/skills/`에 들어가고, 정의의 `skills:` 칸(설치 때 넣음)으로 하위 에이전트가 시작할 때 본문이 미리 주입된다. 어드바이저에게 Skill 도구는 주지 않는다.
- 결정: ADR 0002(조언을 리뷰어가 거른다), ADR 0006(어드바이저가 리뷰어를 직접 부른다), ADR 0008(리뷰어는 Jev). 이슈 #42, 소유자 위임 8-11, 결정 8-15
- 이 문서는 옛 `docs/harness/advisor.md`를 넓힌 것이다.

## 1. 개요

어드바이저는 "작업을 어떻게 나눌지"를 제안문으로 쓰는 역할이다. 코디네이터가 부르는 **Claude Code 하위 에이전트**(`subagent_type: advisor`)다. 조언만 하고, 이슈 등록과 하달은 코디네이터가 한다.

제안문은 리뷰어(Jev)의 허용을 받아야 코디네이터에게 간다. 조언이 틀리면 그 뒤의 이슈가 모두 틀어지므로, 영역 판단을 하지 않는 코디네이터 대신 리뷰어가 조언 단계에서 한 번 거른다(ADR 0002).

## 2. 하는 일과 하지 않는 일

| 하는 일 | 하지 않는 일 |
|---|---|
| 대상 프로젝트를 읽기 도구로 읽기 | 대상 프로젝트 고치기, 실행하기 |
| 작업 단위로 나눈 제안문을 `reviewer-inbox/<조언 id>.md`에 쓰기 | 다른 곳에 쓰기 |
| `run-reviewer.mjs --advice … --advice-id <id>`로 판정받기, 거부면 같은 id로 한 번 고쳐 다시 받기 | 스스로 조언 id 만들기, 판정 줄 고쳐 쓰기 |
| 자료가 모자라면 `자료 요청: <영역> / <질문>` 한 줄 돌려주기 | 직접 깊은 조사(오퍼레이터의 조사 이슈로 한다) |

## 3. 입력과 출력

- **입력(코디네이터가 넘김):** 사용자 지시 원문, 대상 프로젝트 경로, 코디네이터가 정한 조언 id, (있으면) 조사 결과 파일 경로.
- **제안문 양식:** `## 작업 단위 …` 절마다 `### 목표`, `### 완료 기준`(`| 기준 | 확인 방법 |` 표), `### 먼저 끝나야 할 것`, `### 전제·위험`. 리뷰어 코드가 글자까지 검사한다.
- **출력:** 판정 스크립트의 출력 줄을 그대로 돌려준다. 허용 줄에는 `허용된 조언: <64자리>`, `전달 파일: <경로>`, `조언 id: <id>`가 있다.

## 4. 작업 단위 나누기 (결정 8-15)

- 단위 하나는 **작은 모델도 이슈 글만 보고 한 번에 끝낼 수 있는 크기**다. 고칠 파일과 기대 동작을 이름으로 적을 수 있어야 하고, 넘으면 더 나눈다.
- 서로 다른 파일·관심사는 다른 단위로 나눈다. 핵심 로직과 그것을 쓰는 진입점이 둘 다 바뀌면 두 단위로 나누고 순서를 "먼저 끝나야 할 것"에 적는다.
- 문서·예시만 바꾸는 일은 코드 단위와 따로 둔다. 지시에 없는 일을 더하지 않는다.

## 5. 판정과 한도

- 판정은 [reviewer.md](reviewer.md)의 조언 판정이다. 같은 조언 id는 **2번까지만** 판정받는다. 2번째도 거부되면 스크립트가 종료 코드 7로 끝나고, 코디네이터가 기록된 해시와 거부 이유로 사용자에게 묻는다.
- **조언 id 우회 막기:** 코디네이터는 돌아온 허용 줄의 `조언 id`와 `advice-log.jsonl`에 기록된 그 해시 줄의 `adviceId`가 자기가 넘긴 id인지 확인한다. 다른 id로 받은 허용은 쓰지 않는다.

## 6. 실행과 안전

- **모델:** 코디네이터와 같은 급(`model: inherit`). 분해가 틀리면 워커·리뷰어 비용이 전부 낭비되므로 여기서 아끼지 않는다.
- **도구:** Read, Grep, Glob, Write, Bash. 훅이 쓰기는 `reviewer-inbox/`로, 명령은 `run-reviewer.mjs --advice` 한 모양으로 막는다(ADR 0006 결정 2).
- **결과 돌려주기:** 대화형 세션에서는 하위 에이전트가 `SubagentHandback`으로 결과를 돌려준다. guard는 advisor에게 이 도구를 허용한다(run-18에서 막혀 "보고 없이 끝남"이 된 것을 고침). 파일·명령·밖에는 닿지 않는 도구다.
- **시험용 대역:** `setup --advisor-stub`은 `harness/stubs/advisor-stub.md`를 대신 설치한다.

## 7. 한계

- v0의 어드바이저 **정의**는 대상 프로젝트 전체를 맡는 하나다. 조언은 그 하나를 세 자리로 불러 패널로 받는다(결정 8-24, 아래). 훅이 하위 에이전트 이름 `advisor` 하나만 받고, 하위 에이전트끼리는 말할 수 없어 overview 2.3의 "영역별 어드바이저, 겹치면 모두 부르고 협의" 가운데 영역별 정의는 v1로 미룬다. 협의는 결정 8-24의 패널로 했다: 하위 에이전트끼리 말할 수 없으므로 코디네이터가 중계하고, 초안은 파일로 나눈다.
- 분야 지식 파일(8절)은 이 하나의 어드바이저 정의에 붙는다. 분야별 어드바이저를 따로 두고 코디네이터가 골라 부르는 것은 v1이다.
- **패널(결정 8-24):** 코디네이터가 `advisor`를 자리 a(단위 나누기)·b(전제·위험)·c(완료 기준)로 세 번 불러 `reviewer-inbox/panel/<조언 id>/<자리>.md`에 초안을 쓰게 한다. 다시 세 번 불러 서로의 초안을 읽고 자기 초안을 고친 뒤 `추천: <자리>` 한 줄을 받는다. 두 표 이상(셋이 다르면 a의 추천)인 초안으로 최종 어드바이저 한 번이 조언 판정을 받는다. 조언 한 번에 어드바이저 호출 7번이 든다. 초안·교환 단계에는 조언 id를 주지 않아 판정 한도를 쓰지 않는다. 코디네이터는 초안 본문을 읽지 않는다. 초안 파일은 지울 도구가 없어 남는다. 스킬: `advisor-panel`, `coordinator-advice` 2번.

## 8. 분야 지식 (결정 8-23)

- **무엇:** 어드바이저 스킬 `advisor-domain-knowledge`와 그 옆의 `knowledge/<분야>.md` 6개(웹 사이트, 앱, 게임 개발, 보안, 마케팅, 디자인). 분야마다 개념 영역 8개를 원리, 판단 규칙, 트레이드오프, 흔한 오해나 실패 사례로 정리한 시니어 수준의 일반 원리다.
- **어떻게 받나:** `setup`이 SKILL.md와 지식 파일을 `.claude/skills/advisor-domain-knowledge/`에 설치한다. 미리 주입되는 것은 짧은 SKILL.md뿐이고, 어드바이저는 지시가 닿는 분야의 파일만 Read로 읽는다. 여섯 개를 모두 주입하면 매번 약 7만 4천 자(파일마다 1만 1천~1만 4천 자)가 붙기 때문이다. 대상 프로젝트와 어긋나면 프로젝트가 우선이다.
- **어떻게 만들었나:** 분야마다 구조가 다른 후보 세 개(개념 지도형, 실패·점검형, 사례·결정형)를 썼다. 단서 없는 시험(지시나 계획만 주고 위험을 스스로 짚어야 점수)을 연습 8문제와 보류 16문제로 냈다. 연습에서 부족한 영역은 일반 원리로 보강했고(최대 2회), 보류 문제로 판정했다. 통과 기준은 모든 영역 평균 0.75 이상, 치명 오류 없음이다. 통과한 후보는 사실 검토를 받았다. 한 번은 틀린 주장을 찾고 다른 한 번은 그 지적을 따로 확인했다. 고른 파일에서 확인된 오류는 고쳤다.
- **고른 기준:** 확인된 오류 수, Sonnet 보류 평균, Opus 보류 평균 순이다. 다만 Sonnet에서 미달 영역이 남은 승자는 미달 없는 후보로 바꿨다(게임 개발 A를 B로, 마케팅 A를 C로). 확인된 오류는 어차피 고치므로 한두 건 차이보다 영역 미달이 더 큰 결함이라서다.
- **한계:** Opus는 지식 파일 없이도 웹(1.00), 디자인(0.95), 게임 개발(0.91)에서 기준을 넘었다. 파일 효과가 분명한 곳은 기준선에 미달 영역이 있던 앱, 보안, 마케팅이다. 점수는 사실 오류를 고치기 전 파일로 낸 것이다. 바꾼 두 승자만 고친 뒤 Opus로 다시 봤다. 채점도 같은 모델 계열이 했으므로 사람 전문가 검토를 대신하지 않는다. 시험은 파일 전체를 시스템 프롬프트에 넣고 풀게 했지만, 설치된 어드바이저는 스스로 골라 Read해야 한다. 이 경로는 아직 진짜 실행으로 확인하지 않았다. 제미나이 역할 문서 검토(읽기 전용) 뒤 파일마다 덧붙인 "더 짚을 것 (검토 보강)" 절은 채점 시험을 거치지 않았고, 사실 검토만 따로 했다.

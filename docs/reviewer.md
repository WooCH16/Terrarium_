# 리뷰어 설계

- 규칙 문서: [`harness/reviewer/AGENT.md`](../harness/reviewer/AGENT.md). 그 문서의 `## Jev 질문` 절을 `jev-review.mjs`가 읽어 판정 질문을 만든다.
- 스킬: `harness/reviewer/skills/reviewer-verdict`(판정 순서). Jev는 프롬프트를 읽지 않으므로 주입되지 않는 절차 문서다. 질문 문장은 옮겨 적지 않는다(`test/skills.test.mjs`가 막음).
- 실행 코드: `harness/operator/run-reviewer.mjs`(실행, 기록, 댓글), `jev-review.mjs`(코드 검사, 질문, 결정), `jev.mjs`(API 호출)
- 결정: ADR 0002(리뷰어가 두 곳을 거른다), ADR 0006(조언 판정), ADR 0008(Jev와 라우팅). ADR 0004의 모델 순환은 0008로 대체됐다. `pi-워커-리뷰어.md`는 그 전의 계획(안)이다.

## 1. 개요

리뷰어는 허용과 거부만 정하는 역할이다. 두 곳에서 거른다.

1. **조언 판정:** 어드바이저의 제안문을 이슈로 만들기 전에.
2. **결과 보고서 판정:** 오퍼레이터의 결과 보고서를 코디네이터가 완료 기준과 대조하기 전에.

리뷰어는 **Jev**(TypeSafe System One, HTTP API)다. 원칙은 **"판단은 Jev, 결정은 코드"**다. 기계적으로 볼 수 있는 것은 코드가 보고, 글을 읽어야 하는 판단만 Jev에 예/아니오 확률(Noul)로 묻고, 허용·거부는 코드가 정한다.

## 2. 하는 일과 하지 않는 일

| 하는 일 | 하지 않는 일 |
|---|---|
| 제안문·결과 보고서의 모양 검사(코드) | 코드 고치기, 이슈 만들기, 완료 기준 바꾸기 |
| 완료 기준 한 줄마다 두 질문을 Jev에 묻기 | 애매한 것을 허용하기(애매하면 거부) |
| 판정을 이슈 댓글이나 `advice-log.jsonl`에 남기기 | Jev 호출 실패를 거부로 읽기(판정 없음, 종료 코드 6) |

## 3. 실행

- **결과 보고서:** 코디네이터가 `node run-reviewer.mjs --issue <n> [--worker-model …]`로 부른다. 이슈의 가장 최근 `## 결과 보고서`를 판정하고 이슈 댓글로 남긴 뒤 `<댓글 URL> | 리뷰어 판정: 허용|거부 | 모델: jev (<모델 ID>)` 한 줄을 낸다. 허용 댓글은 `## 리뷰어 판정: 허용`과 `허용된 커밋: <해시>`로 시작하고, 합치기 스크립트는 이 줄만 받는다.
- **조언:** 어드바이저가 `node run-reviewer.mjs --advice <제안문> --advice-id <id>`로 부른다. 제안문은 `reviewer-inbox/` 바로 아래에 있어야 한다. 스크립트가 바이트를 한 번 읽어 SHA-256을 내고, 판정마다 `advice-log.jsonl`에 한 줄(시각, 파일, 조언 id, 해시, 판정, 거부 이유, 시도)을 남긴 뒤 제안문을 지운다. 허용이면 같은 바이트를 `handoffs/advice-<해시 앞 8자리>.md`로 옮긴다(훅이 쓰기를 막는 폴더).
- **설정:** `operator.config.json`의 `jev`: `endpoint`, `model`(고정 버전), `timeoutMs`, `yes`(0.7), `no`(0.3). 키는 `TYPESAFE_API_KEY`(환경 변수 → 실행 폴더 `.env` → 하네스 저장소 `.env`).

## 4. 코드 검사

하나라도 어긋나면 Jev를 부르지 않고 거부한다.

- **결과 보고서:** 첫 줄 `## 결과 보고서`, `커밋 해시:` 한 줄, 네 칸(기준별 충족 여부, 근거 위치, 변경 요약, 남은 문제), 이슈의 `## 완료 기준` 표, 보고서 표 `| 기준 | 충족 | 근거 위치 |`에 이슈의 기준이 그대로 있는지, 근거 위치의 파일이 보고서 커밋에 있는지(`git cat-file -e`).
- **제안문:** `## 작업 단위` 절마다 `목표`, `완료 기준`, `먼저 끝나야 할 것`, `전제·위험` 칸과 `| 기준 | 확인 방법 |` 표, 표의 빈칸.

## 5. Jev 질문과 결정

| 판정 | 질문(기준 한 줄마다) | 상태(Jev에 주는 글) |
|---|---|---|
| 결과 보고서 | `met`: 보고서가 이 기준을 충족으로 적었는가 / `evidence`: 근거 위치가 구체적인가 | 보고서 |
| 조언 | `decidable`: 완성된 결과를 보고 충족을 가릴 수 있는 기준인가 / `checkable`: 확인 방법을 실행하거나 볼 수 있는가 | 제안문 |

- 질문 문장의 기준은 규칙 문서의 `## Jev 질문` 절이다. 줄이 빠지면 판정하지 않고 오류다.
- 모든 질문이 예(`yes` 이상)일 때만 허용이다. 아니오(`no` 이하)나 애매(그 사이)가 하나라도 있으면 거부이고, 그 질문과 확률이 거부 이유가 된다. 판정 댓글에는 질문마다의 확률 표가 붙는다.
- 리뷰어는 늘 워커(claude, gemini, muse)와 다른 제공사이므로 "워커와 다른 리뷰어" 규칙(ADR 0004)은 저절로 지켜진다.

## 6. 한도와 실패

- 같은 조언 id는 2번까지만 판정한다. 이미 2번 거부됐으면 Jev를 부르지 않고 종료 코드 7로 끝난다.
- 일시적 실패(네트워크, 시간 초과, 429, 5xx)는 2번 다시 부른다. 그래도 실패하면 종료 코드 6이고, 코디네이터는 다시 부르지 않는다.
- **종료 코드:** `0` 판정을 남김, `2` 인자·설정·입력 오류(키 없음 포함), `4` 판정 중 제안문이 바뀜, `5` 판정 게시·기록 실패, `6` Jev 호출 실패, `7` 같은 조언이 이미 2번 거부됨. `3`은 쓰지 않는다(다른 스크립트에서 "중단").

## 7. 한계

- 리뷰와 라우팅이 Jev 한 곳에 달려 있다. 서비스가 멈추면 둘 다 멈춘다(알려진 한계 3).
- 판정 기록은 같은 컴퓨터의 파일이라 위조할 수 있다(알려진 한계 1).
- 결과 보고서는 보고서의 글을 판정한다. 코드가 실제로 맞는지는 근거 위치와 합치기 시험, 코디네이터의 대조로 본다.
